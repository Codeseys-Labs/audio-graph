## Closeability reason (acceptance audit)

Every criterion is backed by merged, verified code (audit note verdict: "5 of 6
criteria MET, 1 MET-with-minor-caveat, no hard gaps"):

1. **Settings-open debounced/cached health checks** — MET. `get_provider_readiness_cmd`
   (`commands.rs:7972`) with `PROVIDER_READINESS_TTL_MS = 5min` + `MIN_REFRESH = 15s`
   (`:166-167`), `cached_provider_readiness` staleness (`:7419`),
   `begin_provider_readiness_refresh` rate-limit + in-flight dedup (`:7438-7463`);
   frontend on-open call uses `refresh:true` without `force` (honors cache,
   `useSettingsController.tsx:2986`) + request-id cancellation (`:2307`).
2. **Remote catalog discovery** — MET for every implemented provider with a public
   list-models API (asr.api / asr.deepgram / llm.api / llm.cerebras / llm.openrouter);
   others are `Fixed`/`UserSupplied` by design. Saved keys resolve server-side
   (`handleRefreshModels` passes `apiKey || null`).
3. **Missing/expired recovery states** — MET. Status enum Ready/MissingCredentials/
   Unchecked/Error; `providerRecoveryAction` distinguishes present-but-rejected vs
   no-key. Caveat: no status distinct from generic `Error` for an *expired* key —
   cosmetic polish only.
4. **No plaintext secrets serialized** — MET. Key fields `#[serde(skip_serializing)]`;
   `CredentialStore` Zeroize+ZeroizeOnDrop, presence-only IPC; `load_settings_cmd`
   returns redacted settings; provider error bodies scrubbed (tested).
5. **Saved-credential presence enables controls without re-entry** — MET.
   `load_credential_presence_cmd` (`commands.rs:6380`); enablement =
   `savedKeyPresent || draft>0`; controls gated on `credentialAvailable`.
6. **Readiness by capability/mode** — MET. `ProviderCapabilityStageSection` /
   `ProviderCapabilityCard` (by stage) + `ProductModeSummaryCards` (per mode with
   readiness badge, stage coverage, blockers).

## 403d blocker plan (the one open seed)

**Fix (concrete, minimal):** In `src-tauri/src/fs_util/mod.rs`, replace the
`#[cfg(windows)]` block of `try_set_owner_only` that shells out to
`icacls <path> /inheritance:r /grant:r %USERNAME%:F` with a SID-native path:

1. `OpenProcessToken(GetCurrentProcess(), TOKEN_QUERY, …)` →
   `GetTokenInformation(TokenUser)` → `TOKEN_USER.User.Sid` (current process user SID,
   ground truth — no spoofable/absent `USERNAME`, no name→SID ambiguity, no subprocess).
2. Apply a protected, inheritance-removed DACL granting that SID full access via
   `SetNamedSecurityInfoW` with `DACL_SECURITY_INFORMATION |
   PROTECTED_DACL_SECURITY_INFORMATION` (DACL from `SetEntriesInAclW`/`EXPLICIT_ACCESS_W`,
   or SDDL `D:PAI(A;;FA;;;<SID>)`). Decide + document the built-in principals policy;
   faithful port = owner-SID-only, no SYSTEM/Admins.
3. **Preserve invariants:** `try_set_owner_only` stays `Result`, `set_owner_only`
   stays best-effort (swallow+WARN). Existing tests
   `set_owner_only_is_best_effort_and_never_aborts` (`credentials/mod.rs:2406`) and
   `save_completes_with_best_effort_hardening` (`:2425`) must stay green.
4. **Dep:** add `windows` as a direct `[target.'cfg(target_os="windows")'.dependencies]`
   entry in `src-tauri/Cargo.toml`, features `Win32_Security`,
   `Win32_Security_Authorization`, `Win32_Foundation`, `Win32_System_Threading`,
   `Win32_Storage_FileSystem`. Pin the same major (`0.62.x`) already resolved
   transitively via rsac in `Cargo.lock` to avoid a duplicate version;
   verify with `cargo tree -p windows`.
5. **Explicitly out of scope (regression-risky follow-up, not part of 403d):** making
   Windows also fail-closed at the pre-write step (`credentials/mod.rs:1254`). Changing
   `set_owner_only` → `try_set_owner_only?` there risks re-introducing the dropped-write
   regression the best-effort tests guard. 403d changes only *how the SID is resolved*.

**Executability / guardrail:** **EXECUTABLE — no needs-Windows-CI gate.** All changes
are behind `#[cfg(windows)]`; Unix (`0o600`) and other OSes untouched. Provable by a
`#[cfg(windows)]` unit test that writes a temp file, calls `try_set_owner_only`, reads
the DACL back via `GetNamedSecurityInfoW`, and asserts: (a) current-process token SID
present with full access, (b) DACL protected / inheritance removed (`SE_DACL_PROTECTED`),
(c) no unexpected principals. The existing Blacksmith `windows-2025` runner already runs
`cargo test --no-default-features --features cloud` (`.github/workflows/ci.yml:265-270`),
so the test executes automatically — no new CI job or guardrail. Only caveat: a true
end-to-end "another Windows user is denied read" behavioral proof needs a live
multi-account box, which is NOT required by 403d's acceptance.

## Remaining child seeds

Only 403d is a real remaining seed (tracked separately). The audit's two floated items
are OPTIONAL polish/consistency, not epic-blocking gaps — listed below so they are not
lost, but the epic does not need them to close:

1. **Distinct "expired/invalid credential" recovery state** (C3 polish, S, executable) —
   distinguish an auth-rejected saved key (401) from a generic transport error;
   `providerRecoveryAction` emits a dedicated "credential rejected — re-enter or rotate"
   string with a re-enter affordance; verified by a ProviderReadinessPanel test.
2. **Resolve Soniox remote-catalog wiring vs `Planned` status** (C2 consistency, S,
   executable) — `asr.soniox` is fully wired for remote discovery in the backend
   (`list_soniox_models_cmd`, `modelCatalogCommandArgs` arm) but `status: Planned` with
   no UI surface, so that catalog path is dead code from the UI. Either surface a Soniox
   settings section once promoted to Implemented, or gate the arm behind status; add a
   registry test asserting no Implemented-only frontend arm exists for a Planned provider.
