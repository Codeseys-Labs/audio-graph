# vLLM Semantic Router — Modular-Architecture Deep Dive

**Angle:** agent-runtime research, 2026-08-23. Deep-dive the project the maintainer calls "vllm-sr" to mine its modular architecture as inspiration for AudioGraph's Rust-backend-as-LLM-proxy/router shape — not for wholesale adoption. AudioGraph's scale is one user routing between 2-5 cloud providers (plus a future local engine), not a k8s-scale multi-tenant gateway.

## Verdict

**Identity confirmed, cleanly disambiguated: `github.com/vllm-project/semantic-router` ("vLLM Semantic Router," CLI/brand `vllm-sr`, homepage `vllm-sr.ai`) is a real, actively developed, Apache-2.0 project under the vLLM GitHub org — 5,210 stars, 823 forks, created 2025-08-26, now at release v0.3.0 ("Themis," June 2026) with 80+ contributor identities in that cycle and backing from Red Hat (project originator, Huamin Chen), Tencent, IBM, AMD, and DaoCloud.** It must not be confused with the older, unrelated `aurelio-labs/semantic-router` (a pure-Python, MIT-licensed, embedding-similarity route-matching library with no Go/Rust/Envoy component at all — same name, different project, different scale, different everything) — that confusion is easy to make and worth flagging explicitly since the maintainer's "vllm-sr" shorthand is the correct disambiguator. The architecture is genuinely modular and instructive: a Go "brain" (ExtProc filter + decision engine + plugin chain) calls into a family of Rust FFI libraries (`candle-binding`, `onnx-binding`, `nlp-binding`, `ml-binding`) for ML inference, and one of those Rust crates — `candle-semantic-router` — **is published to crates.io independently of the repo** (verified directly against the v0.3.0 release notes: `candle-semantic-router = "0.3.0"`), meaning it is a real dependable library, not just repo-internal glue. But the honest scale verdict is that almost none of this is worth porting wholesale into a one-user desktop app: the semantic classification layer (BERT/LoRA-based domain and PII/jailbreak classifiers, 10-120ms per call on CPU) is solving a problem AudioGraph mostly does not have — deciding *which model* to route to based on prompt content, across dozens of pooled models serving many tenants. AudioGraph's routing problem is a capability/cost/availability table over 2-5 known endpoints (already ADR-0038's shape), not a many-model traffic-shaping problem needing learned classifiers. The two ideas worth stealing are architectural, not the ML: (1) the **signal-extraction → decision-engine → plugin-chain** three-layer separation as a clean mental model for "route table + capability checks + guard plugins," reusable as pure logic with zero ML; and (2) the **PII/content-never-logged discipline as an explicit, named, opt-in plugin knob** (`router_replay`'s `capture_request_body`/`capture_response_body`, off by default in the maintainer's own security guidance) — directly on-point for AudioGraph's non-negotiable "transcript content must never enter logs" criterion. Everything Envoy/Kubernetes/Helm/Milvus-shaped is explicitly inspiration-only and should be discarded at AudioGraph's scale.

## B. Component map — who does what, and what's actually Rust vs. Go vs. Python

The repo is genuinely polyglot (Go, Rust, Python, C++, plus JS/React for the dashboard, per GitHub's language breakdown). The split by responsibility:

| Component | Language | Role |
|---|---|---|
| `extproc`/router core | **Go** | The "brain": Envoy ExtProc gRPC service, decision engine (Boolean-expression evaluation over signals), plugin chain orchestration, OpenAI/Anthropic request translation, cache backends (Redis/Milvus client code), dashboard backend API. Calls into Rust via CGO. |
| `candle-binding` | **Rust** (published crate: `candle-semantic-router`) | ML inference library — embeddings, BERT/LoRA classifiers, multimodal encoders, hallucination checks, MLP-based model selection — built on HuggingFace's Candle framework. Exposes C-ABI functions consumed by Go via CGO. Feature-gated backends: CUDA, Flash Attention 2, Intel MKL, macOS Accelerate. **Not a standalone server** — it is a library the Go process links against as a `.so`/`.a`, with a `OnceLock` pattern for thread-safe global model state. |
| `onnx-binding` | Rust | CPU-optimized inference path using mmBERT + 2D Matryoshka embeddings — a lighter alternative to full Candle/BERT for CPU-only deployments. |
| `nlp-binding` | Rust | Classical NLP: BM25, N-gram keyword classification — the "cheap, sub-millisecond, explainable" tier of signal extraction, deliberately kept separate from the ML tier. |
| `ml-binding` | Rust (via the `linfa` crate) | Classical ML: SVM, KNN — another non-neural, cheaper classification option. |
| `openvino-binding` | **C++** with a Go CGO bridge | Intel hardware acceleration path. |
| CLI (`vllm-sr`), e2e tests, training scripts, fleet simulator | **Python** | User-facing CLI (PyPI package `vllm-sr`), LoRA training pipelines, the "fleet simulator" (a discrete-event simulator for capacity planning, not a runtime component). |
| Dashboard | JavaScript/React (+ WizMap) | Config authoring UI, playground/chat interface, topology visualization. |

**Why this split exists (their framing, useful as a design lesson):** Go owns cloud-native infra concerns (gRPC service, Kubernetes-friendliness, plugin orchestration); Rust owns anything CPU-latency-sensitive (ML inference) so it can run without Python's GIL/runtime overhead in a request's hot path; Python is relegated entirely to CLI/tooling/training, never the request-serving hot path. **This three-way split — hot-path serving in a systems language (their choice: Go; AudioGraph's choice: Rust already) with FFI into a narrower Rust ML layer only where genuinely latency-sensitive, versus Python/scripting kept to CLI and offline tooling — is the one structural idea most transferable to AudioGraph**, which already has this shape natively (Rust owns the hot path; there is no analogous Python tier to segregate).

**Published Rust crate, verified directly:** the v0.3.0 GitHub release notes list, alongside the Python PyPI package (`pip install vllm-sr==0.3.0`) and Helm chart, an explicit **"Rust Crate (crates.io)"** section: `candle-semantic-router = "0.3.0"`. Cross-checked against crates.io itself: `candle-semantic-router`, current version 0.4.0, MIT OR Apache-2.0 dual-licensed, owned by `rootfs` (Huamin Chen), 456 total downloads, 0 reverse-dependents as of this research. **This is a real, independently-versioned, installable crate** — described on crates.io as "Go bindings for Candle BERT semantic similarity model for LLM routing" (the README literally documents building it as a Go-consumed native library via `cargo build --release`, not as a Rust-idiomatic crate for a pure-Rust consumer). **Caveat for AudioGraph:** its API surface is designed for CGO consumption from Go, not for ergonomic use from a pure-Rust binary — depending on it directly would mean adopting a crate whose primary/only consumer today is the semantic-router Go process itself (0 dependents confirms no other Rust project currently uses it as a library). It would be usable, but AudioGraph would be its first real independent Rust-native adopter, and should expect Go-oriented FFI ergonomics (fixed-size buffers, C-string marshaling patterns) rather than idiomatic Rust API design.

## C. The routing decision layer — what it classifies, with what, at what cost

The core mental model (their own framing, borrowed explicitly from Shannon's communication theory): a request goes through an **Information-Theoretic regime** (probabilistic signal extraction — turning a prompt into a structured "signal vector") followed by a **Boolean-Algebra regime** (deterministic decision-engine evaluation over that vector to pick exactly one model).

**Signal extraction layer** — 13 heterogeneous signal types, evaluated in parallel, computed lazily (only signals referenced by an active decision run):
- **Heuristic signals** (keyword match, language detection): sub-millisecond, deterministic, explainable — no ML at all.
- **ML-based signals** (embedding similarity, domain/intent classification, complexity scoring, jailbreak detection, PII detection): 10-120ms on CPU depending on token count and model choice.

**Models used for classification, by size/purpose:**
- **ModernBERT** (149M params, 8,192-token context) — historically the primary intent/jailbreak classifier; also used for hallucination detection and feedback classification.
- **Qwen3-Embedding** — up to 32,768-token context, 100+ languages, used where multilingual routing matters.
- **EmbeddingGemma-300M** — smaller footprint, 2,048-token context, Matryoshka representation learning for truncatable (cheaper) embeddings when full precision isn't needed.
- **LoRA adapters on BERT-base-uncased (110M params)** — the efficiency workhorse: each task-specific classifier adds <1M params via a LoRA adapter sharing one base-model forward pass, so N classification tasks cost roughly 1 base-BERT inference plus N cheap adapter passes, not N full BERT inferences. On CPU, LoRA-adapted inference runs close to base-model speed (~10-20ms).
- Concrete published latency numbers (from the v0.2 "Athena" release blog, AMD Instinct MI300X, ONNX+GPU): domain-extraction latency ranges 10.2ms (~500 tokens) to 36.1ms (~8,000 tokens); PII extraction 8.4ms-118.8ms across the same token range. On CPU, ML signal extraction overall sits in the 10-120ms band; decision-engine Boolean evaluation itself is <0.1ms (bounded at ≤50 decisions × ≤10 conditions each); model-selection-algorithm overhead ranges from <1ms (static selection) to 100-500ms if an LLM-based selector like "Router-R1" is used (their most expensive, least-common option).

**Decision engine:** each "decision" is a named Boolean formula over signal conditions (AND/OR/NOT), carrying its own candidate model set and plugin configuration — deployment-specific model pools rather than one global routing table. The best-matching decision wins by priority or confidence-weighted ranking.

**Honest scale read for AudioGraph:** this entire classification tier exists to solve "which of many pooled, interchangeable models should serve this specific prompt, given domain/complexity/language/safety signals, at production multi-tenant volume." AudioGraph's actual routing problem — as ADR-0038 already frames it — is "given 2-5 *known, named* provider endpoints with *known, static* capability facts (context window, structured-output support, streaming quirks), which one is eligible and preferred for *this operation type* (projection lane vs. final refinement)." That is a capability/eligibility table lookup, not a content-classification problem. Running a BERT classifier to decide "is this a coding question" only pays off when there are many candidate models with genuinely different specializations to route across; at 2-5 hand-configured endpoints the entropy this system is designed to reduce barely exists. **The 10-120ms per-request ML classification tax buys AudioGraph nothing at this scale** and would be pure overhead — this is the single most important "don't copy this" finding.

## D. Envoy ExtProc, Kubernetes, and the actual standalone mode

- **Primary integration is Envoy's External Processing (ExtProc) protocol** over gRPC (port 50051): Envoy intercepts an HTTP request, pauses it, ships the body to the router's gRPC endpoint, the router classifies/decides and returns header mutations (e.g., `x-selected-model: qwen-coder`), and Envoy resumes the request toward the chosen backend. Two Kubernetes deployment shapes exist: **Standalone** (router ships with its own Envoy sidecar as an ingress gateway — good for simple/dev setups) and **Gateway Integration** (reuses an existing Istio/Envoy Gateway mesh, router runs in pure-API mode without its own Envoy).
- **There is a genuine non-Kubernetes local mode**, and it is more developed than a cursory glance suggests: the `vllm-sr` Python CLI (PyPI: `pip install vllm-sr`, or a one-line install script) orchestrates a **Docker Compose** stack — Router + Envoy + Dashboard + storage backends (Redis/Postgres/Milvus) + fleet simulator — via `vllm-sr serve`, explicitly documented as suitable for "evaluation, local development, CI, edge hosts, and single-host deployments." It runs on CPU with no GPU requirement, using ONNX-optimized BERT models, and downloads ~1.5GB of models on first run. Default local ports: dashboard `:8700`, routed-inference OpenAI-compat listener `:8899`, router management API `:8080` (validation/eval/replay/vector-store).
- **The caveat that matters:** even the "local" mode still runs Envoy as a component (as a Docker container in the compose stack) — Envoy is not optional plumbing bypassed in local mode, it is still the ingress hop; what's optional is Kubernetes/Helm, not Envoy itself. There is also a lightweight standalone HTTP Classification API on port 8080 for health checks and ad-hoc classification calls, separate from the full ExtProc routing path — but the *routing* functionality (the part relevant to AudioGraph) is architecturally coupled to the Envoy hop in every deployment mode documented. **For AudioGraph, "adopt the pattern, not the stack" means: keep the Go/Rust decision-engine-and-plugin-chain idea, and skip Envoy entirely** — AudioGraph's Rust process is already the single HTTP boundary; inserting an Envoy sidecar to talk to itself would be pure incidental complexity with zero payoff at one-user scale.

## E. Semantic caching

Four cache backend types behind a common `CacheConfig` (`BackendType`, `SimilarityThreshold`, `MaxEntries`, `TTLSeconds`, `EvictionPolicy`):
- **In-Memory** — fastest, in-process, optional HNSW index for approximate-nearest-neighbor search; not persistent, bounded by pod memory.
- **Redis** — RediSearch module's vector similarity search with an HNSW index inside Redis; distributed and persistent.
- **Milvus** — dedicated vector database, built for millions of entries at production scale.
- **Hybrid** — in-memory HNSW index for fast O(log n) search, backed by Milvus for persistent full-document storage — used to get fast lookups without losing durability.

HNSW parameters (`M` = bidirectional links per node, `efConstruction` = candidate-list size during graph build) trade search speed against accuracy; the in-memory implementation reuses search-buffer objects via a `sync.Pool` to reduce Go GC pressure.

**Scale read:** semantic caching (return a cached response for a *semantically similar*, not identical, prior query) pays for itself when the same class of question recurs across many users/sessions against a shared backend. For a single-user desktop app, the traffic volume and query-repetition patterns needed to make embedding-similarity cache hits worthwhile are unlikely to exist — a much simpler exact-match or short-TTL cache (if any caching is wanted at all) covers the realistic AudioGraph case (e.g., re-running the same projection prompt against unchanged transcript context) without the HNSW/vector-DB machinery. Not worth porting; flagging only because it's a clean building block if AudioGraph's needs ever grow multi-user.

## F. PII, jailbreak, and safety plugins — the part most relevant to AudioGraph's non-negotiable criterion

- **PII detection**: fine-tuned BERT models detect `PERSON`, `EMAIL_ADDRESS`, `PHONE_NUMBER`, `US_SSN`, `CREDIT_CARD`, `IP_ADDRESS`, etc., as a first-class named signal (`signals.pii`), referenced by `decisions` with `type: "pii"`; `include_history: true` extends detection across a multi-turn conversation, not just the latest message.
- **Jailbreak guard**: two methods — a BERT classifier for fast single-turn detection, and contrastive-embedding comparison for multi-turn "gradual escalation" attacks where no single message looks adversarial in isolation. A separate `response_jailbreak` plugin can scan *model output* (not just input) and either warn, block, or just log — catching content that slipped past input-side detection.
- **The load-bearing finding for AudioGraph's security criterion**: the project's own **`router_replay`** plugin — which exists specifically to capture request/response bodies for debugging/replay — ships with `capture_request_body` / `capture_response_body` as **explicit, named, independently togglable config knobs**, capped by a `max_body_bytes` limit (default 2,048 bytes), and the project's own operational guidance says plainly: *"for sensitive data, it is recommended to disable body capture or replay, and apply appropriate access controls to the replay store."* That is exactly the discipline AudioGraph's security criteria demand — content capture is not implicit or bundled into general logging, it is one named, auditable, off-by-default-in-guidance switch, separable from the metrics/observability path that always fires (routing decisions, latencies, model selected) without ever touching content. **This is the single most directly reusable idea in the whole project for AudioGraph**: model any future Rust-side request/response tracing the same way — a distinctly named, size-capped, independently-disableable content-capture path, structurally separated from the always-on operational-metrics path that must never carry transcript/notes content.

## G. OpenAI-compat handling: streaming, tool-calls, and the Anthropic shim

- **Chat completions and streaming**: implemented against OpenAI SDK types directly (not a hand-rolled reimplementation of the wire format); streaming chunk accumulation lives in a dedicated file (`processor_res_body_streaming.go`) — i.e., streaming is treated as its own subsystem with its own accumulation logic, not folded into the non-streaming path with a boolean flag.
- **Tool/function-call passthrough**: uses OpenAI SDK tool types for conversion, plus a "pre-dispatch tools policy" that can strip prior tool-history messages/blocks from either OpenAI- or Anthropic-shaped requests before forwarding — a deliberate policy hook between "client sent this" and "upstream provider receives this," rather than pure passthrough.
- **Native Anthropic support (`anthropic-shim`)**: a real, separately-shipped container image (confirmed in the v0.3.0 release's Docker image list: `ghcr.io/vllm-project/semantic-router/anthropic-shim:v0.3.0`) implementing native `/v1/messages` ingress via an internal request envelope, with Anthropic-streaming-via-OpenAI-SSE-translation and Anthropic-specific tool-calling support (`pkg/anthropic/client.go` transforms OpenAI-format requests to Anthropic format and back). This is a genuinely useful reference for AudioGraph, which per ADR-0038's own research already tracks Messages/Responses/Chat-Completions divergence per endpoint — the shim's existence as a **separate deployable component from the core Go router**, rather than an inline `if provider == anthropic` branch, is worth noting as a structural pattern: protocol-translation lives in its own boundary, not smeared through the core decision path.
- **No independent verification found of exact tool-call streaming fidelity edge cases** for this specific project (unlike the sibling local-LLM-seam research in this same run, which found and cited specific 2026 GitHub issues against `llama-server`/`llama.cpp` tool-call streaming bugs) — deepwiki's answers describe the *presence* of streaming/tool-call handling code paths but this pass did not fetch and read the underlying Go source directly to verify wire-level correctness claims. **Flagging as UNVERIFIED at the implementation-fidelity level**: the architecture for handling streaming and tool-calls clearly exists and is structurally sound by design, but this research did not independently confirm it is bug-free in production the way the sibling local-LLM-seam research did for llama.cpp/llama-server.

## H. Explicit "does this pay off at small scale" evidence found in the project's own materials

Deepwiki's read of the project's own blog/whitepaper materials (`website/blog/2026-03-10-v0.2-vllm-sr-athena-release.md`, whitepaper LaTeX source) surfaces caveats the project itself states, which read as unusually honest for a project's own marketing:
- "If sub-millisecond latency is absolutely critical and cannot tolerate any additional overhead, even the 1-2ms of keyword routing might be too much."
- "For very simple routing needs where rules are static, easily defined by keywords, and do not require semantic understanding, a basic router or rules table might be preferable due to its simplicity and zero setup cost."
- The fleet simulator's own documented limitation: it does not model batch-level routing or joint request assignment, and explicitly does not model classifier-throughput-induced head-of-line blocking if the classifier itself is slow.

This is corroborating, not just AudioGraph-side, evidence for the verdict above: even the project's own docs concede that a rules table beats a semantic classifier when routing needs are simple and static — which is a reasonable description of AudioGraph's 2-5-provider case.

## Implications for AudioGraph's router

1. **Do not port the ML classification layer.** BERT/LoRA-based semantic classification (10-120ms/request) exists to reduce entropy across *many* candidate models at production multi-tenant volume. At 2-5 hand-configured provider endpoints, the entropy this system reduces is already near zero — a static capability/eligibility table (which ADR-0038 already establishes as the shape) is the correct-scale equivalent, and the project's own documentation independently agrees ("a basic router or rules table might be preferable" when routing needs are simple and static).
2. **Do port the three-layer separation as a code-organization pattern, not a runtime.** Signal extraction (cheap eligibility facts: does this endpoint support the needed context/schema/streaming mode?) → decision engine (deterministic rule evaluation, e.g. Boolean/priority match over the ADR-0038 route table) → plugin chain (pre/post hooks: safety checks, provenance recording, guard rails) is a clean mental model AudioGraph's `route.rs`/`executor.rs` can borrow structurally, with zero ML and zero new dependencies — this is the most transferable idea in the whole project.
3. **Do port the "named, capped, independently-disableable content-capture knob" pattern for any future request/response tracing.** The `router_replay` plugin's design — `capture_request_body`/`capture_response_body` as explicit opt-in switches, separate from always-on operational metrics, with a documented recommendation to disable when data is sensitive — is a directly applicable template for how AudioGraph should gate any diagnostic capture of LLM request/response bodies, keeping it structurally distinct from telemetry that must never carry transcript content. This is the one piece of this research with direct, load-bearing relevance to the security criteria stated for this run.
4. **Do not port Envoy, Kubernetes, Helm, or the vector-DB semantic cache.** All are real, well-built, and correctly scoped to their intended deployment target (k8s-scale, multi-tenant LLM gateways) — none address a problem AudioGraph's Rust backend has. Even the project's own "local" mode still runs Envoy as a Docker Compose component; there is no Envoy-free reference deployment to imitate, so AudioGraph gains nothing by studying Envoy integration specifics further.
5. **The published Rust crate (`candle-semantic-router` on crates.io) is real but not a good direct dependency today.** It is designed for CGO consumption from the project's own Go process (0 independent Rust dependents, Go-oriented FFI ergonomics), and its entire purpose — BERT-based semantic classification — is the piece this research recommends against porting in the first place. If AudioGraph ever needs local embedding/classification inference in Rust, evaluate it on its own technical merits then, not as an artifact of this project's modularity.
6. **The Anthropic-shim's "protocol translation as its own deployable boundary" pattern is worth noting for AudioGraph's own multi-protocol handling** (OpenAI Chat Completions vs. Anthropic Messages vs. future Responses API), independent of whether AudioGraph ever needs a separate process — keeping translation logic in one clearly-owned module rather than branching inline through the core route/execute path is the transferable lesson, not the specific shim implementation.
