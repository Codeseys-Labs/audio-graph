# Agent-runtime embedding options inside Tauri v2 — AudioGraph, 2026-08-23

**Angle:** the four concrete integration shapes for an in-app agent runtime (A: Node/Bun sidecar running a TS agent library; B: agent loop in the webview; C: Rust-native agent loop; D: hybrid Rust-provider/TS-orchestration). Engineering cost, latency, maintenance, security posture, ranked recommendation. All external facts verified against npm / crates.io / GitHub / upstream docs on 2026-08-23. Repo facts carry `file:line`.

---

## Verdict

**Rank: C (Rust-native, extending what exists) > A (Rust-owned Node sidecar, keys never leave Rust) >> D (hybrid with TS orchestration in the webview) >>> B (agent loop in the webview).**

The decisive facts are all in this repo, not in the ecosystem. AudioGraph already ships the four hardest pieces of an agent runtime in Rust: a per-invocation ordered streaming channel (`tauri::ipc::Channel<ChatStreamEvent>`, `src-tauri/src/commands.rs:3385-3388`), cancellation (`stream_registry.cancel`, `src-tauri/src/commands.rs:3464`), a single-skin authorized route table across five providers with all five streaming (`src-tauri/src/llm/route.rs:568`, `src-tauri/src/commands.rs:3077-3086`, ADR-0038), and a generate→validate→repair structured-output loop with versioned prompts and a hand-written validator (`src-tauri/src/projection_llm.rs:540`, `:766`, `:1798`). What is genuinely missing is **tool-calling**: `grep -rn '"tools"\|tool_choice\|ToolCall' src-tauri/src/` returns zero hits, and the route layer deliberately classifies a `tool_calls` finish reason as `TerminalStatus::Failed` with the comment "No request in this repository sends tools" (`src-tauri/src/llm/route.rs:646-649`). So "build" = add a tool schema + a tool-dispatch loop to an existing, tested provider layer — not build a provider layer.

Against that, every non-Rust option must *re-implement the trust boundary*, not just the agent loop. The egress policy gate (`enforce_session_content_policy`, `src-tauri/src/commands.rs:663-706`) and the append-only redacted data-movement ledger (which already reserves a `"tool_calls"` DataClass and a `provider` DestinationBoundary — `src/generated/sessionDataMovement.ts:49`, `:53`) are Rust-side, and ADR-0034 forbids treating uninstrumented producers as a privacy guarantee ("Never turn missing telemetry into a privacy guarantee", `docs/adr/0034-require-exhaustive-evidence-for-negative-data-egress-claims.md:24`). An agent runtime that calls providers from a Node process or the webview is an uninstrumented producer by default; wiring it into the ledger costs roughly what the Rust loop costs, so the sidecar's apparent savings largely evaporate.

Option B is not merely worse, it is blocked by the shipped config: the CSP is `connect-src ipc: http://ipc.localhost` (`src-tauri/tauri.conf.json:23`) — no provider host, no `localhost`, no `127.0.0.1`. A webview agent loop requires widening `connect-src` to every provider host *and* moving keys into the renderer, which contradicts ADR-0019's stated shape ("React configures providers, while Rust owns long-lived provider connections, health checks, model catalog calls, and secret use", `docs/adr/0019-credential-and-config-storage.md:18-20`). Reject.

Option A is *viable and safe* if and only if the sidecar is spawned from Rust and Rust keeps the keys. Verified: `app.shell().sidecar()` called from Rust is **not** ACL-gated — "The scope is no longer validated for Rust calls via `ShellExt::shell()`" — so the webview capability stays at `core:default` + `global-shortcut:default` (`src-tauri/capabilities/default.json:8-11`) and never receives `shell:allow-execute`; the plugin also offers `Command::env_clear()` and `CommandChild::write()` so the child can run with a scrubbed environment and receive secrets over stdin instead of env or argv [deepwiki: tauri-apps/plugins-workspace]. The cost is 73–90 MB of embedded JS runtime per platform per sidecar, a second crash/telemetry surface, and a second npm supply chain inside the sanctioned LLM boundary.

Forward-compat with local Rust inference favours C decisively and is *neutral-to-negative* for A: AudioGraph already links two in-process Rust inference engines (`llama-cpp-2`, `mistralrs`; `src-tauri/Cargo.toml:333,342`) behind the default `local-ml` feature. A Rust agent loop calls them as function calls. A Node sidecar can only reach them back across the same IPC it came from, or via a localhost HTTP shim — i.e. the sidecar would need AudioGraph to expose an OpenAI-compatible local server it does not have today.

## Option A — Node/Bun sidecar running a TS agent library

### Mechanics (verified)

`bundle.externalBin: ["binaries/my-sidecar"]` + a per-target-triple filename (`my-sidecar-x86_64-unknown-linux-gnu`, `-aarch64-apple-darwin`, `.exe` on Windows). Tauri appends the triple when resolving at build time and strips it in the bundle. Rust side: `use tauri_plugin_shell::ShellExt; app.shell().sidecar("name")?.spawn()? -> (Receiver<CommandEvent>, CommandChild)`. [v2.tauri.app/develop/sidecar/, v2.tauri.app/learn/sidecar-nodejs/]

**ACL:** the `shell:allow-execute` permission with `{"sidecar": true}` is required only for the JS-side `Command.sidecar()` API. Rust-side `ShellExt::shell()` calls are *not* scope-validated ("The scope is no longer validated for Rust calls via `ShellExt::shell()`") [deepwiki: tauri-apps/plugins-workspace]. **Design consequence: spawn from Rust and the webview capability never grows.** This is the single most important mechanic for AudioGraph, because it means adopting a sidecar does not require handing the renderer a process-spawn primitive.

**Lifecycle:** `tauri-plugin-shell` registers a `RunEvent::Exit` handler that iterates `shell.children` and `kill()`s each [deepwiki: plugins-workspace]. Store the `CommandChild` in state to kill on session end rather than app end. Field caveat from a shipping app: "`spawn()` succeeding does not mean the process is actually working" — add a readiness handshake and a health check [dev.to/chenxxpro, 2026-07-05]. deepseek-harness-desktop does exactly this: "Rust starts the sidecar, waits for its readiness signal, and terminates it when the app exits."

Node SEA is `Stability: 1.1 - Active development` as of Node v26.7.0 docs, though `--build-sea` became a first-class CLI flag in v25.5.0 (before that: `--experimental-sea-config` + `postject`). macOS requires re-signing after injection (`codesign --remove-signature` → postject → `codesign --sign`). Vercel `pkg` — still what the official Tauri Node-sidecar guide uses — is the legacy path; prefer SEA or `bun build --compile`.

**Bun vs Node, the real deciders:**
- Bun **cross-compiles** (`--target=bun-linux-x64` / `Bun.build({compile: 'linux-x64'})`), Node SEA and `deno compile` effectively do not. For AudioGraph's 5-target bundle matrix (`app, dmg, nsis, appimage, deb`) that is a meaningful CI simplification.
- Bun `--compile` **breaks native modules**. Bitterbot chose Node SEA explicitly over `bun --compile` because of `better-sqlite3`. If the sidecar needs any N-API addon, Bun is out.
- Bun does not support Node SEA-style postject; Node cannot produce a single file from a directory with native deps either.
- `--bytecode` (Bun) buys 1.5–4× faster cold start at 2–8× larger embedded code — relevant only if you spawn per-session rather than per-app.

**IPC choice — stdio JSONL vs localhost HTTP/WS.** For AudioGraph, stdio is strictly better and localhost HTTP is actively costly:
- The shipped CSP (`src-tauri/tauri.conf.json:23`) has no `localhost` in `connect-src`. A localhost sidecar reachable *from the webview* requires widening it, and CSP treats `localhost` and `127.0.0.1` as **distinct origins** — a real shipped bug: librecode commit `d8c9136` had `connect-src http://localhost:*` while the sidecar bound `127.0.0.1`, producing "Could not reach Local Server" while the server was healthy. Correct form needs `http://localhost:* http://127.0.0.1:* http://[::1]:*`.
- Tauri v2 **stops auto-injecting `ipc.localhost`** once you supply an explicit CSP; origa PR #181 is a shipped release regression where every IPC call broke because `connect-src` lacked `ipc: http://ipc.localhost`. AudioGraph's CSP already includes both tokens — do not regress that when editing.
- A loopback listener is a *network* surface: any local process can connect unless you add a per-launch bearer token. stdio has no such surface, and pipes are the safest secret channel (see below).
- Real precedent both ways: **stdio JSONL/JSON-RPC** — Tendril (Node SEA + JSON-RPC on stdio), Naresh084/cowork (Node sidecar, JSON-RPC over stdio, Rust "Sidecar Manager"), zosmaai/zosma-cowork (stdin/stdout JSON lines). **Loopback HTTP** — deepseek-harness-desktop (binds `127.0.0.1` on an OS-assigned port, and notably still keeps "process control … in Rust" with "the loopback UI receives no Tauri shell capability").

**Key passing — the trust-boundary question.** Ranked worst→best, with the mechanism verified:
1. **argv** — never. `/proc/<pid>/cmdline` is world-readable; `ps` shows arguments to every user on most Unices.
2. **inherited environment** — the default if you do nothing. A Tauri sidecar "inherits the app's environment" (Tendril). `/proc/<pid>/environ` is mode `0400`, readable by the same UID — i.e. by *any* code running as the user, including the sidecar's own npm dependency tree and any later-spawned tool subprocess. This is the acute risk with pi specifically: `pi-coding-agent`'s default tool set is `["read","bash","edit","write"]` (pi.dev/docs/latest/sdk), so an inherited key is inherited by every `bash`-spawned grandchild. Also: "many programs happily dump their environment to stderr under certain (error) conditions, or log it via syslog for debugging" [netmeister.org/blog/passing-passwords].
3. **explicit scoped env** — `Command::env_clear()` then `.env(K,V)` for exactly the provider slot needed [deepwiki: plugins-workspace]. Removes inheritance-in and limits blast radius; still readable via `/proc/self/environ` inside the sidecar's own process tree.
4. **stdin / pipe** — best. `CommandChild::write(&[u8])` exists [deepwiki: plugins-workspace]. "pipes are safe, environment variables are usually safe if the subprocess doesn't spawn other subprocesses, command line arguments should not be treated as confidential" [security.stackexchange.com/q/20282]. Send the key as the first framed message after a readiness handshake, hold it only in the sidecar's heap, never write it to `auth.json`.
5. **Best of all: don't send it.** Keep provider calls in Rust and expose a `provider.chat` RPC *to* the sidecar over the same stdio pipe. The sidecar then orchestrates and the key never crosses. This collapses A into a process-isolated variant of D-done-right, and is the only A-shape that leaves the sanctioned boundary where ADR-0019 put it.

**pi specifically (verified 2026-08-23).** The package scope has **moved**: `badlogic/pi-mono` now redirects to **`earendil-works/pi`** (95,855 stars, MIT, pushed 2026-08-23), and the live npm scope is **`@earendil-works/*` at 0.84.2 (published 2026-08-14)**. The `@mariozechner/*` packages are frozen: `pi-ai` / `pi-agent-core` / `pi-coding-agent` last at 0.73.1 (2026-05-07), and `@mariozechner/pi-agent` (the package literally named "pi-agent") last shipped **0.9.0 on 2025-11-21** — 9 months stale. Anything citing `@mariozechner/pi-agent` or `pi-agent` is citing a dead name. There is no `pi-agent`, `@pi-dev/agent`, or `@pi/agent` on npm (all 404).
- `engines: {"node": ">=22.19.0"}` on every current `@earendil-works/pi-*` package. A `legacy-node20` dist-tag pinned at 0.74.2 marks the Node-floor bump — a breaking runtime requirement mid-0.x.
- `@earendil-works/pi-coding-agent` 0.84.2: 13.7 MB unpacked, 972 files, 21 direct deps. `@earendil-works/pi-ai` 0.84.2: 4.0 MB, 742 files, deps = `openai@6.40.0`, `@anthropic-ai/sdk@0.91.1`, `@google/genai@1.52.0`, `@aws-sdk/client-bedrock-runtime@3.1048.0`, `@smithy/node-http-handler`, `http-proxy-agent`, `https-proxy-agent`, `@opentelemetry/api`. `pi-agent-core` 0.84.2: 1.9 MB, deps = `typebox`, `pi-ai`, `pi-telemetry`.
- **Version churn:** 41 published versions and 11 minor lines (0.74 → 0.84) in the 3.5 months from 2026-05-07 to 2026-08-14 — roughly a release every 2.5 days, a minor every 10 days, all pre-1.0.
- **RPC mode is real and specified:** strict JSONL over stdin/stdout; commands `{"id":"req-1","type":"prompt","message":"…"}`; replies `{"type":"response","success":bool,data?,error?}`; async `AgentSessionEvent` lines interleaved. **Explicit warning: "Generic line readers that treat Unicode separators as newlines, such as Node's `readline`, are not protocol-compliant"** — split on `\n` only, strip a trailing `\r`. [deepwiki: earendil-works/pi]
- Key resolution priority: `setRuntimeApiKey()` (not persisted to disk) → `~/.pi/agent/auth.json` → env vars (`ANTHROPIC_API_KEY`, …). `ModelRuntime.create({authPath, modelsPath})` lets you relocate both. `InMemoryCredentialStore` exists. So a Rust-owned, stdin-fed, never-persisted key is achievable — via `setRuntimeApiKey` + `SessionManager.inMemory()` + `SettingsManager.inMemory()`.
- **Reference implementation exists**: `zosmaai/zosma-cowork` — Tauri v2 + React 19 + "Node.js sidecar using `@earendil-works/pi-coding-agent`", "thin Tauri relay … a minimal IPC bridge", stdin/stdout JSON lines with commands `init | get_models | prompt | abort | set_model | save_auth | reload`, and a bundled `src-tauri/binaries/node` produced only by the production build. That is the closest thing to a working blueprint for A-with-pi. (deepwiki has not indexed it, so its key-handling internals are **UNVERIFIED** — the `save_auth` command name suggests keys are persisted by the sidecar, which would be the wrong shape for AudioGraph.)
- pi is a *terminal coding harness*. `pi-tui` (2.5 MB, differential terminal rendering) is a hard dep of `pi-coding-agent`; the default tools are file/bash tools. Adopting it for a meeting-notes agent means importing a coding-agent's tool surface, extension loader (`jiti` runtime TS eval, `DefaultResourceLoader` auto-discovering from `~/.pi/agent/extensions/`), and session-file layout, then disabling most of it. `createAgentSession({tools: [...], customTools: [...]})` supports an allowlist, and `ResourceLoader` overrides can null out skills/prompts/AGENTS.md discovery — but the *default* is discovery-on, which for a privacy-sensitive app is a fail-open default that must be explicitly closed and regression-tested.

**Other TS agent libraries, verified:** `ai` (Vercel AI SDK) 7.0.77 (2026-08-22), `@openai/agents` 0.17.0 (2026-08-19), `@anthropic-ai/claude-agent-sdk` 0.3.241 (2026-08-23). All far more actively released than pi's ecosystem is *stable*; all Node-shaped for tool execution.

**Cost (rough order).** Sidecar plumbing (spawn/kill/readiness/health, JSONL framing with the `\n`-only split, crash-restart, stdin key handoff, per-OS build + signing + CI matrix, 3 platform binaries): 2–4 engineer-weeks, most of it build/release rather than logic. Ledger + policy-gate integration so the sidecar's provider calls are not an uninstrumented producer (ADR-0034): 1–2 weeks *if* keys stay in Rust (the sidecar asks Rust to call the provider, so the existing gate fires unchanged); 3+ weeks if the sidecar calls providers itself (you must forward every `provider_call_*` event and re-derive `data_classes` across a process boundary). Agent behaviour itself: near-zero, you get pi's loop. **Total 3–6 weeks, plus permanent ownership of a second supply chain and a second runtime's CVE cadence.**

**Latency.** Immaterial. Per-line stdio framing on small JSON messages is tens of microseconds; Tauri IPC control-message roundtrip is ~300 µs end-to-end (measured, and *clamped by WebKit's 1 ms `performance.now()` resolution*, so the true figure is smaller) against a Rust-dispatch floor of 722 ns for a 25-byte struct [userFRM/tauri-conduit BENCHMARKS.md, criterion on i7-10700KF]. Provider TTFT p50 is 120 ms (Cerebras) to 1.2 s (Anthropic direct) to 3.8 s (reasoning models), p95 up to 2.8–9.2 s [verticalapi.com/benchmark, 2026-05-04; artificialanalysis.ai measures GPT-5.5 Instant at 1.08 s median first chunk / 14.5 s to first *answer* token]. Two extra process hops add ~0.1–0.6 ms per event — **≤0.5 % of the fastest provider's TTFT and ~1–3 % of a single inter-token gap.** Agent-loop latency is set by provider TTFT × number of tool round-trips, full stop. The only place native-vs-JS matters is *bulk payload* movement, and that is a webview-IPC property, not a language property: returning `Vec<u8>` from a Tauri command arrives in JS as a JSON number array — 22.5 MB for a 6.3 MB image, worse than base64, 1811 ms frame stall [mechanicalrock.io "It's physics, not a bug", Apple M2 Max; tauri-ipc-bench]. Send transcript *text* and token deltas over `ipc::Channel`, never blobs, in any option.

**Security posture.** Changes the trust boundary in three ways even at its best: (1) a second process inside the sanctioned LLM boundary whose npm tree can read `/proc/self/environ` and, if it calls providers, sees plaintext transcript; (2) a second crash/telemetry surface — AudioGraph's `sentry` is compiled unconditionally in the Rust process (`src-tauri/Cargo.toml:406-415`), and pi ships `@opentelemetry/api` + `pi-telemetry`, so *two* diagnostic exporters must independently be proven not to carry transcript text; (3) `jiti`-based runtime TypeScript extension loading with filesystem auto-discovery is arbitrary local code execution inside that boundary by design. Also: `pi-coding-agent` bundles `@silvia-odwyer/photon-node` (a native/WASM image lib) — one more reason `bun --compile` may not work and one more native surface to sign.

## Option B — agent loop in the webview

**Verdict: reject. Blocked by config, by provider CORS, and by ADR-0019.**

1. **CSP.** `src-tauri/tauri.conf.json:23` is `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src ipc: http://ipc.localhost`. No provider host is reachable from the renderer. Enabling B means enumerating `https://api.openai.com https://api.anthropic.com https://openrouter.ai https://generativelanguage.googleapis.com https://bedrock-runtime.*.amazonaws.com …` in `connect-src` — a permanent, auditable widening of the renderer's egress, for a webview that already renders live transcript text.
2. **Key exposure.** Keys in the renderer are readable by any injected script and by devtools. AudioGraph deliberately keeps the inspector out of release builds precisely because "the renderer … aggregates live transcript text (privacy/security leak)" (`src-tauri/Cargo.toml:130-149`). Putting keys there inverts that reasoning. The credential layer's whole shape is presence-only exposure: a custom `Debug` that renders every secret through `redacted_presence` (`src-tauri/src/credentials/mod.rs:257-314`, `:453`), and ADR-0019:15-16 "Settings can load credential presence and provider readiness without sending stored plaintext keys to React."
3. **CORS.** OpenAI's own guidance: "Exposing your OpenAI API key in client-side environments like browsers or mobile apps allows malicious users to take that key and make requests on your behalf… Requests should always be routed through your own backend server" [help.openai.com/en/articles/5112595]. OpenAI's CORS behaviour on `api.openai.com` has changed under developers mid-flight ("Has the CORS policy changed (responses API)?" — "Oh, it is a pity when you just release an app, and it stops working"). Anthropic requires an opt-in `anthropic-dangerous-direct-browser-access: true` header plus `dangerouslyAllowBrowser: true`. Gemini's OpenAI-compat endpoint rejects the OpenAI SDK's `x-stainless-*` headers on preflight, requiring callers to null them out one by one [discuss.ai.google.dev/t/58619]. Each of these is a provider-controlled behaviour that can break your app without a release on your side — an unacceptable dependency for a shipped desktop product with five providers.
4. **Bedrock is not browser-reachable at all.** pi's own browser story states Bedrock (`bedrock-converse-stream`) is unsupported in the browser and OAuth flows are Node-only [deepwiki: earendil-works/pi]. AudioGraph ships `aws-sdk-bedrockruntime` as an always-compiled provider (`src-tauri/Cargo.toml:386-390`) and it is one of the five streaming-capable chat providers (`src-tauri/src/commands.rs:3084`). B would silently drop a shipped provider.
5. **The library ecosystem confirms it.** pi *does* maintain browser-safe entry points (`scripts/browser-smoke-entry.ts` + `scripts/check-browser-smoke.mjs` assert no accidental Node-only imports in `pi-ai`/`pi-agent-core`), which is the strongest counter-evidence available — but the same source says a **CORS proxy is recommended for production**, and there was a dedicated package for exactly that: `@mariozechner/pi-proxy` — "CORS and authentication proxy for pi-ai", 14 KB, `hono` + `@hono/node-server`, last published **2025-12-26**, and **it does not exist under `@earendil-works/`** (404). So the browser path's official escape hatch is an unported, 8-month-stale shim. `@earendil-works/pi-web-ui` exists but is pinned at **0.75.3 (2026-05-18)** while the Node packages are at 0.84.2 (2026-08-14) — the browser-facing package lags the runtime by three months and nine minor lines. `pi-agent-core` itself needs Node (`child_process`, stdio).

The *only* defensible fragment of B is UI-side conversation state — which is exactly what D and the existing `ChatSidebar.tsx` already do without keys.

**`rig-core` 0.42 capabilities** [deepwiki: 0xPlaygrounds/rig]: `AgentRunner` is now the *sole* execution path (raw `Completion`/`StreamingCompletion` traits removed) and drives multi-turn tool loops with automatic + concurrent tool execution; `MultiTurnStreamItem` interleaves `StreamAssistantItem` (text/tool deltas, reasoning, usage) with `ToolExecutionCommitted`; `StreamedTurnAssembler` is a sans-IO accumulator; strict-tool constrained decoding via `with_strict_tools()`; `OutputMode` composes structured output with tools. Providers include OpenAI, Anthropic, Gemini, Groq, OpenRouter, Ollama, Azure, Together, DeepSeek, Llama.cpp, and `rig-bedrock` 0.42.0 exists as a companion crate (96,220 recent downloads) — so AudioGraph's five routes are all covered nominally.

**But the churn is the story.** `rig-core` published **27 versions across 24 semver-breaking 0.x minor lines (0.19 → 0.42) in the 12 months to 2026-08-23** — a breaking release roughly every 2 weeks. 0.42 alone breaks `OneOrMany<T>` → `Vec<T>` in message content *and persisted JSON*, unifies the tool-execution API, makes `AgentRunner` mandatory, changes `max_turns` semantics to bound total model calls, migrates providers onto `GenericCompletionModel<Ext>`, and renames streaming telemetry spans. For a repo whose LLM layer is governed by an ADR (0038) and whose route identity is asserted in tests, adopting rig means signing up for a quarterly migration of the *most* security-sensitive module.

**Dependency and logging fit.** `rig-core` 0.42 has 26 required normal deps: `as-any, async-stream, base64, bytes, eventsource-stream, fastrand, futures, futures-timer, glob, http, indexmap, mime, mime_guess, ordered-float, pin-project-lite, reqwest, schemars, serde, serde_json, sha2, thiserror, tokio, tracing, tracing-futures, url`. Most are already in AudioGraph's tree (`reqwest`, `schemars`, `serde`, `serde_json`, `sha2`, `thiserror`, `tokio`, `bytes`, `futures-util`, `url`, `base64`). The mismatch is **logging**: AudioGraph uses `log` + `env_logger` (`src-tauri/Cargo.toml:222-223`); rig uses `tracing` exclusively. A `tracing` subscriber must be wired, and it becomes a second log sink outside the existing sanitization discipline.

**Content-in-telemetry, verified for both leaders — and both default to OFF:**
- `rig-core`: fields `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`, `gen_ai.prompt`, `gen_ai.completion` are declared `Empty` in the canonical span macro and populated only when `CompletionRequest.record_telemetry_content == true`. **Default `false`**; togglable via `CompletionRequestBuilder::record_content_telemetry(bool)` / `PromptRequest::record_content_telemetry(bool)` [deepwiki: 0xPlaygrounds/rig]. A code-level assertion that this is never set true is cheap and testable.
- `genai`: same attributes, opt-in via **environment variable `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true`** [deepwiki: jeremychone/rust-genai]. **This is a worse control than rig's**: an *ambient* env var can flip transcript text into telemetry without a code change, on a user's machine, outside AudioGraph's review. If genai is chosen, the process must clear that variable at startup and assert it.

**`genai` capabilities** [deepwiki: jeremychone/rust-genai]: tool calling since 0.6.0 (`Tool`/`ToolCall`/`ToolResponse`), `ChatRequest::append_tool_use_from_stream_end` for multi-turn history threading, `ChatStreamEvent::ToolCallChunk(ToolChunk)` streaming deltas (Anthropic emits one at `content_block_start` then one per `content_block_delta`), `ChatResponseFormat::JsonMode | JsonSpec(name, schema)` with per-provider JSON-Schema normalization for Gemini/Vertex. **No agent-loop abstraction** — you own the loop. For AudioGraph that is arguably a *feature*: the loop is the part you want to own (gating, ledger writes, cancellation, budget clamping already exist), and the part you want borrowed is provider-shape normalization — which is precisely what `src-tauri/src/llm/` already is.

### What "build" actually means here

The honest framing: AudioGraph's `llm/` + `projection_llm.rs` is already a 26.5k-LOC provider-routing + structured-output + validate/repair layer with an ADR, a route table, budget clamping (`RouteDescriptor::clamp_completion_budget`, `src-tauri/src/llm/route.rs:177`), terminal-status/retry classification, served-model identity folding, and SSE decoding (`llm/sse.rs`, `llm/stream_contract.rs`). "Build a Rust agent loop" = add, on top of that:

1. Tool schema types + `tools` / `tool_choice` on the request bodies, per skin (OpenAI-compatible covers Api/OpenRouter/vLLM; Bedrock Converse has its own `toolConfig` shape; llama.cpp/mistral.rs need grammar-constrained tool emission or a JSON-schema fallback). Reuse `RequestOutputForm` / `ConstrainedDecodingGrade` (`src-tauri/src/llm/route.rs:96`, `:781`) rather than inventing a parallel capability axis.
2. Reclassify `tool_calls` from `TerminalStatus::Failed` to a first-class continuation (`src-tauri/src/llm/route.rs:646-649`) — a deliberate, reviewable one-line inversion of a currently-documented invariant.
3. A bounded tool-dispatch loop: `max_turns`, per-turn token budget, `CancellationToken` (already present, `tokio-util` `rt` feature, `src-tauri/Cargo.toml:213`), tool-result truncation.
4. Tool implementations over existing state: transcript query, notes read, graph query. All are in-process reads of `AppState`; no new egress.
5. Stream `MultiTurn`-style events into the existing `ipc::Channel<ChatStreamEvent>` shape by extending the enum — the frontend already consumes it.
6. One `provider_call_*` ledger row per model call with `data_classes` including the reserved `"tool_calls"` (`src/generated/sessionDataMovement.ts:49`), and `enforce_session_content_policy` invoked once per turn with the agent's action id.

**Cost (rough order):** tool plumbing per skin 1.5–3 weeks; loop + budgets + cancellation 1 week; 3 tools 1 week; ledger/policy 0.5 week (the hooks exist); tests to the repo's standard (this codebase averages ~50 % test lines in its LLM modules) 1–2 weeks. **Total 5–7 engineer-weeks** — more than A's headline 3–6, but it *includes* the trust-boundary work that A's estimate only includes in its best case, and it leaves zero new runtimes, zero new supply chains, and zero new bundle weight.

**Latency:** best possible, and the margin is irrelevant (see A). One fewer process hop saves ~0.1–0.3 ms per streamed event against 10–50 ms inter-token gaps.

**Maintenance:** lowest if you extend in-house or use `genai` as a thin normalizer; **high** if you adopt `rig-core` (24 breaking minors/year touching the security-critical module). Recommendation within C: **extend `llm/` in-house, borrow shapes from `genai`, do not adopt `rig-core` as the spine.** Consider `rmcp` 3.1.4 later if external MCP tools become a requirement — it is the official SDK, at 3.x, with 11 M recent downloads.

**Security posture:** unchanged boundary. Keys never leave the process that already holds them. Transcript never crosses a new boundary. The two gates (`enforce_session_content_policy`, ledger append) fire from the same call sites they already fire from. Only new obligation: assert `record_telemetry_content == false` (rig) / clear `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` (genai), and keep `tracing` out of the log sink or bridge it into the existing sanitized `log` pipeline.

**Forward-compat with local Rust inference:** strictly best. `llama-cpp-2` and `mistralrs` are already in-process (`src-tauri/Cargo.toml:333,342`), and `MistralRsEngine` already does JSON-Schema-constrained structured generation. A Rust tool loop reaches a future local model by function call; a `RouteDescriptor` with `BlockingBackend`/`ConstrainedDecodingGrade` already models the capability differences between a cloud endpoint and a local engine. When a rust-native vLLM-class server lands, it appears as one more route in a table that already has five.

## Option D — hybrid: Rust owns provider calls + keys, TS owns conversation orchestration in the webview

This is, precisely, **AudioGraph's current shipped architecture** (`start_streaming_chat` + `ipc::Channel` + `ChatSidebar.tsx` + `get_chat_history`), so "adopt D" is a null change for chat and a real question only for the *agent loop*.

Two sub-variants, and they are not close:

**D1 — TS owns turn presentation and user-facing conversation state; Rust owns the agent loop including tool dispatch.** Cost above C: ~0. Security: unchanged. This is what to build. It is C plus the frontend you already have.

**D2 — TS owns the *agent loop* (decide-tool → request-tool → observe → continue) in the webview, calling Rust per model turn and per tool.** This is where it breaks:
- Every loop iteration becomes ≥2 webview↔Rust roundtrips. Latency is still fine (~0.3 ms each), but *correctness* isn't: the loop's budget, turn cap, cancellation, and ledger accounting now live in the least-trusted, most-injectable tier. The policy gate is per-command (`enforce_session_content_policy` is called inside each command, `src-tauri/src/commands.rs:663`), so a renderer-driven loop can be induced to make N provider calls where policy assumed one, and the ledger's `MovementBasis`/turn accounting is authored by the renderer.
- ADR-0034's logic bites: the ledger's completeness argument depends on the producer set being known and exhaustive. A loop whose iteration count is renderer-decided is not an exhaustive producer set in any auditable sense.
- Tool execution against transcript/notes/graph must be Rust-side anyway (that data lives in `AppState`), so D2 buys only "the `while` loop is in TypeScript" while paying full trust-boundary cost.
- The renderer cannot use any TS agent library for the loop without either (a) importing a Node-shaped one that won't bundle, or (b) using pi's browser-safe subset — which drops Bedrock and needs the unported CORS proxy for direct calls it wouldn't be making anyway.

**Verdict on D:** adopt D1 (which is C). Reject D2.

## Implications for the 83cc runtime decision

1. **The gap is tool-calling, not provider access.** `grep` proves zero tool-calling exists (`src-tauri/src/llm/route.rs:646-649` documents this as intentional), while five streaming providers, structured outputs, prompt versioning, a validate/repair loop, cancellation, and an ordered per-invocation event channel all ship today. Scope 83cc as "add a bounded tool loop to `llm/`", not "choose an agent framework". Any option that replaces the provider layer discards 26.5k tested LOC and one accepted ADR (0038).

2. **Latency cannot decide this fork; stop weighing it.** Provider TTFT p50 spans 120 ms → 3.8 s and p95 reaches 9.2 s; every IPC hop under consideration costs 0.1–0.6 ms. Native code buys nothing measurable in an I/O-bound agent loop. The one real performance rule is transport-shaped, not language-shaped: never move blobs through `invoke` (a 6.3 MB image arrives as a 22.5 MB JSON number array with 1811 ms of frame stall). Stream transcript text and token deltas over `ipc::Channel`, which `start_streaming_chat` already does.

3. **A sidecar changes the trust boundary in exactly one avoidable way and two unavoidable ways.** Avoidable: keys crossing. Because Rust-side `app.shell().sidecar()` is not ACL-gated, and because `Command::env_clear()` + `CommandChild::write()` exist, the sidecar can run with a scrubbed environment and either receive the key on stdin (never persisted, `setRuntimeApiKey` + `SessionManager.inMemory()`) or — better — never receive it and call back into Rust for each model turn. Unavoidable: (i) a second npm/Node CVE surface *inside* the sanctioned LLM boundary, whose dependency tree can read `/proc/self/environ` and, in pi's case, whose default tool set includes `bash` (so any inherited secret is inherited by every grandchild); (ii) a second telemetry/crash exporter (`@opentelemetry/api` + `pi-telemetry` alongside the unconditionally-compiled Rust `sentry`) that must independently be proven transcript-free. If the maintainer adopts A, these three must be explicit acceptance criteria, not footnotes.

4. **The webview is not a candidate.** The shipped CSP (`src-tauri/tauri.conf.json:23`) admits only `ipc:` and `http://ipc.localhost`; the credential layer exposes presence only (`src-tauri/src/credentials/mod.rs:453`); ADR-0019:18-20 assigns "secret use" to Rust; devtools are deliberately excluded from release builds *because* the renderer aggregates transcript text (`src-tauri/Cargo.toml:130-149`). Add to that: Bedrock is not browser-callable, OpenAI's CORS behaviour has broken shipped apps mid-flight, Gemini's OpenAI-compat endpoint rejects the OpenAI SDK's own default headers on preflight, and pi's browser escape hatch (`pi-proxy`) was never ported to the current `@earendil-works` scope. B is closed.

5. **`pi-agent` as a name is dead; verify the scope before any ticket cites it.** `@mariozechner/pi-agent` last shipped 0.9.0 on **2025-11-21**. The live artifacts are `@earendil-works/pi-*` **0.84.2 (2026-08-14)** from `earendil-works/pi` (95,855★, MIT, pushed today), requiring **Node ≥22.19.0**. The RPC contract is real and well-specified (JSONL, `prompt`/`response`/event lines, split on `\n` only — Node's `readline` is explicitly non-compliant), a working Tauri+pi sidecar reference exists (`zosmaai/zosma-cowork`), and key injection can be non-persistent. The costs are 11 pre-1.0 minor lines in 3.5 months, a mid-stream Node-floor bump, 13.7 MB / 972 files of coding-agent surface (TUI, file/bash tools, `jiti` runtime-TS extension auto-discovery from `~/.pi/agent/extensions/`) that must be affirmatively disabled, and a browser-side package (`pi-web-ui` 0.75.3) three months behind the runtime. Adopting pi means adopting a *coding harness* and subtracting.

6. **Bundle arithmetic matters more for AudioGraph than for a typical app, because of the cloud build.** The default `local-ml` profile already links whisper.cpp + llama.cpp + mistral.rs, so +75 MB is noise. But `--no-default-features --features cloud` exists specifically as "a fast, light, cloud-only build" (`src-tauri/Cargo.toml:52-56`), and that is exactly the profile a JS-runtime sidecar would inflate most — measured floors: Bun 73.32 MB (linux-x64) / 75.92 MB (windows-x64), Node SEA ~90 MB, Deno ~90–120 MB. If a sidecar is adopted, decide whether the cloud build ships it, and note that `bun --compile` cross-compiles (a real CI-matrix win) but breaks on native N-API modules — the documented reason Bitterbot chose Node SEA, and a live risk given `pi-coding-agent`'s `@silvia-odwyer/photon-node`.

7. **Do not adopt `rig-core` as the spine, even though it is the clear Rust leader.** 8,373★, MIT, pushed today, 1.38 M recent downloads, and 0.42 genuinely has what an agent needs (`AgentRunner` multi-turn tool loop, concurrent tool execution, `MultiTurnStreamItem` streaming with tool deltas, strict-tool constrained decoding, `rig-bedrock` companion). But it shipped **24 semver-breaking 0.x minor lines in 12 months**, and 0.42 alone breaks persisted-JSON message shape (`OneOrMany` → `Vec`), removes the raw completion traits, and changes `max_turns` semantics. Absorbing that cadence in the module governed by ADR-0038 is the wrong trade. Borrow *shapes* from `genai` 0.6.5 (tool types, `ToolCallChunk` streaming, `JsonSpec`, per-provider schema normalization) and keep the loop in-house — with the caveat that genai's content-capture switch is an **environment variable** (`OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`), which must be cleared and asserted at startup rather than trusted. Avoid `swiftide` (last release 2025-11-15) and `allms` (640 recent downloads).

8. **Concrete recommendation.** Build the loop in Rust inside `llm/` (option C / D1). Sequence: (a) invert `tool_calls` → continuation in `route.rs` behind the new agent path only; (b) tool schema on the OpenAI-compatible skin first (Api + OpenRouter cover most users), Bedrock `toolConfig` second, local engines via `MistralRsEngine`'s existing schema-constrained generation third; (c) bounded loop with `max_turns` + existing `CancellationToken` + `clamp_completion_budget`; (d) three read-only tools over `AppState` (transcript, notes, graph); (e) one `provider_call_*` ledger row per model call carrying the reserved `"tool_calls"` data class, and `enforce_session_content_policy` per turn; (f) extend `ChatStreamEvent` rather than adding a second channel; (g) reuse `agent-status` / `agent-proposal` (`src-tauri/src/events.rs:77`, `:81`) and the existing `AgentProposalsPanel.tsx` for the gated auto-answer flow. Keep option A on the shelf as the escape hatch for one specific future need — **sandboxed third-party tool execution** — where a separate process with its own crash boundary is genuinely the right tool, and where the sidecar should receive no provider key at all.

9. **Housekeeping, verified not-a-problem-today:** `src-tauri/Cargo.toml:151` pins `tauri = "2.11.0"` — the top of GHSA-7gmj-67g7-phm9's vulnerable range (`>=2.0, <=2.11.0`, patched `>=2.11.1`). **The committed `src-tauri/Cargo.lock` resolves `tauri 2.11.5`, so shipped builds are patched.** The only residual is that the caret *floor* names a vulnerable release, so a future `cargo update --precise`/downgrade or a fresh resolve pinned low could reintroduce it; raising the manifest floor to `"2.11.1"` closes that with zero tree change. Not a blocker, and not an 83cc dependency — noted because it sits adjacent to any change that widens what the webview can reach.
