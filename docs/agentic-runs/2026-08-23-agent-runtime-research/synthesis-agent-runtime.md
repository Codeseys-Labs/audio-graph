# Agent runtime for epic 83cc: adopt pi vs build Rust-native — synthesis memo

**Run:** 2026-08-23 agent-runtime research. Synthesizes `pi-ecosystem-audit.md`, `audiograph-agent-seams.md`, `tauri-embedding-options.md`, `local-llm-seam.md`, with supporting evidence from the sibling router artifacts `nvidia-switchyard.md` and `vllm-semantic-router.md`. All repo refs are to this checkout; all package/version facts were registry-verified 2026-08-23 by the underlying artifacts.

## 1. Executive verdict

**Build the agent loop in Rust, extending the existing `src-tauri/src/llm/` + `projection_llm.rs` substrate, and port `@earendil-works/pi-agent-core`'s `Agent` API semantics as the design spec rather than the dependency.** Three deciding reasons, each independently sufficient. (a) *The gap is tool-calling, not an agent runtime*: `grep` for `"tools"`/`tool_choice`/`ToolCall` in `src-tauri/src/` returns zero hits and `route.rs:646-649` deliberately classifies `tool_calls` as `TerminalStatus::Failed` — while everything else an agent loop needs already ships in 26,502 LOC of ADR-governed Rust: per-invocation ordered streaming (`tauri::ipc::Channel<ChatStreamEvent>`, `commands.rs:3385-3452`), cancellation (`commands.rs:3460-3486`), five streaming providers behind ADR-0038's named-route table, `json_schema`-strict structured outputs with a validate/repair loop (`projection_llm.rs:540,766,1798`), the `enforce_session_content_policy` egress gate (`commands.rs:663-706`), and a data-movement ledger that already reserves a `"tool_calls"` DataClass (`src/generated/sessionDataMovement.ts:49`) (`tauri-embedding-options.md`). Adopting a TS runtime imports a second copy of slots Rust already owns. (b) *Every pi shape either changes the trust boundary or relocates the ADR-0038 gate*: a Node sidecar or webview provider calls put keys and transcript in a new process/tier (SECURITY FACTS violation); even the key-safe embed — `pi-agent-core` in the webview behind a Rust-delegated `streamFn` — moves system-prompt authorship, context assembly, and tool dispatch out of the code that stamps provenance "from trusted code" (`route.rs:1-25`), forcing Rust to validate an untrusted assembly instead of producing a trusted one (`pi-ecosystem-audit.md` §5). In Rust, the gate stays where it is. (c) *Upstream clock*: 43 of 267 pi releases carry breaking changes landing in minor bumps; 0.83.0 broke TypeBox tool-parameter schemas — exactly where AudioGraph's domain tools would live — and the maintainer's own pi harness is pinned `>=0.81.1 <0.83.0` while npm is at 0.84.2. The best Rust alternative spine, `rig-core`, is worse: 24 breaking 0.x minors in 12 months in the module ADR-0038 governs. In-house loop, `genai` 0.6.5 shapes borrowed, pi-agent-core semantics ported. Note the epic's vocabulary is stale: **npm `pi-agent` does not exist** (404; unscoped `pi-agent-core` is a squatted 0.0.1 placeholder); the live artifacts are `@earendil-works/pi-*` 0.84.2 (2026-08-14, MIT, Node ≥22.19.0) from `github.com/earendil-works/pi`.

## 2. The performance intuition, quantified

The intuition "Rust is faster, so the agent should be Rust" is **right for the conclusion and wrong for the reason**, and the ADR should say so to keep the argument honest.

**Where the agent loop lives is a latency non-factor.** The loop is I/O-bound on cloud LLM APIs: provider TTFT p50 spans 120 ms (Cerebras) → 1.2 s (Anthropic direct) → 3.8 s (reasoning models), p95 to 9.2 s; inter-token gaps run 10–50 ms. Against that, a Tauri IPC control-message roundtrip measures ~300 µs end-to-end (clamped by WebKit's 1 ms `performance.now()` resolution; the Rust dispatch floor is 722 ns for a 25-byte struct), and a sidecar's extra process hops cost 0.1–0.6 ms per event — **≤0.5 % of the fastest provider's TTFT and ~1–3 % of a single inter-token gap** (`tauri-embedding-options.md`, sources: tauri-conduit benchmarks, verticalapi/artificialanalysis TTFT surveys). Anyone arguing Rust-vs-TS for the loop on speed grounds is arguing over noise. The loop's wall-clock is provider TTFT × number of tool round-trips, full stop.

**Where Rust genuinely buys speed in this app:** (1) the audio capture/DSP path, which is already Rust and has real-time constraints — unaffected by this decision; (2) **local inference**: `llama-cpp-2` and `mistral.rs` are linked in-process behind the default `local-ml` feature (`Cargo.toml:45-46,333,342`), so a Rust loop reaches a local model **by function call**, whereas any TS runtime reaches it only via a localhost OpenAI-compat HTTP server AudioGraph does not ship (§4); (3) the one real transport rule, which is payload-shaped, not language-shaped: never move blobs through `invoke` (a 6.3 MB `Vec<u8>` arrives in JS as a 22.5 MB JSON number array with a 1,811 ms frame stall) — stream text and token deltas over `ipc::Channel`, which `start_streaming_chat` already does.

**So the honest claim is:** Rust-native wins this fork on trust-boundary preservation, substrate reuse, and local-inference forward-compat — not on loop latency.

## 3. The options, developed

The fork is not two-way. "Adopt pi-agent" decomposes into three concrete shapes plus the build option (`pi-ecosystem-audit.md` implication 1; `tauri-embedding-options.md` options A–D).

### Option C/D1 — Rust-native loop in `llm/`, existing React frontend presents it — **RECOMMENDED**

- **What 83cc users get:** a chat panel over the existing `ChatSidebar.tsx` pipeline, upgraded from single-shot to a bounded multi-turn tool loop with three read-only tools (transcript query, notes read, graph query); gated auto-answer wired into the existing `askAgentProposal → sendChatMessage` bridge; all five providers including Bedrock; local models included.
- **Engineering cost:** 5–7 engineer-weeks (`tauri-embedding-options.md`): tool plumbing per provider skin 1.5–3 wk, loop + budgets + cancellation 1 wk, three tools 1 wk, ledger/policy 0.5 wk (hooks exist), tests to repo standard 1–2 wk. This estimate *includes* the trust-boundary work the other options only include in their best case.
- **Key custody / trust boundary:** unchanged. Keys stay in the keyring-backed, zeroize-on-drop Rust credential store (`credentials/mod.rs:1-14,148`); `enforce_session_content_policy` and ledger appends fire from the same call sites they fire from today.
- **Duplication vs reuse:** zero duplication; 100 % reuse of the ~9k-line schema/retry/cache/route/gate substrate (`audiograph-agent-seams.md` §6).
- **Maintenance:** lowest — no upstream clock. Within-C guidance: **do not adopt `rig-core` as the spine** (24 breaking 0.x minors in 12 months; 0.42 alone breaks persisted-JSON message shape); borrow shapes from `genai` 0.6.5 (`Tool`/`ToolCall`/`ToolResponse`, `ToolCallChunk` streaming, `JsonSpec`) without necessarily depending on it, and if genai *is* linked, clear and assert `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` at startup — an ambient env var is a weaker control than a code flag for a no-transcript-in-telemetry invariant.
- **Forecloses:** nothing. A future TS orchestration layer can always sit on top of gated Rust commands; the reverse migration (TS loop → Rust) is the expensive direction.

### Option D2 — `pi-agent-core` in the webview, Rust-delegated `streamFn` — rejected for 83cc; harvest its API as the design spec

This is the shape the pi audit proved is real and upstream-supported: `pi-agent-core` + `pi-ai` are **CI-gated browser-bundle-safe** (upstream `scripts/browser-smoke-entry.ts` builds a live `Agent` under `esbuild platform:"browser"`; a treeshake gate enforces one provider catalog + one vendor SDK), `Agent` accepts any `streamFn` (3-line contract, no-throw, errors encoded in-stream), and `streamProxy` exists precisely for "apps that route LLM calls through a server [that] manages auth" (`pi-ecosystem-audit.md` §3,5). Keys never leave Rust; no CSP change.

- **What users get:** the same feature set as C, minus Bedrock-specific work (Rust still makes the calls), with pi's genuinely best-in-class loop ergonomics for free.
- **Why rejected anyway:** (1) it **relocates the ADR-0038 gate** — Rust receives a pre-assembled `{model, context, tools}` from the least-trusted tier and must re-resolve a named route id and re-run the content policy on an untrusted assembly, converting "Rust assembles, therefore Rust knows" into "Rust validates what the renderer claims" (`pi-ecosystem-audit.md` §5); (2) the loop's budget, turn cap, and ledger accounting live in the renderer, so ADR-0034's exhaustive-producer argument breaks — a renderer-driven loop can make N provider calls where policy assumed one (`tauri-embedding-options.md` D2); (3) pi's default `SessionManager` writes full transcripts as JSONL to `~/.pi/agent/sessions/` — an unsanctioned third data location — avoidable but fail-open; (4) the upstream clock (43/267 breaking releases; the 0.83.0 TypeBox break hit tool schemas; the maintainer's own harness pins three minors behind current); (5) tool execution against transcript/notes/graph must be Rust-side anyway (the data lives in `AppState`), so D2 buys "the `while` loop is in TypeScript" at full re-validation cost.
- **What to keep:** port these `pi-agent-core` semantics into the Rust loop — required `streamFn` with errors-as-terminal-message; the `AgentEvent` union (agent/turn/message/tool lifecycle with `message_update` text deltas); `beforeToolCall`(block) / `afterToolCall`(override) / `shouldStopAfterTurn` / `prepareNextTurn` as the four extension points; steering vs follow-up as **separate queues** with `all` | `one-at-a-time` drain modes; `AgentToolResult.terminate` requiring unanimity across a tool batch; `parallel` default with a per-tool `sequential` override that escalates the whole batch; `addedToolNames` for progressive tool disclosure. These are hard-won details a first-pass Rust loop would get wrong.

### Option A — `pi-coding-agent` as a Rust-spawned Node sidecar — rejected for 83cc; shelved for one named future need

- **What users get:** pi's full loop via the real, well-specified RPC mode (strict JSONL over stdio; Node `readline` is explicitly non-compliant). A working Tauri-v2 blueprint exists (`zosmaai/zosma-cowork`), key-handling internals UNVERIFIED.
- **Cost:** headline 3–6 wk, but the ledger/policy integration so the sidecar isn't an uninstrumented producer (ADR-0034) erodes most of the savings; +70–120 MB embedded JS runtime per platform (Bun `--compile` 73.3 MB linux-x64 measured; Node SEA ~90 MB); a second npm supply chain (972-file coding-agent tree) and a second telemetry exporter (`@opentelemetry/api` + `pi-telemetry` alongside the unconditionally-compiled Rust `sentry`) **inside the sanctioned LLM boundary**, each to be independently proven transcript-free.
- **Trust boundary:** this is the shape "adopt pi-agent" naturally suggests and **the only one that changes the boundary irrecoverably** if the sidecar holds keys or calls providers. It is survivable only under strict discipline: spawn from Rust only (`ShellExt::shell()` is not ACL-gated, so the webview never gains `shell:allow-execute`), `env_clear()`, key via stdin or — best — no key at all with a `provider.chat` RPC back into Rust; affirmatively disable pi's jiti extension auto-discovery (any loaded extension can read every API key via `ctx.modelRegistry.getProviderAuth()`; `docs/security.md` confirms no sandbox), its default `read/write/edit/bash` tool set, and its JSONL session store — all fail-open defaults.
- **Forecloses:** the light `--no-default-features --features cloud` build's size story; adds a permanent second CVE cadence.
- **Shelf condition:** revisit only for **sandboxed third-party tool execution**, where a separate crash boundary is genuinely right — and then the sidecar receives no provider key at all.

### Option B — agent loop in the webview with direct provider calls — rejected outright

Blocked by shipped config, not preference: CSP is `connect-src ipc: http://ipc.localhost` only (`tauri.conf.json:23`); keys would enter a renderer that aggregates live transcript (devtools are excluded from release builds for exactly this reason, `Cargo.toml:130-149`); Bedrock is not browser-callable, silently dropping a shipped provider; provider CORS behavior (OpenAI mid-flight changes, Gemini rejecting `x-stainless-*` preflight) can break the app without a release on our side; pi's own browser CORS escape hatch (`pi-proxy`) was never ported to the `@earendil-works` scope. ADR-0019 assigns "secret use" to Rust. Record the rejection in the ADR so it cannot be re-proposed.

## 4. The local-LLM seam — and the maintainer's direct question

**"Could pi-agent use the rust-backend, or is that too much to engineer?" — Yes, it could, cheaply, in either of two shapes; it is not too much to engineer, and that is exactly why it should carry zero weight in this decision.**

- **Shape 1 (IPC delegation):** `pi-agent-core`'s `Agent` takes any `streamFn`; a streaming Tauri command that emits pi-ai `AssistantMessageEvent` shapes is small (one command + event mapping), needs no CSP change and no listener. The cost is not the wiring — it is the security design around it (§3 D2): the command must accept only a **named agent-route id** (never a provider/baseUrl from the webview), re-resolve through `route.rs`, and re-run `enforce_session_content_policy` on the webview-assembled payload.
- **Shape 2 (localhost HTTP):** pi-ai's `Model{baseUrl, compat}` makes any OpenAI-compatible endpoint a config entry (`docs/models.md` names Ollama/vLLM/LM Studio; there is a dedicated llama.cpp doc). But AudioGraph would have to *ship* that server — and an unauthenticated localhost proxy holding credentials is reachable by any local process (`nvidia-switchyard.md` documents exactly this gap in NVIDIA's own reference router: no client auth, default `0.0.0.0` bind), so this shape requires a minted per-launch bearer token or a unix socket, plus a CSP widening. Strictly more work and more surface than Shape 1.

**The forward constraint's premise is stale in this repo.** "Someday local LLM inference may land in Rust (not before a rust-native vllm-class server exists)" — AudioGraph **already ships two Rust-native in-process inference engines by default**: `llama-cpp-2` (`llm/engine.rs`) and `mistral.rs`/Candle with JSON-Schema-constrained generation (`llm/mistralrs_engine.rs`), via `Cargo.toml:45-46 default = ["local-ml"]`, plus a generic OpenAI-compat client documented for Ollama/LM Studio/vLLM (`api_client.rs:3-4`). And the "vllm-class server" bar is closer than assumed: `mistral.rs serve` is a mature Rust-native OpenAI+Anthropic-compatible local server today, `candle-vllm` is a second, while vLLM-proper's Rust frontend remains an HTTP layer over the Python/CUDA engine (`local-llm-seam.md` §A). Every candidate runtime — pi-ai, rig-core, genai, the `ai` crate, and AudioGraph's own `ApiClient` — supports arbitrary OpenAI-compat `baseUrl`s as a verified first-class feature (`local-llm-seam.md` §B), so **the seam does not discriminate between the forks**.

**What leaks through the OpenAI-compat abstraction** (and therefore must be planned as per-endpoint `compat` tuning whichever fork wins, per `local-llm-seam.md` §C, all 2026-issue-verified): tool-call format fidelity (llama-server emitting raw XML tool calls in streams; tool-call counts decreasing mid-stream on smaller MoE models), `json_schema`+`strict` support that is version-gated and silently no-ops on older servers, SSE field completeness breaking strict client schemas, and unreliable context/usage accounting (LM Studio returning `NaN` token counts; Ollama's 2048-token default context). ADR-0038's "capability checks are per-ENDPOINT" discipline already models this correctly; extend it to local routes. **The Rust loop has one additional advantage here: for in-process engines it can bypass the HTTP surface entirely** — `MistralRsEngine`'s grammar-constrained generation gives tool-schema enforcement by function call, with none of the section-C leak surface.

## 5. Integration sketch (Rust-native), sequenced into verifiable units

Against the real seams documented in `audiograph-agent-seams.md`: the `selectAgentQueue`/`AgentProposalsPanel` question queue, the `askAgentProposal → sendChatMessage` bridge (`src/store/index.ts:1810-1824`), the `start_streaming_chat` + `Channel<ChatStreamEvent>` hot path, and `prepare_chat_request` context assembly (`commands.rs:2974-3037`).

1. **Route-layer inversion.** Reclassify `tool_calls` from `TerminalStatus::Failed` to a first-class continuation in `route.rs:646-649`, **behind the new agent path only**. *Verify:* existing non-agent dispatches still classify `tool_calls` as `Failed` (the current invariant is documented and test-pinned); new path unit-tested for continuation.
2. **Tool schema per skin.** `tools`/`tool_choice` on the OpenAI-compatible skin first (Api + OpenRouter — covers most users), Bedrock `toolConfig` second, local engines via `MistralRsEngine`'s existing schema-constrained generation third. Reuse `RequestOutputForm`/`ConstrainedDecodingGrade` (`route.rs:96,781`) rather than a parallel capability axis. *Verify:* request-body serialization tests per skin; the OpenRouter `require_parameters` pin still holds under tools.
3. **Bounded loop.** `max_turns`, per-turn budget via `RouteDescriptor::clamp_completion_budget` (`route.rs:177`), the existing `CancellationToken`, tool-result truncation. Port the pi-agent-core semantics listed in §3 (steer/follow-up queues, before/afterToolCall, terminate unanimity, parallel→sequential escalation). *Verify:* loop terminates under turn cap, budget clamp, cancellation, and unanimous `terminate` in tests.
4. **Three read-only tools over `AppState`:** transcript query (beyond the current last-10-segment window), **notes read — this closes a real gap: `prepare_chat_request` includes graph + transcript but NOT materialized notes today** (`audiograph-agent-seams.md` §3), and graph query (reusing `build_graph_chat_context`'s top-k selector as the tool's core). No new egress: in-process reads. *Verify:* tool outputs never appear in logs; fixtures contain no real transcript content.
5. **Gate + ledger per turn.** `enforce_session_content_policy` invoked once per turn with the agent's action id; one `provider_call_*` ledger row per model call carrying the reserved `"tool_calls"` DataClass. *Verify:* a privacy-mode-blocked session yields zero provider calls from the agent path; ledger rows are 1:1 with model calls under a multi-turn test.
6. **Stream extension.** Extend `ChatStreamEvent` with tool-lifecycle variants (tool_call_started/delta/result) rather than adding a second channel; the frontend already consumes this channel and coalesces deltas. *Verify:* old frontend tolerates unknown variants (serde tagging test); `ChatSidebar.tsx` renders tool activity.
7. **Gated auto-answer.** Slot the 83cc policy exactly where the manual "Ask AI" click sits: `askAgentProposal` already dismisses the card and routes the question through `sendChatMessage`; the auto-answer flow is a policy-gated automatic dispatch of the same action, surfaced through the existing `agent-status`/`agent-proposal` events (`events.rs:77,81`) and `AgentProposalsPanel.tsx`. Note pi has no primitive for an externally-triggered turn under human approval either — this is net-new product work on **any** fork. *Verify:* gate-off ⇒ no dispatch; gate-on ⇒ one dispatch per approved question; proposal dedupe unaffected.
8. **UI consolidation (parallelizable):** relocate/bridge `ChatSidebar.tsx` into the bento agent tile per 83cc's panel design — a UI move over an existing working pipeline, not a new integration.

Sequencing note per project memory: units 1–6 are one Rust lane; keep them serialized on this box.

## 6. Open maintainer decisions vs prototype probes

**Genuine product/preference calls (not settleable empirically):**
1. **Auto-answer gate policy:** per-question approval (current Ask-AI shape, automated suggestion), per-session opt-in, or fully automatic with undo? This defines what "gated" means in 83cc.
2. **Agent write access in v1:** tools read-only (recommended above), or may the agent propose graph writes through the existing `approve_agent_proposal` approval flow from day one?
3. **Surface consolidation:** merge chat into the bento agent tile and retire the sessions-browser "Ask" aside, or keep two entry points?
4. **The forward-constraint bar:** does `mistral.rs serve`/`candle-vllm` already satisfy "a rust-native vllm-class server exists," pulling the local-agent-backend timeline forward — or does the bar mean vLLM-parity throughput/hardware breadth? (Product judgment; `local-llm-seam.md` §A deliberately refuses to decide it.)
5. **Does the `--features cloud` light build ship the agent panel at all?** (Zero size cost under the Rust option, but it fixes the feature matrix.)

**Prototype probes (empirically settleable — run before or during unit 2):**
- **P1 — OpenRouter/Api tools streaming fidelity:** minimal `tools` request against the existing skin; confirm `tool_calls` finish-reason shape, streamed argument-delta assembly, and `require_parameters` interaction.
- **P2 — Bedrock `toolConfig` via `aws-sdk-bedrockruntime`:** confirm ConverseStream tool-use event shapes map onto the planned `ChatStreamEvent` variants.
- **P3 — MistralRs constrained tool emission:** can the in-process engine emit a valid tool call under its existing JSON-Schema-constrained generation, and at what latency?
- **P4 — `ChatStreamEvent` forward-compat:** serde round-trip of unknown enum variants against the shipped frontend decoder.
- **P5 — prompt-cache prefix under the loop:** verify appending tool results per turn preserves the byte-identical stable prefix discipline (`projection_llm.rs:44,1511-1523`) or document that agent-chat routes opt out of cache breakpoints.

## 7. Risks and UNVERIFIED

**Risks:**
- **Route-invariant flip (unit 1)** is a deliberate inversion of a documented, test-pinned invariant; scope it strictly to the agent path and review it as a security change, not plumbing.
- **Renderer-assembled input:** even under the Rust loop, the user message and any UI-selected context arrive from the webview; treat them as untrusted input to the gate, same as today's chat path.
- **Per-endpoint compat drift** (local-llm-seam §C) will surface the day a local agent route ships: tool-call format, strict-schema gating, SSE completeness, usage accounting all vary by server+model+streaming mode. Budget `compat`-style per-endpoint overrides, not drop-in parity.
- **Telemetry discipline:** if `genai` (or any tracing-based crate) is linked, it introduces a `tracing` sink outside the existing sanitized `log` pipeline, and its content-capture switch is an ambient env var — clear and assert at startup. The `router_replay` pattern from `vllm-semantic-router.md` (named, size-capped, independently disableable content-capture knob, structurally separate from always-on metrics) is the right template for any future agent-turn debugging capture.
- **Design-spec drift:** porting pi-agent-core semantics from the on-disk 0.83.0 `.d.ts` risks copying details 0.84.x changed; re-read the current `dist/agent.d.ts` at implementation time.

**UNVERIFIED (inherited from the artifacts, preserved):**
- `zosmaai/zosma-cowork`'s key handling (its `save_auth` RPC suggests sidecar-side persistence — the wrong shape here); irrelevant unless option A is revived.
- Whether pi 0.84.x docs changed statements quoted from the installed 0.83.0 tree; `StreamOptions.fetch` behavior under the anthropic-messages adapter; whether the pi treeshake gate covers the `openai-completions` bundle path (browser bundle size inferred, not measured). All moot under the recommendation.
- All Rust repo claims in this run are **source-read only** — no cargo/rustc was executed (hard rule: occupied Rust lane). The cost estimates in §3 are engineering-judgment ranges from `tauri-embedding-options.md`, not measured.
