# "nvidia-switchyard" — Identity Check and Architecture Mining

## Verdict

The name maps cleanly to a real, current NVIDIA project: **`NVIDIA-NeMo/Switchyard`** (product name "NVIDIA NeMo Switchyard"), a Rust proxy + embeddable library for routing LLM traffic across models/providers while preserving native OpenAI/Anthropic wire compatibility. It is NOT a Kubernetes-scale service you'd deploy as a cluster component — it ships as two consumable artifacts: a standalone Rust binary (`switchyard-server`, Axum-based HTTP proxy) and a set of Rust library crates (`switchyard-libsy`, `switchyard-protocol`, `switchyard-translation`) published on crates.io that embed directly into a host Rust process with no HTTP stack of their own. That library shape is exactly the "adoptable inside a Rust desktop-app backend" case the task asked me to evaluate, and it is directly relevant to AudioGraph: the routing *algorithms* (weak/strong classifier, signal-driven stage routing, escalation, random/A-B) are crate-embeddable, but the credential/auth model of the standalone server has a real gap against AudioGraph's security bar — it has zero client-authentication (no bearer tokens, no unix sockets) and defaults to binding `0.0.0.0`. Maturity is genuinely pre-alpha: the project is 3 months old (created 2026-05-19), on v0.2.0, self-labeled "Experimental software. Not for production use," and still shedding architecture (a Python CLI/launcher layer was fully removed on 2026-08-20, three days before this research). Treat routing *ideas* as mature and directly transferable; treat any *code* from this repo as a fast-moving pre-1.0 dependency, not a stable foundation.

### Architecture — what it routes on
Three-layer model (LLM client → target → route), documented at `docs/core_concepts.md`:
- **LLM client**: upstream base URL, wire format (`openai_chat` | `openai_responses` | `anthropic_messages`), credential env-var name, retry policy.
- **Target**: one upstream model ID bound to an LLM client.
- **Route**: one client-visible model ID plus the algorithm that selects/serves targets.

Routing algorithms (all implemented in `switchyard-libsy`, shared between the server and library paths):
- `passthrough` — one target, no decision.
- `random` — uniform or weighted split (A/B, cost experiments).
- `llm_classifier` — a judge model scores request `p_solve`; routes to `weak_target` when `p_solve ≥` a tier-conditioned threshold, else `strong_target`. Thresholds step up for `uncertain`/`unmatched`/`unsupported` verdicts; malformed/failed judge calls hard-fail to `strong_target`. Custom mode accepts an arbitrary JSON Schema + `jsonptr` policy for N-way routing across arbitrary targets, not just weak/strong.
- `stage_router` — routes on signals already present in the conversation (tool-call results, tool errors, agent-progress markers) without an extra classifier call; optional judge fallback when signals are ambiguous.
- `llm_classifier` with `mode = "escalation"` — every turn runs on the weak tier first; a judge reads that answer and decides whether to re-send to the strong tier.
- `session_affinity = true` — pins a session's first-selected target (including a fallback-to-strong result) for the rest of that session identity, skipping re-classification on subsequent turns.

So the routing signal taxonomy is: **capability/cost tier** (weak vs. strong model) decided by (a) an LLM-as-judge classifying the request, (b) deterministic signals already in the transcript (tool results/errors), or (c) fixed/weighted random assignment. There is no built-in semantic-embedding / intent-classification router (that's the vLLM Semantic Router's territory, a different, unrelated project — see "Adjacent project" below) and no cost-based or GPU-utilization-based routing signal; it is agent-turn-shaped, not inference-cluster-shaped.

Request lifecycle (`docs/architecture.md`): Receive (accept client API format) → Normalize (provider-neutral internal types) → Route (apply policy, pick target) → Execute (call backend, apply configured fallback) → Return (translate response/stream back to client's format). `switchyard-translation` performs the OpenAI Chat ⇄ OpenAI Responses ⇄ Anthropic Messages conversions in both directions, in both directions for both streaming and buffered payloads.

### Deployment shape — library vs. service vs. k8s-native
Not k8s-native at all; no Helm chart, no operator, no cluster CRDs turned up in any source. Two consumable shapes, explicitly documented as interchangeable ("These are the same strategies the server exposes as route types, so a deployment can move between the server and library paths without changing routing behaviour"):
1. **Server path** — build/install `switchyard-server` (`cargo install --locked switchyard-server`), point it at a TOML deployment file, run it as a standalone Axum HTTP proxy on a host+port you choose.
2. **Library path** — `cargo add switchyard-libsy` (crates.io, v0.2.0, Apache-2.0, MSRV 1.96.1, ~11K SLoC) directly into your own Rust binary. Per crates.io/the README: "It can use target-owned clients or hand each call back to the host, allowing it to embed in proxies, gateways, and agent runtimes without owning an HTTP stack." Concretely: an `Algorithm` yields a stream of `Step`s; `Step::CallModel` is a model call the *host* executes over its own transport/credentials, ending in `Step::Done`. This is the load-bearing detail for embeddability — libsy never opens a socket or holds a credential itself; it is a pure decision engine that your process drives.
- Both `switchyard-libsy` and `switchyard-protocol` are published crates (`cargo add switchyard-libsy`, docs at docs.rs/switchyard-libsy/0.2.0), not git-only dependencies, despite some in-repo docs still showing `git = "https://github.com/NVIDIA-NeMo/Switchyard.git"` snippets (a doc/README inconsistency, not a publishing gap).
- A `switchyard-py` crate exists (PyO3 bindings) purely so Python callers can drive the Rust core; Python is not required to use `switchyard-libsy` from Rust, and as of PR #501 (2026-08-20) the Python-based coding-agent launcher CLI (`switchyard launch claude/codex/openclaw`) was deleted outright — the project is contracting toward "native server or embedded library only."

### Credential handling model
- Per-`LLM client`, the TOML config sets `api_key_env`, naming an **environment variable**; the actual secret is never written into the config file. If `api_key_env` is omitted, no auth header is sent upstream at all (useful for local self-hosted vLLM/Ollama targets with no credential).
- The server reads these env vars at process startup. `TranslatingLlmClient` sets the wire-appropriate header per backend: `Authorization: Bearer <key>` for OpenAI-shaped backends, `x-api-key` + `anthropic-version` for Anthropic-shaped backends.
- Switchyard does not log request/response body content; the maintainers explicitly state telemetry headers never carry payload content. It supports a `--routing-log-file PATH` durable log that appends one JSON record per completed routed response (routing decision + metadata, not full prompt/response bodies) and `RUST_LOG`-gated structured tracing for decisions/failures.
- **Gap relative to AudioGraph's mandatory design element**: `switchyard-server` has **no authentication surface for its own clients** — no bearer token, no API key, no mTLS peer check, and **no unix-socket / named-pipe listen mode**. It only binds a TCP socket, defaulting to `0.0.0.0:4000` (configurable via `--host`/`--port`, so `--host 127.0.0.1` gets you loopback-only, but that is an operator responsibility, not a built-in default or enforced posture). TLS (`--tls-cert`/`--tls-key`) is available for transport encryption but is orthogonal to client authentication — it protects the wire, not who's allowed to send requests. Any local process that can reach the bound port can use the proxy and, transitively, the credentials it holds. This is precisely the AudioGraph non-negotiable ("a localhost proxy holding creds is reachable by ANY local process unless authenticated") and Switchyard-as-a-standalone-server does not solve it out of the box.

### OpenAI-compat surface and streaming passthrough
- Server accepts three inbound wire formats: OpenAI Chat Completions, OpenAI Responses, and Anthropic Messages; each configured LLM client declares exactly one *upstream* format, and `switchyard-translation` converts between whichever the client sent and whichever the backend expects — including converting Anthropic-shaped clients to call an OpenAI-shaped backend and vice versa.
- `GET /v1/models` lists configured route IDs (not upstream provider catalogs — "no catalog auto-discovery... to expose several upstream models, add one `passthrough` route per model"). The same endpoint also returns a Codex-compatible `models` array (context window, tool support, reasoning flags) so Codex can treat Switchyard as a direct provider.
- Streaming: `TranslatingLlmClient` handles both buffered and streamed calls; when the encoded request has `stream: true` the client gets back `LlmResponse::Stream`, and Switchyard translates and passes through Server-Sent Events end-to-end rather than buffering and re-emitting. Confirmed via repo docs ("Switchyard supports streaming by passing through Server-Sent Events (SSE) streams to clients") and via `docs/known_issues.md` item #1 ("Buffered upstream work continues after the client disconnects, so a cancelled request can still incur provider cost") — a real, currently-open streaming-cancellation gap worth knowing about if adopting this pattern.
- Known limitation (independent review, Starlog): provider-specific extensions are lossy across translation — Anthropic's `<thinking>` blocks and OpenAI's `tool_choice: required` / JSON-schema strict mode don't round-trip cleanly. If an app depends on provider-specific agent features, routing through a translating proxy can silently break them.

## Implications for AudioGraph's Router

1. **Adopt the algorithm shape, not the server binary.** `switchyard-libsy`'s `Algorithm` → `Step::CallModel` → host-executes-the-call → `Step::Done` pattern is close to a template for AudioGraph's own router: the Rust backend keeps owning the HTTP client, the credentials, and the TLS/loopback posture, while an embedded decision engine (hand-rolled or literally `switchyard-libsy` via `cargo add`) only decides *which* target a request should hit. This satisfies "API keys live in the Rust process" by construction — the algorithm crate never sees a key, because it never makes the call.
2. **Do not reuse `switchyard-server` as-is for the localhost proxy surface.** It has no bearer-token/API-key gate on inbound connections and no unix-socket option, and it defaults to `0.0.0.0`. If AudioGraph's router exposes an OpenAI-compatible localhost endpoint for a TS/pi-agent harness to call, it needs its own auth layer regardless of whether the routing logic underneath borrows from or vendors Switchyard's crates — e.g., a per-session bearer token minted by the Rust process and handed to the harness at spawn time, checked on every request, plus an explicit `127.0.0.1`-only bind (or, better, a Unix domain socket / Windows named pipe, which Switchyard doesn't support but Tauri's own IPC or a small custom Axum layer can). This is a place where AudioGraph's requirements are strictly stricter than what this reference implementation ships, not a place to copy it uncritically.
3. **The `weak_target`/`strong_target` classifier and `stage_router` signal-driven routing are directly transferable design patterns** for a future local-vs-cloud LLM split (epic 1dd6's local inference engine sitting behind the same router): route simple summarization/tagging calls over transcript chunks to a small local model when available, escalate to a cloud frontier model for complex synthesis, using either an LLM-judge classifier or deterministic signals (e.g., transcript chunk length, presence of ambiguous entity resolution) — mirroring Switchyard's `llm_classifier` and `stage_router` algorithms respectively, without adopting Switchyard's HTTP surface.
4. **Session affinity is a good idea for a desktop app**: pinning a routing decision for the life of a recording session (rather than re-classifying every chunk) reduces judge-call overhead and gives predictable behavior mid-session — directly applicable to AudioGraph's continuous-capture-to-graph pipeline.
5. **Protocol translation (OpenAI Chat ⇄ Anthropic Messages ⇄ OpenAI Responses) is a real, nontrivial feature** if AudioGraph's router needs to present one stable client-facing API (say, OpenAI-compatible) while swapping between Anthropic and OpenAI-shaped upstreams transparently — Switchyard proves the pattern works but also documents its edges (thinking-block and strict-tool-schema lossiness). If AudioGraph's harness only ever needs one wire format end-to-end, skip this complexity entirely; it's not free.
6. **Treat any direct Switchyard crate dependency as a pinned, re-audited pre-1.0 dependency**, not a long-term foundation — the project's own maintainers flag breaking API/algorithm changes before v1.0, and the Python-launcher deletion three days before this research shows the project is still discarding entire subsystems. Mining the *architecture* (three-layer client/target/route model, `Step`-stream host-executed calls, translation-as-a-separate-crate) is lower-risk and higher-value for AudioGraph than taking a runtime dependency on `switchyard-libsy`/`switchyard-server` today.
7. **The streaming-cancellation gap** (`known_issues.md` #1: cancelled client requests don't stop in-flight upstream billing) is a reminder to build cancellation-propagates-to-upstream explicitly into AudioGraph's own proxy if/when it streams LLM responses back to a UI that a user can interrupt mid-generation.
