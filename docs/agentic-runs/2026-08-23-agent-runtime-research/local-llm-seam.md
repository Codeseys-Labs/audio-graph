# The Future Local-LLM Seam — Does the Agent-Runtime Choice Foreclose It?

**Angle:** audio-graph-b437 (epic 83cc: pi-agent vs Rust-native agent loop). This note evaluates only the forward-compatibility question: if/when local LLM inference lands in Rust, does today's agent-runtime pick block it, and does the "point it at an OpenAI-compatible base URL" argument actually hold per-candidate, or is it an assumption.

## Verdict

**The agent-runtime choice does not gate the future local-LLM seam, for either fork — but the seam is a config knob, not a foregone code change, and it requires AudioGraph to keep the LLM route inside the sanctioned Rust boundary regardless of which agent runtime wins.** Every viable agent-runtime candidate — pi-agent's provider layer (`pi-ai`), the Rust agent frameworks (`rig-core`, `genai`, `ai`), and AudioGraph's own `api_client.rs` — is built around an arbitrary OpenAI-compatible `baseUrl`/`base_url` as a first-class, verified feature, not an incidental one. That means "point pi-agent at the Rust backend" is real and cheap **only if** the Rust backend exposes an OpenAI-compatible HTTP surface at that point (it doesn't have to *be* the inference engine; it can be a thin local proxy in front of `mistral.rs serve`/`llama-server`/a future Rust vLLM-class server). The harder-won fact from this pass is that "OpenAI-compatible" is not one contract: tool-call formatting, `strict` JSON-schema enforcement, streaming SSE field completeness, and context-length/usage accounting all diverge by local server, verified against 2026 issue trackers below — so whichever runtime wins must plan for `compat`-style per-endpoint overrides, not assume drop-in parity. On the inference-engine side, the maintainer's framing ("not until a rust-native vllm-class server exists") is already partially obsolete: `mistral.rs serve` is a mature, actively developed Rust-native OpenAI+Anthropic-compatible local server today (2026), and `candle-vllm` is a second, independently maintained one — both closer to "a rust-native vllm-class server" than the maintainer's mental model assumes, though neither has vLLM's model/hardware breadth. The literal vLLM Rust rewrite (the "Rust frontend") remains a server-side HTTP/tokenization layer in front of the unchanged Python/CUDA engine, not an in-process Rust inference path — that fact from the repo's own prior research (`docs/research/vllm-rust-frontend.md`) still holds as of this pass, updated only by a still-experimental feature-parity roadmap issue.

## A. State of Rust-native / Rust-shippable local OpenAI-compatible serving (2026)

### `mistral.rs serve` — mature, actively developed, the strongest "rust-native local server" candidate today

- Single binary; `mistralrs run` (terminal chat) and `mistralrs serve` (HTTP) share one process. `mistralrs serve` exposes **both** an OpenAI-compatible `/v1` surface (`/v1/chat/completions`, `/v1/completions`, `/v1/models`, `/v1/images/generations`, `/v1/re_isq`, `/health`) **and**, as of the current README, an **Anthropic-compatible** `/v1/messages` + `/v1/messages/count_tokens` surface on the same process. Source: ericlbuehler.github.io/mistral.rs/quickstart; github.com/EricLBuehler/mistral.rs README (fetched 2026-08-23).
- Model coverage is broad and multimodal: text, vision, video, audio input, speech generation, image generation, embeddings; GGUF/GGML/SafeTensors; automatic architecture/chat-template detection; in-situ quantization (ISQ) plus prebuilt UQFF artifacts; CUDA paged-attention + MoE perf work explicitly validated on GB10/B200/H100 SXM (v0.8.2 notes).
- Agentic features ship in the engine itself, not bolted on: integrated tool calling with **grammar-enforced strict schema mode**, a server-side agentic loop (auto-execute tools, feed results back), persistent Python/shell execution sessions, an **MCP client** (Process/HTTP/WebSocket), and OpenAI-compatible file inputs/Skills.
- AudioGraph already links `mistral.rs` in-process today (`src-tauri/src/llm/mistralrs_engine.rs`, `MistralRsEngine`, `mod.rs:10`) for entity extraction — but only via its embeddable Rust SDK, not `serve` mode. `mistralrs serve` is a separate deployment shape (spawn as a local HTTP server) that AudioGraph does not currently use but could point `ApiClient` at, exactly like the existing vLLM runbook does for a remote/WSL2 server (`docs/ops/vllm-backend.md`).
- **Verdict on maturity:** this is the best-positioned "rust-native vLLM-class local server" that exists **today**, not "someday." It is not vLLM's peer on raw throughput/hardware breadth, but it satisfies the maintainer's literal bar (Rust-native, OpenAI-compatible, servable) already.

### `candle-vllm` — independently maintained, alive, narrower scope than the name implies

- `EricLBuehler/candle-vllm` ("Efficient platform for inference and serving local LLMs including an OpenAI compatible API server") has **616 commits** with recent activity referencing current-generation models (Qwen3.6-27B-FP8, Qwen3.5-122B-A10B GGUF, GLM-5.2-FP8) and a `--ui-server` flag — this is an **actively maintained, non-archived** project as of this pass, not the stale/abandoned project a "not yet" assumption might expect. Source: github.com/EricLBuehler/candle-vllm (fetched 2026-08-23).
- It is a separate project from `mistral.rs` (same author, different codebase/scope) — candle-based, OpenAI-compatible server, PagedAttention-style serving. It does not carry vLLM's hardware/model breadth or its Python ecosystem integrations (LoRA marketplace, speculative-decoding zoo, semantic router, Omni multimodal pipeline — all vLLM-proper features per vllm-project.github.io's 2026 blog cadence).

### `llama-server` (llama.cpp) — trivially shippable, C++ not Rust, but the de facto "local OpenAI-compat" baseline

- Not Rust, but ships as a single native binary with zero Python dependency and is what AudioGraph already links via `llama-cpp-2` (`src-tauri/src/llm/engine.rs`) for native GGUF inference — the *serve* binary (`llama-server`) is the same upstream project in HTTP-server mode, trivially spawnable as a sidecar.
- Maturity is real but **uneven per surface** — see gotchas in section C: structured-output (`json_schema` + `strict`) support arrived later than `json_object` support and lagged for years in some builds; tool-calling format fidelity and `/v1/responses` SSE completeness both have open/recently-closed 2026 issues.

### vLLM itself — no full Rust rewrite; the "Rust frontend" is a server process layer, confirmed still evolving

- This repo already ran a dedicated research pass on this exact question (`docs/research/vllm-rust-frontend.md`, 2026-05-28): the official vLLM Rust frontend (merged via RFC #40846 / PR #40848, now living at `vllm-project/vllm/rust/`) replaces **only** the CPU-bound HTTP/tokenization/chat-template/dispatch layer; the CUDA inference engine remains Python/PyTorch, reached over ZMQ+MessagePack. There is no published Rust client crate meant for embedding, and the frontend explicitly targets Unix-like platforms only.
- **Freshness check for this pass:** `vllm-project/vllm` issue **#44280**, "[Roadmap] Rust Frontend Feature Parity" (opened by @BugenZhao), confirms the frontend is still gated behind `VLLM_USE_RUST_FRONTEND=1`, still "experimental and not yet feature-complete," and is actively tracking a long list of unported tool-parsers and reasoning-parsers (e.g. `granite4`, `minimax_m3`, `xlam`, `holo2`) as open work — i.e., progress since May, not a status change. Source: github.com/vllm-project/vllm/issues/44280 (fetched 2026-08-23). No independent, credible full-Rust vLLM engine rewrite exists in the official project; third-party full rewrites (`rvllm`, `guoqingbao/vllm.rs`) remain independent/early per the prior research and were not re-verified here (out of scope — see that file for disambiguation).
- **Net:** the maintainer's "not until a rust-native vllm-class server exists" bar is not met by vLLM-proper in 2026 (still Python-engine-cored), but — see above — it arguably *is* met by `mistral.rs serve` today, under a looser reading of "vllm-class" (OpenAI-compatible local server with paged-attention-class serving features), and candle-vllm is a second such project. Whether that satisfies the maintainer's intended bar is a product judgment call, not a technical one, and worth surfacing explicitly rather than silently substituting.

### LM Studio / Ollama — external-dependency options, not embeddable, with a real footgun

- Both are already named as generic-`Api` targets throughout the codebase (`src-tauri/src/llm/api_client.rs:3-4,27,60,85,102`, `mod.rs:5`, `sse.rs:3-4`, `streaming.rs:7`) — AudioGraph's `ApiClient` doc comments literally enumerate "Ollama, LM Studio, vLLM, OpenRouter" as targets today. They are processes the user runs themselves; AudioGraph never embeds them.
- Ollama's well-documented default-context footgun (historically 2048 tokens regardless of the model's real max, requiring an explicit `num_ctx` override) and LM Studio's context-overflow-policy default ("Stop at Limit" vs. "Rolling Window"/"Model Maximum") both mean the *served* context window is not reliably the *advertised* one — this is a serving-layer quirk, not an agent-runtime quirk, but it directly feeds section C's context-length-reporting gotcha.

## B. The decoupling argument — verified per candidate, not assumed

Claim under test: *if every agent-runtime candidate's provider layer supports an arbitrary OpenAI-compatible `baseUrl`, then the agent-runtime decision and the inference-engine decision are independent, and "could pi-agent use the Rust backend" reduces to "point it at `localhost`."* Verified per candidate, 2026-08-23:

| Candidate | Custom OpenAI-compat base URL support | Evidence |
|---|---|---|
| **pi-agent / `@earendil-works/pi-ai`** | **Yes, first-class.** `createProvider()` takes `baseUrl`, `auth`, `models`, and an `api` implementation (`openai-completions` is one of the built-ins); a documented Ollama example sets `baseUrl: 'http://localhost:11434/v1'` with keyless auth. `models.json`/extension `registerProvider()` supports the same for zero-code config. | pi.dev/docs/latest/custom-provider; github.com/earendil-works/pi/blob/main/packages/ai/README.md (fetched 2026-08-23) |
| **rig-core** (Rust) | **Yes, first-class.** `ProviderBuilder` trait exposes a `BASE_URL` const per provider; `OpenAICompletionsExtBuilder`/`OpenAIResponsesExtBuilder` both default to `OPENAI_API_BASE_URL` but honor the `OPENAI_BASE_URL` env var override (`from_env()`, `client.rs:216-222,239-244`) or an explicit `.base_url()` builder call. A documented "Implementing a Custom LLM Provider" guide plus a generic `OpenAICompatibleProvider` trait exist specifically for "any OpenAI-compatible providers" via `GenericCompletionModel`. | docs.rs/rig-core/latest (ProviderBuilder, client.rs source); docs.rig.rs/guides/extension/write_your_own_provider (fetched 2026-08-23) |
| **genai** (`jeremychone/rust-genai`) | **Yes, first-class, by design for this exact use case.** A "Custom Adapter" targets any OpenAI-compatible endpoint via `genai_{n}::model_name` + `GENAI_{n}_ENDPOINT`/`GENAI_{n}_API_KEY` env vars; a separate `ServiceTargetResolver` mechanism generalizes this further. Issue #5 ("OpenAI compatible API support," filed 2024) is closed `FIXED`. | github.com/jeremychone/rust-genai README + issue #5 (fetched 2026-08-23) |
| **`ai` crate** (lib.rs) | **Yes.** Explicit guidance: "For llama.cpp, MLX, Ollama, or another OpenAI-compatible image endpoint, use the OpenAI provider with the compatible server's base URL." Azure/llama.cpp/MLX/Ollama/vLLM all documented as configured handles with explicit `base_url`. | lib.rs/crates/ai (fetched 2026-08-23) |
| **AudioGraph's own `api_client.rs`** | **Yes, already shipped.** `ApiConfig { endpoint, api_key, model, .. }` (`api_client.rs:24-32`) is the exact same shape; doc comment lists "OpenAI, Ollama, LM Studio, vLLM, OpenRouter, Anthropic via proxy" (`api_client.rs:3-4`). | `src-tauri/src/llm/api_client.rs:3-4,24-32` |
| **Raw provider SDKs (OpenAI/Anthropic)** | Not independently re-verified this pass (well-documented, low-uncertainty, and not a 83cc candidate) — both official SDKs accept a `baseURL` constructor option; not re-cited here to avoid restating training-data-era knowledge as new verification. Flagging as the one line item in this table taken on lower rigor than the rest. | — |

**The claim holds.** Every actual 83cc-relevant candidate independently implements the same pattern: identity/auth/model-list/`baseUrl` as separable concerns, with `openai-completions`-shaped wire format as the default target for "point at localhost." This is strong, multi-source convergent evidence, not a single vendor's marketing claim.

**The qualifier that matters:** pi-ai's own docs describe **auto-detected compat quirks for a specific named list** (Cerebras, xAI, Chutes, DeepSeek, NVIDIA NIM, Together AI, zAI, OpenCode, Cloudflare Workers AI) — local servers (Ollama/vLLM/llama.cpp/mistral.rs) are **not** on that auto-detect list, so a local endpoint gets pi-ai's *default* `openai-completions` assumptions (`maxTokensField: max_completion_tokens`, `supportsStrictMode: true`, etc.) unless the integrator supplies an explicit `compat` override. rig-core's generic `OpenAICompatibleProvider` trait carries the same implicit assumption — "OpenAI-compatible" is asserted, not probed. This is exactly why section C matters: the decoupling argument is real at the *transport/config* layer, but each local server still needs its own `compat`-equivalent tuning to behave correctly once you look past `baseUrl`.

## C. Gotchas that leak through the OpenAI-compat abstraction

All four items below are verified against 2026-dated issues/discussions, not inferred from spec docs.

### Tool-calling format fidelity
- `ggml-org/llama.cpp#22072` (opened Apr 2026, closed "not planned"): `llama-server`'s OpenAI-compatible tool calling "sometimes emits malformed/incomplete JSON arguments for simple object schemas" — reproduced against Qwen3.6-35B-A3B via a real client (ChatWise).
- QwenPaw issue #3560 (Apr 2026): `llama-server` sends **raw XML-formatted tool calls at the end of the stream** instead of the OpenAI `tool_calls` field shape; the official OpenAI Python SDK cannot parse it. Marked High severity, "blocks llama.cpp users from using tool calling in streaming mode," with only a community patch as workaround.
- `openclaw/openclaw#38569` (Mar 2026): smaller MoE models (Qwen3.5-122B-A10B) streamed through `llama-server` produce a tool-call count that **decreases mid-stream** ("Invalid diff: now finding less tool calls!") — an artifact of grammar-constrained generation on smaller models that a naive streaming-diff parser mishandles; the same server+larger-model combo does not trigger it.
- `abetlen/llama-cpp-python#2227` (May 2026): Gemma 4 tool calls come back as raw native tokens inside `message.content` instead of `message.tool_calls` via the Python binding's `create_chat_completion()` — silently dropped, no error — even though the upstream **C++ server already carries the fix** (PR #21326). Same engine family, two different tool-calling behaviors depending on which surface you hit.
- **Implication:** "the model called a tool" is not a binary OpenAI-compat fact for local servers; format correctness varies by (server version, model family, streaming vs. non-streaming, and which binding/proxy sits in between).

### Structured output / JSON-schema support
- `ggml-org/llama.cpp#10732` (opened Dec 2024, still open in 2026, labeled enhancement/good-first-issue): `response_format: {"type": "json_object"}` works, but `response_format: {"type": "json_schema", ...}` silently does **nothing** — no error, just unstructured output — on the server surface that is supposed to implement the OpenAI structured-output contract.
- Independently, a May 2026 production report (`vectorize-io/hindsight#1656`) confirms the *fix path* exists in current builds — "`llama-server` 9200+ does support `response_format: {"type": "json_schema"}` with `strict: true`, which generates a grammar-level constraint" — but flags that the **default/soft path** (`json_object` + schema-in-prompt) is what many integrations still use, and that path "does not enforce `json_object` strictly for non-GPT models," producing numbered-list text, markdown-fenced JSON, or malformed JSON that multiplies retry/GPU cost 4-10x.
- Ollama's own structured-output support requires **0.3.0+**, and sub-7B / low-quantization models "frequently produce malformed JSON or ignore required fields entirely" regardless of server-side enforcement (sitepoint.com 2026 local-LLM guide).
- **Implication:** "structured output" is version-gated and quantization-sensitive per local server, and the schema-enforcement path is often not the one a naive OpenAI-compat client reaches by default — directly relevant to AudioGraph's own entity-extraction JSON-schema reliance (`llm/executor.rs`, ADR-0038's constrained-decoding grading discussion) if a future local-LLM-served agent chat path reuses the same extraction contract.

### Streaming SSE quirks
- `ggml-org/llama.cpp#20607` (Mar 2026, closed "not planned"): `llama-server`'s `/v1/responses` streaming SSE omits fields (`output_index`, `id` on `function_call` items, `created_at`/`model`) that the Vercel AI SDK's Zod schema requires, breaking tool calling end-to-end for any AI-SDK-based client (OpenCode, Cursor) even though the underlying model+server correctly executes 11-tool/48KB-prompt requests when tested directly with `curl`. A community-built 80-line SSE proxy patching exactly those three fields is the documented workaround.
- Combined with the tool-call-XML-in-stream issue above (QwenPaw#3560) and the fluctuating-tool-call-count issue (openclaw#38569), the pattern is consistent: **streaming is where OpenAI-compat servers diverge most**, because SSE chunk shape and incremental tool-call assembly are the least standardized part of the spec.

### Context-length / usage reporting
- `anomalyco/opencode#423`: "Context usage count is always 0 for some local openai-compatible providers" — reproduced against **LM Studio (Mac)** and **Ollama (Windows)**, explicitly **not** reproduced against `llama.cpp` in the same test matrix. Token counts come back as `NaN` when debug-logged from LM Studio's response — same `openai-completions` wire shape, three different usage-accounting behaviors.
- Ollama's long-standing default-context-window footgun (frequently 2048 tokens regardless of the model's actual trained context) and LM Studio's context-overflow-policy default both mean the *effective* context window a client can rely on is not reliably discoverable from the OpenAI-compat surface alone — `RooCodeInc/Roo-Code#2462` documents users needing a manual context-length override because the advertised/documented client-side config path didn't exist for their Ollama setup.
- **Implication:** any future local-LLM-served agent chat context budget (live transcript + notes + graph context, per this epic's stated inputs) cannot trust a served endpoint's self-reported context/usage numbers uniformly — this is exactly the kind of per-endpoint capability grading ADR-0038 already does for cloud routes (`docs/adr/0038-route-llm-operations-through-a-single-skin-named-route-table.md`, "Capability checks are per-ENDPOINT") and would need to extend to any local route.

## D. Shared-infrastructure note: what a future local-LLM engine would reuse from epic 1dd6 (offline STT v2)

Epic `audio-graph-1dd6` (offline STT v2, in progress, research phase — `docs/agentic-runs/2026-08-23-offline-stt-research/`) is independently building two pieces of infrastructure a future Rust-native local-LLM engine (or even just an `mistral.rs serve`/`llama-server` local-preset UX) would want to reuse rather than duplicate:

1. **Model download/readiness manager.** `src-tauri/src/models/mod.rs` already has `get_models_dir()` (`app_data_dir()/models`), a shared blocking `reqwest` client with connect/read timeouts, three download shapes (bare file / archive / multi-file), progress events (`model-download-progress`: `model_id, model_name, bytes_downloaded, total_bytes, elapsed_ms, percent, status`), and a `ModelReadiness` 3-state enum (`Ready | NotDownloaded | Invalid`) exposed via `get_model_status`. The 1dd6 audit (`audit-current-stack.md:291-324`) flags that this exists but isn't uniformly wired (diarization backend selection bypasses it) — a defect, but one an LLM-model-download UI would inherit either way, fixed or not.
2. **Hardware capability probe.** `gpu-backend-landscape.md` §12 designs exactly the primitive a local LLM engine needs before choosing CUDA/Vulkan/DirectML/CPU: "one probe, cheap, cached, overridable, and never able to prevent the app from starting," cached against `{selected_backend, adapter_luid, driver_version, app_version}` and re-probed on driver change. Concrete primitives already identified: `whisper_rs::vulkan::list_devices()` (per-GPU id/name/VRAM), `ort`'s `ExecutionProvider::is_available()` + `.error_on_failure()` pattern (defeats silent CPU fallback), and `mistralrs doctor`'s own GPU-detection-and-compiled-features report as a UI pattern worth copying (`rust-inference-stacks.md:304,391`).

**Read for 83cc:** neither piece is agent-runtime-specific — both are inference-engine plumbing that exists (or is being built) one layer below the agent-runtime decision. Whichever fork 83cc takes, a future "run a local LLM for the agent" feature is downstream of 1dd6's probe/download work, not gated by it, and not gated by whether the agent runtime is pi-agent or a Rust-native loop.

## Implications for the 83cc runtime decision

1. **The local-LLM seam is not a reason to prefer either fork.** Both pi-agent (via `pi-ai`'s provider layer) and a Rust-native loop (via `rig-core`/`genai`/AudioGraph's own `ApiClient`) can point at an OpenAI-compatible local endpoint with equal ease, verified per-candidate above. This axis should carry near-zero weight in the 83cc decision.
2. **"Point pi-agent at the Rust backend" requires the Rust backend to speak HTTP OpenAI-compat, not to lend pi-agent a Rust binding.** If pi-agent is adopted, "using the Rust backend for local inference" means AudioGraph's Rust process runs (or proxies to) an OpenAI-compatible server — `mistral.rs serve`, `llama-server`, or a future Rust vLLM-class server — on localhost, and pi-agent's `createProvider()`/`models.json` targets that URL. It does **not** mean linking pi-agent as a Rust library (it is a Node/TS package) or pi-agent calling into Rust structs directly.
3. **The trust-boundary fact this angle surfaces, restated plainly:** whatever process hosts the agent runtime's provider layer is where the LLM API key and the transcript/notes/graph content **must** live and flow, per this epic's non-negotiable design criteria. If pi-agent runs in a Node/Bun sidecar or the webview, the key and content cross into that process — a boundary change other angles are tasked with evaluating directly. This angle's finding is narrower but load-bearing for that evaluation: **the OpenAI-compat base-URL pattern works identically whether the calling process is Rust or Node**, so routing pi-agent's provider calls back through a Rust-hosted endpoint (keeping the key server-side, proxying through the sanctioned route) is technically straightforward *if* the maintainer wants pi-agent's UX without moving the trust boundary — worth flagging to whichever angle is deciding sidecar-vs-webview-vs-native.
4. **Budget for per-endpoint `compat` tuning, not zero-code parity, the day a local LLM route ships.** The gotchas in section C (tool-call format, `json_schema` strict-mode gating, SSE field completeness, context/usage accounting) are all real, current (2026), and vary by server+model+streaming-mode. AudioGraph's own ADR-0038 already treats capability as per-endpoint, not per-provider-family (`"Capability checks are per-ENDPOINT... never the aggregate... record"`) — that same discipline is the correct model for a future local route, and is already the right shape regardless of which agent runtime calls it.
5. **The maintainer's "not until a rust-native vllm-class server exists" gate may already be closer than assumed.** `mistral.rs serve` is a real, actively developed, Rust-native, OpenAI+Anthropic-compatible local server today, and AudioGraph already links `mistral.rs`'s embeddable SDK in-process (`mistralrs_engine.rs`) — the gap to "run it in `serve` mode as a local agent-chat backend" is a deployment-shape change, not a new dependency. This does not argue for pulling that forward into 83cc's scope, but it means the "someday" premise this angle was asked to test should be revisited on its own timeline, separate from the runtime-adoption decision.
