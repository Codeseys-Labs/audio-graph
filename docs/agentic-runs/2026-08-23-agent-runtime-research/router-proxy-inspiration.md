# Router-proxy design sketch — the Rust backend as credential-owning LLM proxy/router

**Angle:** design synthesis over the two project investigations ([`nvidia-switchyard.md`](./nvidia-switchyard.md), [`vllm-semantic-router.md`](./vllm-semantic-router.md)) plus the repo's real seams (`src-tauri/src/llm/route.rs`, `src-tauri/src/llm/executor.rs`, `src-tauri/src/projection_llm.rs`, `src-tauri/src/credentials/mod.rs`). 2026-08-23.

## Verdict

**The router-proxy shape is right for this app — but the correct framing is that AudioGraph does not need to *build* a router; it already ships one, and what is missing is a second, authenticated front door onto it.** ADR-0038's single-skin named route table is implemented and live: `LLM_ROUTES` (`src-tauri/src/llm/route.rs:188-281`) is exactly the "provider table with capability metadata" the proposal asks for, the `AuthorizedRoute` seal (`route.rs:378-389`) makes ungated dispatch a compile error, credentials are keyring-custodied and zeroized (`credentials/mod.rs`), and content egress is choked through `enforce_session_content_policy` (`commands.rs:663-706`). What does not exist is any production listener at all — every `TcpListener::bind` in `src-tauri` is a test mock (`ws_request.rs:121` is `#[cfg(test)] test_support`; the rest are provider-mock servers in `executor.rs`/`openrouter.rs`/`tts` tests) — plus tool-call plumbing (zero hits for `tools`/`tool_choice` in `src-tauri/src/`; `route.rs:646-649` maps a `tool_calls` finish reason to `Failed` with the comment "No request in this repository sends tools"). From the two mined projects, **adopt ideas, adopt no code**. Switchyard contributes three transferable patterns — the decision-engine-yields-`Step::CallModel`-and-the-host-executes-it shape (which AudioGraph's route/executor split already embodies), session affinity, and `GET /v1/models` listing *route ids* rather than upstream catalogs — but it is pre-alpha, has **zero client authentication, and defaults to binding `0.0.0.0:4000`** ([`nvidia-switchyard.md`](./nvidia-switchyard.md) §"Credential handling model"), i.e. it fails this run's one mandatory design element outright. vLLM Semantic Router contributes two — the signal→decision→plugin three-layer code organization (as pure logic, zero ML) and the `router_replay`-style *named, size-capped, independently-disableable, off-by-default* content-capture knob ([`vllm-semantic-router.md`](./vllm-semantic-router.md) §F) — while its headline feature, BERT/LoRA semantic classification at 10-120 ms/request, buys nothing over 2-5 hand-configured endpoints, a conclusion the project's own docs concede ("a basic router or rules table might be preferable," §H). Neither project solves loopback-plus-per-session-bearer (or UDS/named-pipe) client auth; AudioGraph builds that itself, in its own Axum-or-equivalent layer, as ~one middleware plus a token mint. The router core stays a Rust module with two doors: the in-process function call the projection pipeline and any Rust-native 83cc loop already use for free, and the authenticated OpenAI-compatible localhost surface that exists *only if* the 83cc fork picks an out-of-process client.

**Neither project provides the mandatory element.** Switchyard has no inbound auth at all and TLS-without-client-auth is explicitly called out as protecting the wire, not the caller ([`nvidia-switchyard.md`](./nvidia-switchyard.md) §"Credential handling model"). vLLM-SR's trust model is the cluster boundary (Envoy/mTLS/k8s NetworkPolicy), which does not exist on a desktop. The loopback+token design below is AudioGraph-original work, informed by both projects' *absence* of it.

## Implications for AudioGraph's router

### 1. Minimal viable router: what exists vs. what is new

Existing — the router core is ~shipped (all verified in-tree this pass):

| Piece | Where | Status |
|---|---|---|
| Named route table, per-**endpoint** capability rows (`max_context_tokens`, `max_completion_tokens`, `ConstrainedDecodingGrade`), honest `None` over fabricated numbers | `llm/route.rs:114-130`, `:188-281`; ADR-0038 | shipped |
| Compile-enforced authorization gate (`AuthorizedRoute` private seal; `authorize_route_dispatch` the only constructor) | `route.rs:378-389`, `:568` | shipped |
| Terminal-status normalization (`Completed`/`Truncated`/`Refused`/`Failed`/`TransportLost`) + four-class retry taxonomy, `ExternalEffectUnknown` never auto-retried | `route.rs:596-730` | shipped |
| Structured outputs: strict JSON-schema wiring incl. OpenRouter `require_parameters`, generate→validate→repair loop, versioned prompt ids | `projection_llm.rs:31-32`, `:540-756`, `:766`; `openrouter.rs:1609-1692` | shipped |

| Content-egress policy gate per action × data-class × provider | `commands.rs:663-706` | shipped |

New — the actual work of this proposal:

1. **The listener itself.** No production HTTP/socket server exists in `src-tauri`. This is a net-new Axum (or raw hyper) service owned by the Rust process, bound before any client spawns.
2. **Auth: per-session bearer token, loopback-only bind.** Mint a 256-bit random token per app run (never persisted, never logged, constant-time compared), hand it out-of-band: via `invoke()` for a webview client, via stdin for a Rust-spawned sidecar (the `env_clear()` + `CommandChild::write()` pattern verified in [`tauri-embedding-options.md`](./tauri-embedding-options.md)). Bind `127.0.0.1:0` (ephemeral port — the handoff carries `{port, token}`), and reject non-loopback peer addresses as defense-in-depth. This is the inverse of Switchyard's `0.0.0.0` default and is non-negotiable per this run's criteria.
3. **Unix socket / named pipe, weighed:** stronger than loopback+token (filesystem/ACL-scoped, no port at all), and tokio supports both (`UnixListener`; `tokio::net::windows::named_pipe`). The costs: (a) TS-client support is uneven — undici's `Agent { connect: { socketPath } }` handles UDS, but **Windows named-pipe reachability from `fetch`-based TS clients (OpenAI SDK, pi-ai) is UNVERIFIED** (probe P1 below); (b) a webview client cannot reach either — page `fetch` speaks TCP only and the shipped CSP is `connect-src ipc: http://ipc.localhost` (`tauri.conf.json:23`); (c) Axum-over-named-pipe is nonstandard plumbing. **Decision: loopback + bearer is the baseline (works for every client shape on all three OSes); design the listener behind a small `Listener` abstraction so a UDS/named-pipe variant is an additive hardening unit, not a rewrite.** If the 83cc client ends up *in the webview*, note that Tauri's existing `ipc::Channel` already beats both options and the HTTP surface may never need to be reachable from it at all.
4. **OpenAI-compatible *server* skin.** Existing code is the client side of Chat Completions; serving `/v1/chat/completions` + `/v1/models` is new. One skin only, mirroring `AdmittedSkin` — no Anthropic/Responses ingress until a probe admits a second skin (ADR-0038). `/v1/models` lists **authorized route ids** (`route.openrouter`, `route.local_llama`, …), Switchyard-style; the request's `model` field must name a route id — the client never sends a provider name, base URL, or upstream model id (this is [`pi-ecosystem-audit.md`](./pi-ecosystem-audit.md) implication #3 made wire-level).
5. **Tool-call passthrough.** Entirely new (see verdict). Needed by the 83cc agent loop regardless of runtime fork: request `tools`/`tool_choice` serialization, `tool_calls` deltas in the stream contract, and un-mapping `finish_reason: "tool_calls"` from `Failed` *when tools were sent* (`route.rs:646-649` — the current mapping stays correct for tool-less requests). No translation layer means no Switchyard-documented lossiness to inherit.
6. **Cost metadata.** The capability row has no cost field. Add `cost: Option<CostFacts>` under the same honesty rule as tokens (`None` means "not documented in this repository"; ADR-0038's None-over-fabricated posture, `route.rs:110-112`) — **recorded and displayed at authorization time** (ADR-0038 sub-decision 2 already requires cost shown when authorizing a fallback entry), never a silent selector (that would be rejected option C, "implicit selection is the silent fallback the ticket forbids, in a costume").
7. **Structural no-content-logging for the new surface.** The proxy's always-on telemetry carries route id, terminal status, retry class, latency, token counts — never bodies. Any debug body capture is the vLLM-SR `router_replay` pattern: a distinctly named config knob, size-capped, independently disableable, off by default, writing only to a sanctioned store ([`vllm-semantic-router.md`](./vllm-semantic-router.md) §F). The new surface is also a new ADR-0034 egress **producer** and must appear in the producer inventory and the data-movement ledger (`tool_calls` DataClass is already reserved — `src/generated/sessionDataMovement.ts:49`).
8. **The same gates, third caller.** Every request entering via the socket runs `enforce_session_content_policy` and `authorize_route_dispatch` — the listener is a third caller of the existing choke points, never a bypass. The `AuthorizedRoute` seal makes the bypass unwritable in Rust; the review criterion is that the HTTP handler resolves the route id through `resolve_route`/`route_by_id` and nothing else.

### 2. Semantic routing at N=1 — honest assessment

**The vLLM-SR classification layer is overkill here, and not marginally.** Its 13-signal extraction exists to pick among *many pooled, interchangeable* models under multi-tenant volume; AudioGraph routes 2-5 named endpoints whose capability facts are static rows. The static table dominates on every axis: 0 ms vs 10-120 ms per call, deterministic vs probabilistic, auditable vs opaque. The project's own docs agree ("for very simple routing needs… a basic router or rules table might be preferable," [`vllm-semantic-router.md`](./vllm-semantic-router.md) §H). There is also a repo-specific, harder reason: **ADR-0038 already rejected capability-negotiated dynamic selection (option C) as silent fallback in a costume — semantic classification is option C with an ML costume.** Adopting it would contradict an accepted ADR, not merely over-engineer. And the Switchyard `llm_classifier`/escalation variants carry a subtlety the desktop context makes disqualifying: **an LLM-judge sees the request content, so every judge call is itself a content-bearing egress event** that needs its own authorized route, its own egress-gate pass, and its own ledger row — at N=1 that is paying an extra authorized egress per turn to make a decision a table makes for free.

What *does* earn its place:

- **The three-layer separation as code organization** (signals = cheap eligibility facts already in hand: route capability row, provider readiness, privacy mode, operation kind; decision = deterministic match over `LLM_ROUTES`; plugins = egress gate → provenance stamp → ledger row as ordered hooks). Zero ML, zero dependencies; it names what `route.rs`/`executor.rs` already half-do.
- **The `router_replay` content-capture knob pattern** (§1.7 above) — the one directly load-bearing import for the security criteria.
- **Deterministic Switchyard-style `stage_router` signals plus session affinity, deferred to 1dd6**: once a local engine exists, "route projection-patch ticks to local when the model is downloaded and the hardware probe passed; route final refinement to the authorized cloud route" is a static predicate over facts the app already owns — no judge. Escalation local→cloud, if ever wanted, is an *individually authorized fallback entry* under ADR-0038's empty-list default, never automatic.
- **Not earned:** semantic cache (single user; the realistic repeat case — re-running a projection prompt over an unchanged basis — is an exact-match key on the basis hash, already the scheduler's coalescing concern); PII/jailbreak classifiers (transcript content is *supposed* to flow into the sanctioned route; the shipped, deterministic privacy-mode gate is the correct-scale control, and meeting transcripts are not adversarial prompt traffic).

### 3. Both consumers, one router — and 1dd6 behind the same surface

The router core is a module with **two front doors**, mirroring Switchyard's server/library duality ("a deployment can move between the server and library paths without changing routing behaviour," [`nvidia-switchyard.md`](./nvidia-switchyard.md)):

- **Projection pipeline (existing consumer): in-process door, unchanged.** `run_projection_patch_dispatch` keeps calling the executor as a function. Forcing it through localhost HTTP would add serialization, latency, and a new failure mode for zero gain — the projection lanes gain nothing from a wire hop inside one process. The refactor unit (U1 below) just makes the shared entry point *named*, so both doors provably converge on `authorize_route_dispatch`.
- **83cc agent runtime (chat): door depends on the fork.** A Rust-native loop ([`tauri-embedding-options.md`](./tauri-embedding-options.md) rank C; [`pi-ecosystem-audit.md`](./pi-ecosystem-audit.md) "port the semantics, not the runtime") uses the in-process door and the HTTP surface may never need to exist. A webview `pi-agent-core` loop uses the existing Tauri-channel commands (a `streamFn` over `start_streaming_chat`-shaped commands) — still no HTTP. **Only an out-of-process client (Node sidecar, external harness) needs the authenticated localhost surface.** Build the spine so the listener is an additive unit (U3-U5), and do not build it before the 83cc fork picks a shape that needs it — but design U1/U2 so it bolts on without touching route/executor.
- **1dd6 local inference: already a row, not a new architecture.** `route.local_llama` and `route.mistralrs` exist in `LLM_ROUTES` today with `requires_cloud_content_transfer() == false`, so local routes bypass the cloud egress gate *by construction* (`settings/mod.rs:634-640`). When 1dd6 lands its hardware probe + model-download manager, those feed the existing readiness gate (`ensure_llm_provider_start_enabled`, `provider_registry.rs:82`) and can populate per-model capability rows (context/completion budgets per downloaded GGUF — with real numbers this time, since the app controls the engine). A local engine served behind the OpenAI-compatible listener also automatically becomes reachable by the same out-of-process agent client with the same token — one surface fronting cloud and local uniformly, which is precisely the maintainer's proposed end state. An in-process engine (`llama-cpp-2`, `mistralrs` — both already linked, `Cargo.toml`) doesn't even need the loop through the socket for in-process consumers.

### 4. Sequenced verifiable units (smallest spine first)

Each unit is independently landable and names the check that proves it. U1-U2 are useful under every 83cc fork; U3-U6 only if an out-of-process client is chosen.

1. **U1 — Name the façade.** One in-process entry point (`llm::router::dispatch(RoutedRequest) -> RoutedResponse/Stream`) that the chat commands and the projection executor both call; no behavior change. *Verify:* existing test suite green; one new test asserts both consumers reach `authorize_route_dispatch` through the façade (the seal already guarantees they cannot skip it).
2. **U2 — Tool-call plumbing.** `tools`/`tool_choice` on the request types, `tool_calls` deltas in `stream_contract.rs`, `terminal_status_from_finish_reason` gains a tools-were-sent branch. *Verify:* recorded-SSE fixture round-trip test (request with tools → streamed tool-call deltas → assembled calls); regression test that tool-less requests still map `tool_calls` → `Failed`.
3. **U3 — Auth spine, no content path.** Loopback ephemeral-port listener + token mint + constant-time bearer middleware + `GET /v1/models` returning authorized route ids. *Verify:* integration test — no token → 401; wrong token → 401; non-loopback peer → refused; valid token → route list matching `LLM_ROUTES` ∩ authorized.
4. **U4 — Non-streaming `/v1/chat/completions` → façade.** Route id in `model`, gates fire. *Verify:* golden test against a local mock provider; a privacy-mode test proving `enforce_session_content_policy` blocks the socket path exactly as it blocks the Tauri path; ledger row asserted for the new producer.
5. **U5 — SSE streaming + disconnect-propagates-cancel.** *Verify:* test that dropping the client connection mid-stream triggers `stream_registry.cancel` and the upstream request is torn down — the test that proves AudioGraph does not ship Switchyard `known_issues.md` #1.
6. **U6 — Per-consumer route authorization + provenance.** The agent-chat route is a distinct authorized route from the projection routes (ADR-0038 sub-decision 1's shape: operations may differ in route); served-route provenance stamped on socket-served responses. *Verify:* provenance snapshot test; authorization-surface test that an un-authorized route id over the socket is rejected before dispatch.
7. **U7 — (with 1dd6) local-engine rows + readiness.** Hardware-probe/model-manager facts feed capability rows and the readiness gate; optional authorized escalation entry. *Verify:* route resolution test with local engine present/absent; egress-gate test that local routes pass under `LocalOnly` privacy mode.

### 5. Risks, UNVERIFIED items, and probes

- **R1 — Windows named-pipe reachability from TS HTTP clients: UNVERIFIED.** undici's UDS support (`Agent { connect: { socketPath } }`) is documented; whether `socketPath: "\\\\.\\pipe\\audiograph-llm"` works against a tokio named-pipe server, and whether the OpenAI SDK / pi-ai accept such a dispatcher, was not verified this pass. *Probe:* ~20-line Node script + ~40-line tokio named-pipe echo server; if it fails, loopback+bearer remains the only cross-platform option — which is the baseline anyway, so this risk cannot block the spine.
- **R2 — Client ergonomics with `{ephemeral port, token}` handoff.** pi-ai's `createProvider({baseUrl, auth})` and the OpenAI SDK's `baseURL` both accept this shape on paper ([`local-llm-seam.md`](./local-llm-seam.md) §B verified `baseUrl` support per candidate); header naming (`Authorization: Bearer` vs `api-key`) and error-path *logging of headers* in the chosen client are unverified. *Probe:* point the candidate client at the U3 spine; grep its debug/error output for the token.
- **R3 — Listener sharing a tokio runtime with live audio capture.** An SSE server under load must not starve capture. *Probe:* run capture + synthetic streaming load; measure buffer overrun/`CAPTURE_STORAGE_FULL`-adjacent metrics. Mitigation if needed: dedicated runtime for the listener.
- **R4 — vLLM-SR tool-call/streaming fidelity claims are UNVERIFIED at wire level** — flagged inside the source artifact itself ([`vllm-semantic-router.md`](./vllm-semantic-router.md) §G). This sketch depends on none of them; imported patterns are organizational only.
- **R5 — Token theft by a compromised client process.** Accepted and bounded: the token grants exactly the authority the webview already has via `invoke()` (routed, gated, ledgered LLM calls) — it never grants key material or ungated egress. State this equivalence in the ADR so the token is not mistaken for a key. A UDS/named-pipe upgrade (post-R1) narrows it further via peer credentials/ACLs.
- **R6 — Switchyard/vLLM-SR code adoption re-proposed later.** If ever reconsidered, `switchyard-libsy` is a pin-and-reaudit pre-1.0 dependency at best ([`nvidia-switchyard.md`](./nvidia-switchyard.md) recommendation #1), and `candle-semantic-router` is a Go-FFI-shaped crate with zero independent Rust dependents ([`vllm-semantic-router.md`](./vllm-semantic-router.md) "Implications" #5). Neither survives the auth bar or the scale test today.
- **R7 — Cost metadata has no in-repo source.** Every cost fact added to the table needs a citation or stays `None` — same honesty rule as the token limits (`route.rs:110-112`). UNVERIFIED until someone documents per-route pricing; do not scrape it implicitly.
- **R8 — Second wire skin pressure.** An out-of-process client that wants Anthropic Messages ingress would reopen ADR-0038's skin admission. The answer is the ADR's: a parity probe first, and pick clients that speak Chat Completions (all candidates in [`local-llm-seam.md`](./local-llm-seam.md) §B do).
