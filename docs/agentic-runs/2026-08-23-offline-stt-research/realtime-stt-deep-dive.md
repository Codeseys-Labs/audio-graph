# RealtimeSTT Deep Dive — Architecture Extraction for Offline STT v2

## Verdict

RealtimeSTT (KoljaB, MIT, ~10k stars, 850 forks, 147 open issues as of 2026-08-23 — [github.com/KoljaB/RealtimeSTT](https://github.com/KoljaB/RealtimeSTT)) is not a novel streaming-ASR architecture — it is a well-engineered **orchestration layer** around off-the-shelf batch-oriented components (WebRTC VAD, Silero VAD, faster-whisper/CTranslate2, and now a pluggable multi-engine factory). Its value for AudioGraph is almost entirely in the *state-machine and heuristics layer* — dual-sensitivity VAD gating, preroll buffering, dual-model (fast/accurate) transcription with text stabilization, and dynamic silence-duration tuning based on sentence completeness — not in any of the underlying ML components, which Rust already has equivalent or better crates for (whisper-rs, silero crates, sherpa-onnx bindings). Two architecture facts are decisive for AudioGraph's design: **(1) Whisper-family batch models are not natively streaming** — RealtimeSTT's "realtime" mode is VAD-gated re-transcription of a growing buffer, which has an inherent latency floor around one inference pass per update (500ms–1.5s in third-party benchmarks), not the <200ms achievable with cache-aware streaming encoders (Conformer/NeMo, Moonshine, Kroko, Cheetah). **(2) RealtimeSTT has no real-time speaker diarization**, and the project's own author has stated real-time diarization is unsolved in open source — the sibling project WhoSpeaks does *post-hoc, sentence-level* embedding-clustering diarization requiring ≥1.5s of clean per-speaker audio, not frame-level real-time diarization. AudioGraph should port the state-machine/heuristics *concepts* wholesale into Rust, but should not treat RealtimeSTT's whisper-batch-loop as the target streaming architecture, and must treat diarization as a separate, lagging, best-effort subsystem rather than a hard streaming requirement.

## 1. VAD Stack: WebRTC VAD + Silero, and how they combine

RealtimeSTT runs **two VAD models in series/parallel**, not one:

- **WebRTC VAD** (`_is_webrtc_speech`): a fast, cheap, frame-level GMM-based classifier (Google's libwebrtc VAD, wrapped via `webrtcvad` Python package). Configured via `webrtc_sensitivity` on a 0 (least aggressive / most sensitive-to-speech) to 3 (most aggressive / least sensitive) scale — inverted from Silero's scale. Used as the **first-pass, low-cost gate**.
- **Silero VAD** (`_is_silero_speech`): a small neural VAD (`create_silero_vad_model`, configurable ONNX or PyTorch backend via `silero_backend`, `silero_use_onnx`, `silero_onnx_model_path`, `silero_onnx_threads`). Produces a speech probability, thresholded by `silero_sensitivity` (0 = least sensitive, 1 = most sensitive — same direction as most people expect, opposite of WebRTC's scale). Silero is described as "more robust against background noise" and does the heavier lifting for **end-of-speech** detection.

**Combination logic**: speech is considered active only if `is_webrtc_speech_active` (or WebRTC speech was recent, i.e. debounced) **AND** `is_silero_speech_active`. WebRTC acts as a cheap trigger; whenever WebRTC fires, a more expensive Silero check is dispatched **on a separate thread** so the fast VAD isn't blocked waiting on the neural VAD. Silero's internal recurrent state is explicitly reset on recording start/stop and during warmup to prevent state leakage between utterances — this matters because Silero VAD (like many streaming VADs) carries hidden state across frames, and leaking that state across utterance boundaries silently degrades accuracy. There's also `silero_deactivity_detection` (bool) to specifically use Silero for the *deactivation* (speech-ended) side of the state machine, and `deactivity_silence_confirmation_duration` to require the "silence" signal to hold for a confirmation window before trusting it (debouncing against brief mid-word Silero dips).

Additionally, `faster_whisper_vad_filter` (default `True`) applies CTranslate2/faster-whisper's own bundled VAD filter *inside* the transcription call itself — a third, engine-level VAD pass, described in the docs as "for robustness against background noise" at the cost of extra GPU work. So the full stack in the worst case is: WebRTC (frame gate) → Silero (deactivation debounce, in a background thread) → faster-whisper's internal VAD filter (segment-level, inside the ASR call).

**Design implication**: this is a classic **cheap-fast-filter → expensive-accurate-filter cascade**, a pattern that transfers directly to Rust regardless of which crates back each stage.

## 2. The realtime loop: chunking, buffering, state machine

Audio enters via `feed_audio()` (or the built-in PyAudio microphone thread), accumulating into an internal `buffer` until `buffer_size` (default **512** samples) is reached, then pushed onto an `audio_queue`. A dedicated `_recording_worker` thread drains that queue continuously. `sample_rate` defaults to **16000 Hz** (the docstring warns changing it "will very probably break functionality" because WebRTC VAD is sensitive to sample rate — WebRTC VAD only supports 8/16/32/48kHz mono frames).

**Preroll**: a `pre_recording_buffer` (default duration **1.0s**, `pre_recording_buffer_duration`) continuously retains the *most recent* N seconds of audio even while not recording, so that when speech is detected the utterance doesn't lose its first syllables to VAD reaction latency. `pre_recording_buffer_trim_config` controls how/when that preroll is trimmed once merged into the recording. This preroll pattern is essential for any push-to-VAD design — the VAD needs several frames of speech to confirm activation, and without a preroll buffer you clip the onset of every utterance.

**State machine** (`AudioToTextRecorder`, states include `inactive`, `listening`, `recording`, plus wake-word states `wakeword`/`listening`, managed via `_set_state`):
- Recording starts either (a) explicitly via `start()`, (b) automatically when `start_recording_on_voice_activity=True` and `_is_voice_active()` returns true, or (c) after wake-word detection followed by voice activity.
- On start, the preroll buffer is prepended to the recording frames, and Silero state / stabilizer state are reset (see `core/lifecycle.py` — `RealtimeTextStabilizer.reset(...)`, `reset_silero_vad_state(...)`).
- Recording stops when silence has persisted past `post_speech_silence_duration` (dynamically adjustable — see §4), or via explicit `stop()`. `min_length_of_recording` discards utterances shorter than a floor (guards against VAD blips), and `min_gap_between_recordings` enforces a cooldown between consecutive recordings to avoid re-triggering on trailing audio/echo.
- On stop, `RealtimeTextStabilizer.finalize()` is called, flushing any pending stabilized delta as the final text.

**Recent refactor (visible in current `master`)**: the codebase has been decomposed from a single monolithic `audio_recorder.py` into `RealtimeSTT/core/` pure-helper modules — `lifecycle.py` (start/stop transitions), `recording_buffers.py`, `state.py`, `voice_activity.py`, `preroll.py`, `realtime_text_stabilizer.py`, `realtime_boundary_detector.py` — with `AudioToTextRecorder` explicitly kept as a stable public facade over them (per `docs/module-map.md`: *"This is the main compatibility boundary... must not reorder, rename, or remove parameters"*). This is a genuinely good separation-of-concerns model to imitate in Rust: **pure, dependency-free helpers for VAD/stabilization/preroll math, wrapped by a stateful orchestrator that owns threads/channels/callbacks.**

## 3. faster-whisper/CTranslate2 usage, and the dual-model split

`faster_whisper` (CTranslate2 backend) is the **default** of now **many** pluggable `transcription_engine` backends, selected through a factory (`RealtimeSTT/transcription_engines/factory.py`, `ENGINE_CLASS_PATHS` dict) with **lazy imports** so unused engine dependencies aren't installed (`pip install "RealtimeSTT[engine_name]"` extras). Verified full engine roster from `docs/engines/` and `docs/troubleshooting.md`:

| Engine | Backend / accel | Platform notes / adapter limitations |
|---|---|---|
| `faster_whisper` (default) | CTranslate2, CUDA (`float16`/`int8_float16`) or CPU (`int8`) | Full support for `compute_type`, `batch_size`, `suppress_tokens`, VAD filter |
| `whisper_cpp` | whisper.cpp (ggml), CPU-first | `compute_type`, `batch_size`, `faster_whisper_vad_filter`, `suppress_tokens` **don't map**; no language-probability reporting (returns 1.0) |
| `openai_whisper` | Original PyTorch impl | CUDA or CPU via PyTorch |
| `sherpa_onnx_*` (moonshine, parakeet) | ONNX Runtime, CPU INT8 | Models must be **manually downloaded/extracted** — no auto-download |
| `kroko_onnx` | ONNX Runtime, streaming-native `.data` models | Needs `stt-install-kroko --build` helper; Windows builder requires Python 3.12 x64 + Docker Desktop; community models are CC-BY-SA (commercial use needs verification) |
| `parakeet` | NVIDIA NeMo, GPU/CUDA | Linux/WSL2-optimized, not a practical native-Windows target |
| `omnilingual_asr` | Meta Omnilingual ASR, CUDA via matching torch/torchaudio | **Linux/WSL2 + Python 3.11.x only** — no native Windows, no Python 3.12+ (upstream `fairseq2n` dependency) |
| `moonshine`/`moonshine_streaming` | HF Transformers, CUDA/CPU | English-only in this adapter; no auto language detection |
| `granite_speech`/`granite`, `qwen3_asr`/`qwen_asr`, `cohere_transcribe`/`cohere` | HF Transformers / vendor packages, CUDA/CPU | Various — `qwen3_asr` can optionally use vLLM; `cohere_transcribe` may need gated model access |

**UNVERIFIED**: exact version numbers/dates each engine adapter landed — deepwiki and GitHub search show them present on current `master` but I could not pin a specific release tag per engine within this pass.

**Dual-model strategy** (the core "realtime vs final" split the maintainer asked about):
- **Realtime model** (`realtime_model_type`, default same tiny-class model unless overridden; `beam_size_realtime` default **3**): a smaller/faster model+beam config, invoked repeatedly by a dedicated `_realtime_worker` thread while recording is in progress, on a cadence controlled by `realtime_processing_pause` (default **0.1s**) — or, if `realtime_transcription_use_syllable_boundaries=True`, scheduled by a `RealtimeSpeechBoundaryDetector` that fires on detected acoustic syllable boundaries (with `realtime_boundary_detector_sensitivity` and `realtime_boundary_followup_delays` — default `(0.05, 0.2)` — forcing extra re-transcriptions shortly after a boundary) instead of a fixed timer. This is a real (if narrow) streaming-scheduling idea: don't re-run inference on a naive fixed clock, run it when the *acoustic signal* suggests a fresh word/syllable boundary just completed, with cheap follow-up retries.
- **Final model** (`model`, `beam_size` default **5**): runs once per completed utterance in a **separate process** (`TranscriptionWorker`, a `multiprocessing` worker communicating via pipes — not just a thread, deliberately isolating the heavier model and avoiding GIL contention with the realtime thread and the audio capture thread), using CTranslate2/faster-whisper's own bundled VAD filter and full beam search.
- `use_main_model_for_realtime=True` collapses both onto one model instance to save VRAM, at the cost of contention/reduced responsiveness — an explicit memory/latency tradeoff knob.
- `early_transcription_on_silence` (ms): starts running the **final** transcription speculatively *before* `post_speech_silence_duration` has fully elapsed, discarding the result if voice resumes — trades extra GPU work for lower perceived end-to-end latency on the final pass. This is effectively speculative execution applied to ASR finalization.

**Text stabilization** (`RealtimeTextStabilizer` / `RealtimeTextObservation`, `core/realtime_text_stabilizer.py`): each realtime pass produces a `RealtimeTextObservation` fed into the stabilizer's `observe()`, which returns an event exposing `accepted` / `is_outlier` / `stable_delta` / `stable_text` / `display_text`. This is the mechanism behind the `on_realtime_transcription_update` (raw, possibly jittery) vs `on_realtime_transcription_stabilized` (denoised) callback split. I could not extract the exact diffing algorithm (word-level LCP vs edit-distance vs repeated-observation voting) from documentation alone — **UNVERIFIED** at the algorithm-internals level, though the module is explicitly unit-tested in isolation (`tests/unit/test_realtime_text_stabilizer.py`) and documented as a "pure" helper with no side effects, order/timestamp-dependent. The architectural takeaway — that raw ASR partials must pass through an explicit outlier-rejecting stabilizer before being shown to a user or fed into a downstream KG extractor — is the important, portable idea regardless of the exact diff heuristic.

## 4. Deciding an utterance ended: silence duration + "Intelligent Speech Endpoint Detection"

Base mechanism: `post_speech_silence_duration` (seconds of trailing silence required to finalize). But the CLI client (`stt_cli_client.py`, `-sed`/`--speech-end-detection`) layers a **dynamic** adjustment on top, driven purely by punctuation heuristics on the realtime partial text:
- Text ending in `"..."` → treat as mid-sentence pause → use `mid_sentence_detection_pause` (default **3.0s**) — give the speaker more room.
- Text ending in sentence-final punctuation (`.`, `!`, `?`, `。`) **and** the previous partial also ended that way (i.e. stable across two observations) → `end_of_sentence_detection_pause` (default **0.7s**) — finalize fast.
- Anything else → `unknown_sentence_detection_pause` (default **1.3s**) — a middle-ground default.

Plus a **"Hard Break Prevention"** guard: a `text_time_deque` tracks recent partials + timestamps; if the earliest and latest cached texts in a short window are highly similar (i.e. the transcript is stuck repeating, typically from a noise loop or a stuck mic), the client force-calls `stop()` to break out — a watchdog against infinite non-terminating "recording" state.

RealtimeVoiceChat (sibling project, layered on top of RealtimeSTT — see §6) generalizes this into an ML-based `TurnDetection` module using a **DistilBERT sentence-completeness classifier**, blended 65% punctuation-heuristic / 35% model-probability, further scaled by a UI-configurable `speed_factor` and floored at `pipeline_latency`. This is the more sophisticated version of the same idea and is a stronger candidate to port than the plain punctuation heuristic, since it generalizes past reliance on punctuation (which ASR partials often omit or get wrong mid-utterance) — but it also introduces a second small model inference per partial, a latency/accuracy tradeoff AudioGraph should evaluate empirically rather than assume.

## 5. Wake-word support

Two backends, selected via `wakeword_backend`: `pvporcupine`/`pvp` (Picovoice Porcupine — **note: no longer free**, per a GitHub issue thread) and `oww`/`openwakeword` (fully open, ONNX/tflite models). Key parameters: `wake_words_sensitivity` (0–1), `wake_word_activation_delay` (grace period after monitoring starts before wake-word logic engages), `wake_word_timeout` (revert to inactive if no speech follows a detected wake word), `wake_word_buffer_duration` (samples trimmed from the recording buffer so the wake word itself doesn't leak into the transcript). Wake-word detection sets `wakeword_detected=True`, which — alongside plain VAD — is one of the two triggers that flips the state machine into `recording`.

**This is not directly relevant to AudioGraph's live-meeting use case** (no wake-word gating needed for continuous meeting capture) but the pattern — *a cheap pre-filter model gates entry into the expensive recording/transcription state, with its own timeout and buffer-trim housekeping* — is structurally identical to the VAD gate and reusable if AudioGraph ever wants a "start recording on hotword" mode.

**Known rough edges** (from GitHub issues, still open as of query time): `wakeword_backend='oww'` throws `AttributeError: 'AudioToTextRecorder' object has no attribute 'owwModel'` unless `wake_words` is *also* non-empty despite docs claiming it's unnecessary for openwakeword (issue #266, #297); and `openwakeword>=0.6.0` API is required by the current code but `setup.py` only floors at `>=0.4.0`, so pip can silently install an incompatible 0.4.0 on Python 3.13+ (where `tflite-runtime` has no wheels), producing confusing cascading errors (issue #297, opened against a documented version floor bug). **Lesson for AudioGraph**: pin exact transitive-dependency version floors for any wake-word/VAD ONNX runtime, don't just floor a minimum — silent-fallback-to-incompatible-version bugs are a recurring theme in this ecosystem.

## 6. Terminology / hotword seeding — and why it's weaker than it sounds

RealtimeSTT exposes `initial_prompt` (str or token-iterable, fed to Whisper's cross-attention conditioning) and `initial_prompt_realtime` (separate prompt for the fast pass), plus `suppress_tokens` (token-ID list, default `[-1]` which is Whisper's special "no timestamps" sentinel). This is **prompt-based steering**, not true contextual biasing/hotword boosting. Whisper's `initial_prompt` mechanism nudges output style/vocabulary probabilistically via the prompt tokens prepended to the decoder context — it does not guarantee a term appears, does not weight a phrase list at the lattice/decoding level, and competes for the same limited context window as everything else. The server's default `initial_prompt` example (from `RealtimeSTT_server/README.md`) is itself just formatting guidance ("End incomplete sentences with ellipses...") — confirming the mechanism is oriented at output *formatting*, not vocabulary/terminology injection. `suppress_tokens` only removes tokens Whisper *would* have said; it can't add tokens to a lexicon Whisper's tokenizer/training never saw (e.g. a proper noun or acronym not in Whisper's BPE vocabulary at reasonable probability). **This is a real architectural gap relative to what AudioGraph needs** for a "terminology/hotword seeding" feature — true contextual biasing (weighted phrase-list boosting at decode time, as in Kaldi/Vosk-family engines, NeMo's context-biasing, or lattice rescoring against a custom lexicon) is a materially different and stronger mechanism than prompt-conditioning, and is **not what RealtimeSTT does**. Any Rust engine wanting real hotword/terminology support should look past faster-whisper's prompt trick toward engines that expose actual contextual-biasing hooks, or implement a post-hoc rescoring/fuzzy-correction pass against a known term list.

## 7. Speaker diarization — confirmed absent, and why it's architecturally hard

Directly confirmed via deepwiki: *"RealtimeSTT does not explicitly support speaker diarization or speaker identification... the system focuses on real-time speech-to-text transcription."* Cross-checked against GitHub issue history:

- Issue #25 (2024, still referenced as current guidance): author states *"that is basically currently not possible, at least not in the opensource world... Realtime speaker diarization isn't solved in opensource still."*
- Issue #234 (2025): author elaborates on **why** — reliable speaker-embedding comparison needs "at least 1.5 sec of audio material from a speaker," shorter windows are "really unreliable," and real-world audio is further degraded by overlapping speakers and background noise; he also flags a **feedback-loop failure mode** where RealtimeSTT transcribes its *own* TTS output as if it were a new speaker utterance (self-triggering), for which the practical fix is **echo cancellation**, not diarization — a distinct problem AudioGraph must solve regardless of diarization scope if it ever plays audio back through a shared device.
- **WhoSpeaks** (KoljaB/WhoSpeaks): the author's own answer to the diarization gap. Architecture: per-*sentence* (not per-frame) voice-embedding extraction (via a TTS model's speaker-conditioning-latents extractor, e.g. Coqui XTTS's `get_conditioning_latents`, or alternatively resemblyzer/ECAPA/pyannote embeddings per the #234 thread's code sample) → cosine-similarity grouping → KMeans safety-check for single-vs-multi-speaker → agglomerative clustering with a silhouette-score-based automatic cluster-count selection. This runs as a **background thread consuming a queue of (text, audio) pairs from RealtimeSTT's finalization callback**, i.e. diarization lags behind transcription and re-clusters retroactively as more sentences accumulate — it is explicitly *not* a low-latency streaming component. The author reports it beating pyannote-audio on a hard 2-speaker test clip (95% sentence-assignment accuracy) but the tool description itself calls existing diarization libraries (including its own) as still "far from trivial," and `speaker_diarize.py` is hard-capped at 2 speakers (`auto_diarize.py` handles N speakers via the clustering path).

**Implication for AudioGraph is unambiguous**: do not design the STT v2 streaming path assuming diarization runs inline at frame rate. Architect diarization as a **separate, retroactive, sentence/utterance-level clustering pass** that consumes finalized utterances + their audio spans and emits speaker labels with a deliberate lag (seconds, re-clusterable as more data arrives) — mirroring WhoSpeaks' queue-consumer pattern, not the VAD/ASR hot path. This also argues for an architecture where the temporal knowledge graph can accept "utterance, unknown-speaker-provisional" then later receive a speaker-label correction/backfill event, rather than requiring speaker identity at ingestion time.

## 8. Latency-tuning knobs (full reference)

| Parameter | Default | Tradeoff |
|---|---|---|
| `silero_sensitivity` | (0–1 scale) | ↑ = more speech detected, more noise false-positives; ↓ = misses quiet speech |
| `webrtc_sensitivity` | 0–3, inverted scale | ↑ (toward 3) = less sensitive/more aggressive noise rejection, risks clipping speech in noisy rooms |
| `post_speech_silence_duration` | — | ↓ = lower finalize latency, risk of clipping mid-utterance pauses; ↑ = safer segmentation, higher latency |
| `min_length_of_recording` | — | filters VAD blips vs risk of dropping legitimately short utterances |
| `min_gap_between_recordings` | — | avoids overlap/echo re-trigger vs delay before next utterance can start |
| `realtime_processing_pause` | 0.1s | ↓ = more frequent partial updates, more CPU/GPU load |
| `beam_size` (final) | 5 | ↑ = better accuracy, slower |
| `beam_size_realtime` | 3 | ↓ = faster partials, less accurate |
| `compute_type` | "default" | e.g. int8 = much faster esp. on CPU, small accuracy cost |
| `early_transcription_on_silence` | 0 (off) | speculative final-pass execution before silence threshold fully elapses; trades GPU cycles for perceived latency |
| `use_main_model_for_realtime` | False | shares one model instance (saves VRAM) at cost of contention |
| `buffer_size` / `sample_rate` | 512 / 16000 | init-only; changing breaks WebRTC VAD assumptions |
| `pre_recording_buffer_duration` | 1.0s | preroll retained continuously; larger = safer against onset-clipping, more memory |
| `allowed_latency_limit` | 100 chunks | max unprocessed queue depth before chunks are discarded — a backpressure/drop-oldest safety valve |
| `realtime_transcription_use_syllable_boundaries` | False | switches realtime scheduling from fixed timer to acoustic-boundary-triggered |

Server/multi-user-specific tuning (FastAPI example server): `--max-sessions`, `--max-active-speakers`, `--max-realtime-queue-age-ms`, `--max-global-inference-queue-depth` — under load, the server explicitly **coalesces/drops stale realtime work while preserving the final transcription path**, i.e. it sacrifices partial-update freshness before it sacrifices final-transcript correctness under resource pressure. That prioritization order (drop partials first, protect finals) is a sound backpressure policy to replicate.

## 9. Known weaknesses / issues (verified against live GitHub issues)

- **GPU memory exhaustion** with larger models or dual-model setups; mitigations are smaller/shared models, reduced batch sizes, or CPU INT8 engines.
- **CPU float16→float32 silent fallback**: CTranslate2 logs a warning and auto-converts float16 model weights to float32 when the device/backend can't do efficient float16 (issue #221) — silent perf degradation if unnoticed.
- **`feed_audio` requires real-time-paced input** — RealtimeSTT uses timestamp information internally and explicitly "can't process faster than realtime" (confirmed by maintainer in issue #221), so it cannot be used to batch-process a pre-recorded file faster than its own duration without workarounds. This matters if AudioGraph ever wants to backfill/reprocess recorded audio quickly.
- **`input_device_index` sample-rate validation failures** on some external USB mics on Linux/ALSA (issue #276, open, unresolved as of latest comment 2025-10-29) — device capability negotiation is fragile.
- **Low-resource hardware (Raspberry Pi class) essentially unsupported** — native ML dependencies (onnxruntime/ctranslate2/torch) abort at the C++ level before Python can catch exceptions (issue #304); maintainer's own recommendation is to use such devices only as a thin audio-capture client streaming to a stronger machine — directly validating a client/server split architecture for constrained devices.
- **openwakeword version-floor bug** silently installing an incompatible API version on Python 3.13+ (issue #297) — see §5.
- **whisper.cpp adapter gaps**: no `compute_type`/`batch_size`/VAD-filter/`suppress_tokens` equivalence; no real language-probability reporting.
- **omnilingual_asr / parakeet Linux-only** — confirms that several of the newer, more accurate engines RealtimeSTT wraps are **not viable for a Windows-primary target** without WSL2, reinforcing that AudioGraph's Windows acceleration story cannot lean on these specific upstream Python packages even indirectly-inspired.
- **147 open issues** on a 10k-star/850-fork repo — a large, actively-used, but not fully triaged issue backlog; treat specific error messages you hit as likely-known and searchable rather than novel.

## 10. Sibling projects: RealtimeVoiceChat and Linguflex

**RealtimeVoiceChat** (KoljaB/RealtimeVoiceChat) — a full voice-agent pipeline built on RealtimeSTT + an LLM + RealtimeTTS. Its most portable addition beyond RealtimeSTT itself is the **`TurnDetection` module** (§4): async worker thread, punctuation-heuristic + DistilBERT-classifier blended pause-duration model, feeding back into RealtimeSTT's `post_speech_silence_duration` at runtime via callback (`on_new_waiting_time`). It also demonstrates **interruption handling**: when new user speech is detected while TTS is playing, it flips a `tts_to_client` flag off, marks `user_interrupted`, force-flushes any partial assistant answer, sends explicit `stop_tts`/`tts_interruption` client messages, and aborts in-flight LLM generation — a clean state-transition pattern for "user barge-in" that AudioGraph doesn't need for meeting transcription (no TTS to interrupt) but is a good reference if AudioGraph ever adds a voice-driven query/command layer on top of the graph. It also demonstrates **speculative TTS pre-synthesis** (starting TTS ~0.25s before the silence threshold fully elapses, `_TTS_ALLOWANCE_OFFSET_S`) — the same speculative-execution pattern as RealtimeSTT's `early_transcription_on_silence`, applied one stage downstream.

**Linguflex** (KoljaB/Linguflex) — a much broader personal-assistant framework (smart home, calendar, email, image gen, voice cloning) built on top of RealtimeSTT + RealtimeTTS + function calling. Its own README candidly frames its core engineering challenge as *"finding the lowest common denominator for your favorite 60 Python libraries"* across "various platforms, OS versions, Python environments, CUDA versions, and CuDNN versions" — i.e. dependency/environment matrix hell is treated as the *hardest* problem, harder than any individual ML component. This is a strong argument *for* AudioGraph's Rust-native, single-binary-with-vendored-acceleration-backends approach: the entire Python-ecosystem sibling-project cluster around RealtimeSTT independently converges on "the multi-backend Python dependency matrix is the actual pain," which a statically-linked Rust binary with compile-time backend selection sidesteps by construction. Linguflex contributes no STT-architecture ideas beyond what RealtimeSTT already provides (it pins `RealtimeSTT==0.3.81`, `RealtimeTTS[all]==0.4.19` as a consumer, not a fork).

## Implications for AudioGraph

**Port (concepts, not code):**
1. **Dual-VAD cascade** (cheap frame-gate → expensive neural confirm, running the neural check off the hot path) — directly implementable with existing Rust crates: `webrtc-vad` (0.4.0, verified on crates.io) for the fast gate, and any of several verified Silero-VAD Rust crates (`silero` 0.7.0, `silero-vad-rust` 6.2.1, `silero-vad-crs` 0.4.0 with SIMD/zero-dep C port, `silero-vad-pure` 0.1.1 pure-Rust — pick based on ONNX Runtime vs pure-Rust preference for the Windows .exe bundle) for the accurate stage. Reset VAD hidden state explicitly at utterance boundaries — this is an easy-to-miss correctness bug.
2. **Preroll ring buffer** (~1s) prepended on recording start — trivial to implement, prevents onset-clipping, should be a from-day-1 requirement.
3. **Dual-model realtime/final split with explicit stabilization layer** — run a small/fast model continuously for live UI feedback and a larger/accurate model once per finalized utterance; never surface raw realtime partials to the knowledge-graph extractor without passing them through an outlier-rejecting stabilizer first (jittery partials would otherwise pollute entity/relation extraction with transient garbage).
4. **Dynamic silence-duration / endpointing**, ideally the ML-blended (punctuation + lightweight completeness classifier) version from RealtimeVoiceChat rather than pure punctuation — punctuation alone is an unreliable termination signal for live meeting speech, which is often grammatically loose.
5. **Speculative early-finalization** (`early_transcription_on_silence` idea): start the accurate pass before the silence timer fully expires, discard-and-retry if speech resumes — reduces perceived finalize latency for cheap.
6. **Drop-partials-before-finals backpressure policy** under load — matches AudioGraph's own priority (a live KG can tolerate a missed partial update far better than a lost/garbled final utterance).
7. **Retroactive, lagging, queue-consumer diarization** (WhoSpeaks pattern: sentence-level embeddings → clustering, seconds of lag, revisable) — do not block the streaming pipeline on diarization; design the KG ingestion contract to accept a provisional "unknown speaker" utterance now and a speaker-label backfill event later.
8. **Client/server / thin-client split** as a resilience pattern for constrained hardware — validated independently by RealtimeSTT's own low-resource-device guidance, not just a nice-to-have for AudioGraph's Tauri desktop-vs-future-mobile story.

**Skip / do not imitate:**
1. **Whisper-batch-loop-as-"realtime"** — this is RealtimeSTT's central architectural compromise (VAD-gated re-transcription of a growing buffer, not a native streaming encoder), and it carries an inherent latency floor (third-party benchmarks put whisper.cpp streaming word-emission latency around 1.2s vs 500-900ms for native streaming engines and ~600-900ms for Moonshine/Cheetah). AudioGraph's stated priority ("streaming/incremental output beats batch accuracy") argues for evaluating native cache-aware streaming encoders (NeMo/Conformer-family, sherpa-onnx's zipformer/paraformer streaming models, Kroko) as the primary engine, with a Whisper-family model as an optional high-accuracy fallback pass — the inverse of RealtimeSTT's default framing where Whisper is primary and "realtime" is a bolt-on.
2. **`initial_prompt`-based "terminology seeding"** — this is prompt-conditioning, not contextual biasing; it's a weak substitute for true hotword/lexicon boosting and shouldn't be presented to the maintainer as a solved feature. If terminology seeding is a hard requirement, budget for either an engine with real contextual-biasing hooks or a post-ASR fuzzy-correction/rescoring pass against a term list.
3. **Wake-word engine plumbing (Porcupine/openWakeWord) verbatim** — not needed for AudioGraph's always-on meeting-capture use case; the underlying "cheap gate → state transition → timeout" pattern is reusable, but there's no reason to adopt Porcupine (no longer free) or openWakeWord (currently has real API-versioning breakage on Python 3.13+, per issue #297) as dependencies since the pattern is trivial to reimplement directly if ever needed.
4. **Python multiprocessing-for-GIL-isolation** — RealtimeSTT runs the final-transcription model in a separate OS process specifically to dodge Python's GIL; Rust has no GIL, so this isolation technique (with its IPC/pipe overhead) is pure Python-ecosystem tax that a native Rust engine simply doesn't need — use ordinary async tasks/threads instead.
5. **The specific multi-engine adapter roster** (omnilingual_asr, parakeet-via-NeMo, qwen3_asr, cohere_transcribe, granite_speech) — these are Python/HF-Transformers/NeMo-ecosystem conveniences, several explicitly non-Windows-native (omnilingual_asr, parakeet), and not something to replicate 1:1; AudioGraph's own engine survey (owned by a different investigator in this fan-out) should judge each model family on its own merits for Rust/ONNX/whisper.cpp/CTranslate2-equivalent availability rather than assuming RealtimeSTT's roster reflects a vetted "best of" list — it reflects whatever the maintainer wired up over time, with acknowledged adapter gaps in several of them.
