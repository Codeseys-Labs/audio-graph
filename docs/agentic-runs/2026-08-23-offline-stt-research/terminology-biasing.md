# Terminology Seeding & Contextual Biasing for Local ASR

## Verdict

Every local streaming ASR engine viable for AudioGraph's Windows build supports *some* form of runtime vocabulary biasing, but the mechanisms are architecturally incompatible with each other and none of them behave like Deepgram's `keyterm=` (the one biasing mechanism already shipped in this repo, [`src-tauri/src/asr/deepgram.rs`](../../../src-tauri/src/asr/deepgram.rs)). The three local engines already seamed into this codebase split into three different capability tiers: **sherpa-onnx's Zipformer transducer** (`src-tauri/src/asr/sherpa_streaming.rs`) has a real contextual-biasing graph (`hotwords_file`/`hotwords_score`, boost-weighted prefix tree) that the *currently pinned crate version already exposes in Rust* — but it is gated to `decoding_method=modified_beam_search`, and the stub in this repo is hard-coded to `greedy_search`, so hotwords are a decoding-method change away, not a wiring change away. **Moonshine** (`src-tauri/src/asr/moonshine.rs`, currently a native-library-free seam) has, in its *official* upstream (`moonshine-ai/moonshine`, MIT, 10.9k★, rebranded from Useful Sensors), the best mid-session update story of anything surveyed: `set_keyterms()` / `set_context()` mutate an already-streaming transcriber with no reconnect and "no latency cost," which is a strictly better fit for AudioGraph's live-graph-entities-feed-the-decoder goal than Deepgram's connection-time-only `keyterm=` param ever was — but only if AudioGraph binds the native Moonshine Voice C library directly, *not* the older Moonshine-via-sherpa-onnx ONNX path, which has no biasing hook at all. **Whisper-family models** (`initial_prompt`) are the weakest fit for streaming: the prompt budget is a hard 223 tokens and, in stock OpenAI Whisper, decays completely after the first 30s window unless `carry_initial_prompt` is set (and that flag had its own overflow bug until a 2026 fix) — `faster-whisper`/CTranslate2 solved this properly with a distinct `hotwords` parameter re-injected every window, which is the Whisper-family option AudioGraph should actually target if a Whisper backend is chosen. Across every engine, the biasing decays or degrades the same way: recall for listed terms goes up, at the cost of occasionally biasing *toward* an on-list term in ambiguous audio — which means a correction pass (fuzzy/phonetic lexicon matching, optionally LLM-constrained) is not optional scaffolding but the necessary second tier for anything decode-time biasing can't reach: names spoken before they're known, terms with no acoustic realization on the list, and out-of-vocabulary sequences the decoder simply cannot spell.

## 1. Academic landscape: contextual biasing 2023–2026

Direct arXiv sweep (`abs:"contextual biasing" AND (abs:"speech recognition" OR abs:transducer)`, sorted by date, 30 hits, run 2026-08-23) shows the field has moved through three overlapping eras that map onto what's implementable locally today:

- **Attention/beam-search biasing for transducers** (2023–2024): [Contextualized ASR with Attention-Based Bias Phrase Boosted Beam Search](https://arxiv.org/abs/2401.10449) (Jan 2024), [Improving ASR Contextual Biasing with Guided Attention](https://arxiv.org/abs/2401.08835), [Locality enhanced dynamic biasing and sampling strategies for contextual ASR](https://arxiv.org/abs/2401.13146). These are the academic lineage behind what sherpa-onnx and NeMo ship today: a context-phrase graph consulted during beam search, not a change to the acoustic model itself.
- **CTC-native and hybrid biasing** (2024–2025): [XCB: an effective contextual biasing approach to bias cross-lingual phrases](https://arxiv.org/abs/2408.10524), and critically the NeMo team's own line of work — "Fast context-biasing for CTC and Transducer ASR models with CTC-based Word Spotter" (Andrusenko et al., Interspeech 2024, cited as ref [17] in the TurboBias paper below) is the first practical method to extend beam-search-style biasing to CTC models, which previously had no hook at all.
- **GPU-native, model-agnostic boosting trees** (2025–2026): [TurboBias: Universal ASR Context-Biasing powered by GPU-accelerated Phrase-Boosting Tree](https://arxiv.org/html/2508.07014v2) is the state of the art as of this research date — a single boosting-tree mechanism that works across CTC, RNN-T/TDT, *and* attention encoder-decoder (AED/Canary) models in both greedy and beam search, scaling to 20K key phrases with only 2-5% RTFx overhead, citing companion papers "NGPU-LM" (Interspeech 2025) and "Pushing the limits of beam search decoding for transducer-based ASR models" (Interspeech 2025). This is now shipped in NeMo as `boosting_tree` config (see §5).
- **Zero-shot / no-retraining biasing**: [Zero-shot Context Biasing with Trie-based Decoding using Synthetic Multi-Pronunciation](https://arxiv.org/abs/2508.17796) (Aug 2025) and [Contextual Biasing to Improve Domain-specific Custom Vocabulary Audio Transcription without Explicit Fine-Tuning of Whisper Model](https://arxiv.org/abs/2410.18363) (Oct 2024) both target exactly AudioGraph's constraint — biasing a shipped model with no fine-tuning step.
- **Dynamic-vocabulary / streaming-specific**: [OWSM-Biasing: Contextualizing Open Whisper-Style Speech Models with Dynamic Vocabulary](https://arxiv.org/abs/2506.09448), [Contextual Biasing for Streaming ASR via CTC-based Word Spotting](https://arxiv.org/abs/2605.18222) (May 2026), [DYNAC: Dynamic Vocabulary based Non-Autoregressive Contextualization](https://arxiv.org/abs/2506.00422) — this cluster is explicitly about the problem AudioGraph has (a vocabulary list that grows mid-session as the knowledge graph discovers new entities), and is still an active research area, not a solved one.
- **LLM-in-the-loop biasing**: [Contextual Biasing for LLM-Based ASR with Hotword Retrieval and Reinforcement Learning](https://arxiv.org/abs/2512.21828) (Dec 2025), [RLBR: Reinforcement Learning with Biasing Rewards for Contextual Speech LLMs](found in the same sweep) — relevant only if AudioGraph ever adopts an LLM-native ASR path; not relevant to the sherpa-onnx/Moonshine/Whisper stack this report focuses on.
- **Post-ASR correction, not decode-time biasing** (see §6 for full treatment): [Retrieval Augmented Correction of Named Entity Speech Recognition Errors](https://arxiv.org/html/2409.06062) (Pusateri et al.), [DeRAGEC](https://aclanthology.org/2025.findings-acl.786.pdf), [RECOVER](https://arxiv.org/html/2603.16411v1) (March 2026), [Improving Named Entity Transcription with Contextual LLM-based Revision](https://arxiv.org/html/2506.10779v1).

The consensus across this corpus, stated explicitly in TurboBias and echoed in the zero-shot papers: decode-time biasing is a *rescoring* intervention (it shifts probability toward listed terms during search), not a correction mechanism — it cannot introduce a word the acoustic model's vocabulary can't spell, and aggressive boosting has a measurable general-accuracy cost (quantified in §5's Moonshine table). That's the academic grounding for the tiered recommendation in §8.

## 2. Whisper-family: `initial_prompt`

**Token budget is a hard, verified 223 tokens**, not the commonly cited "224" or "244" — confirmed against the actual `openai/whisper` source (`n_text_ctx // 2 - 1` = `448 // 2 - 1` = 223, standard checkpoints) via the [carry_initial_prompt overflow-fix PR](https://github.com/openai/whisper/pull/2823) and the community's own resolved confusion in [discussion #1824](https://github.com/openai/whisper/discussions/1824). At ~4 characters/token, that's roughly 890 characters — enough for a short attendee list and a handful of acronyms, not a domain glossary.

**Decay behavior is the load-bearing fact for streaming**: by default, `initial_prompt` is consumed once and only affects the *first* 30-second window. From window 2 onward, the prompt slot is filled by `condition_on_previous_text` (the model's own prior output), and the seeded vocabulary has zero further influence — this is exactly the "decay over long audio" failure mode the research brief anticipated, and it is real and default-on. The `carry_initial_prompt=True` option ([PR #2343](https://github.com/openai/whisper/pull/2343)) re-prepends the prompt to every window's decode call, but it shipped with a genuine bug: when `initial_prompt` itself is ≥223 tokens, the "remaining budget" calculation goes negative, the slice inverts, and the *entire accumulated transcript* gets carried instead of the glossary — the opposite of the intended behavior. This was only fixed in [PR #2823](https://github.com/openai/whisper/pull/2823) (2026), which clamps the remaining length at zero. Any AudioGraph integration against upstream `openai/whisper` (unlikely — this is a Python/PyTorch reference implementation, not something to embed in a Tauri binary) needs to pin a version at or after that fix if `carry_initial_prompt` is used with a glossary near the budget ceiling.

**Chunked-streaming interaction**: `initial_prompt` and `carry_initial_prompt` are properties of `transcribe()`'s internal sliding-window loop over a *known-length* audio buffer, not of a genuinely incremental streaming API. Feeding live 16kHz audio in small chunks to `transcribe()` per-chunk (the common DIY streaming pattern, documented painfully in [faster-whisper issue #299](https://github.com/guillaumekln/faster-whisper/issues/299)) means manually managing a token deque and re-supplying it as `initial_prompt` every call — brittle, and independently solved better by `faster-whisper`'s `hotwords` (below).

**whisper.cpp** (the C++ runtime most plausible for a Tauri-embedded Whisper path, given it has no Python/PyTorch dependency) exposes the identical `initial_prompt` + `carry_initial_prompt` pair at the C API level (`whisper_full_params.initial_prompt`, confirmed via [`include/whisper.h`](https://github.com/ggml-org/whisper.cpp/blob/master/include/whisper.h): *"maximum of whisper_n_text_ctx()/2 tokens are used (typically 224)"*), plus a second, structurally different mechanism: **GBNF grammar-constrained decoding** (`--grammar`, `whisper_grammar_element`), ported from `llama.cpp`. Grammar constrains the *space of legal outputs* (useful for closed command sets — "Red"/"Green"/"Blue"), it does not bias frequency inside an open vocabulary, and the maintainer of the [original biasing feature request](https://github.com/ggml-org/whisper.cpp/issues/1979) reported it becomes a decode-speed problem once the grammar covers "many, many words" — grammar is the wrong tool for a growing entity glossary, right tool for a closed command grammar.

## 3. faster-whisper / CTranslate2: a genuinely separate `hotwords` mechanism

This is the one Whisper-family path that solves the decay problem properly, and it is **not the same code path as `initial_prompt`** — verified from the actual `get_prompt()` implementation in [`faster_whisper/transcribe.py`](https://github.com/SYSTRAN/faster-whisper/blob/master/faster_whisper/transcribe.py):

```python
def get_prompt(self, tokenizer, previous_tokens, without_timestamps=False, prefix=None, hotwords=None):
    prompt = []
    if previous_tokens or (hotwords and not prefix):
        prompt.append(tokenizer.sot_prev)
        if hotwords and not prefix:
            hotwords_tokens = tokenizer.encode(" " + hotwords.strip())
            if len(hotwords_tokens) >= self.max_length // 2:
                hotwords_tokens = hotwords_tokens[: self.max_length // 2 - 1]
            prompt.extend(hotwords_tokens)
        ...
```

`hotwords` is re-encoded and re-injected into the `sot_prev` prompt slot on **every** decode call inside `generate_segments`, not just the first — this is the mechanism that survives long audio without an explicit carry flag. Constraints confirmed from source and [DeepWiki's transcription-options page](https://deepwiki.com/SYSTRAN/faster-whisper/4.3-transcription-options-and-configuration): mutually exclusive with `prefix` (prefix wins if both are set), truncated to `max_length // 2 - 1` tokens (same ~223-token ceiling as `initial_prompt`, budget not additive with it), and — per real-world reports in the [feature PR discussion](https://github.com/SYSTRAN/faster-whisper/pull/731) — recall degrades for names further down a long list (a user with 180 names reported top-of-list names transcribed correctly, names near the bottom ignored), which is consistent with the token-budget-truncation model, not a ranking bug. `faster-whisper` runs on CTranslate2 (CPU + CUDA fp16/int8, confirmed `ctranslate2>=4.0,<5` dependency), which is a real Windows-CUDA-capable backend, but it is a Python-hosted engine; a Rust embed would mean either FFI into `ctranslate2`'s C++ library directly or accepting a sidecar-process architecture — a decision that belongs to the GPU-backend-landscape and build-vs-adopt angles of this research run, not this one, but it directly determines whether this `hotwords` mechanism is reachable from AudioGraph's Rust core at all.

## 4. kyutai-stt: experimental prompt-based nudging, not a hotword list

Kyutai's [delayed-streams-modeling](https://github.com/kyutai-labs/delayed-streams-modeling/) repo (stt-1b-en_fr and stt-2.6b-en, delayed-streams-modeling architecture, genuinely low-latency streaming with word-level timestamps and semantic VAD) documents a prompt mechanism distinct from every other engine surveyed: you supply a **short audio clip plus its transcript** as a "prompt" (`--prompt_file`, `--prompt_text`), and the model imitates the spelling demonstrated in that clip for subsequent audio — e.g. priming with an audio clip saying "Loonah" makes the model spell a similarly-pronounced name "Loonah" instead of "Luna" elsewhere in the transcript. Upstream's own caveat, verbatim: *"this is an experimental feature and its behavior is very sensitive to the prompt provided."* This is architecturally the delayed-streams-modeling analog of Whisper's `initial_prompt` (context injected once, not a maintained hotword list), it requires an audio exemplar (not just text — a meaningfully higher integration cost than a plain word list), and there is no documented mid-session update API, no boost-strength knob, and no phrase-list mechanism. **Kyutai STT is not currently a viable terminology-biasing target for AudioGraph** — it's a strong streaming-latency architecture (see the parallel gpu-backend/model-landscape angles for that evaluation) with essentially no productized biasing story as of this research date.

## 5. sherpa-onnx: transducer-only `ContextGraph`, and a repo-specific gap

sherpa-onnx's hotwords mechanism, confirmed via source-grounded questions against the [k2-fsa/sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) repo and cross-checked against the currently-published Rust crate docs (not just wiki-summarized claims — see the correction below):

- **Mechanism**: a `ContextGraph` built from a hotwords file/buffer. Each line is a phrase (words or BPE/CJK tokens space-separated), with an optional per-hotword boost override (`HELLO WORLD :2.0`); the default boost is `hotwords_score`. During `modified_beam_search`, token-level scores of hypotheses that match a path through the graph get boosted; `OnlineRecognizerResult.context_scores` exposes the resulting log-domain contribution.
- **Hard constraint, verified against source**: hotwords require `decoding_method = "modified_beam_search"` *and* a transducer model. The C++ `OnlineRecognizerConfig::Validate()` explicitly rejects (`return false`, logged error) any config where `hotwords_file` is non-empty and `decoding_method != "modified_beam_search"`; CTC models (`OnlineRecognizerCtcImpl`) only support `greedy_search` or `ctc_fst_decoder_config` and have no `ContextGraph` integration at all — **confirmed independently in a live GitHub issue** ([#3092](https://github.com/k2-fsa/sherpa-onnx/issues/3092), Jan 2026): *"Note that hotword support is only available for transducer models."*
- **Modeling-unit constraint**: encoding hotwords into token IDs requires `OnlineModelConfig.modeling_unit` (`cjkchar` | `bpe` | `cjkchar+bpe` | `bbpe`) to match the loaded model's vocabulary, and `bpe`/`cjkchar+bpe` additionally require a `bpe_vocab` file from the same SentencePiece run that trained the model — this is metadata that has to travel with every downloadable model bundle, not something a user can bolt on after the fact.
- **Repo-specific correction — the pinned crate DOES have the fields**: an initial DeepWiki query claimed the Rust crate's `OnlineRecognizerConfig` does *not* expose `hotwords_file`/`hotwords_score`/`hotwords_buf`. That is **stale/wrong** as of the version this repo actually pins. Direct verification against `docs.rs/sherpa-onnx/latest` (crate version **1.13.5**, matching `sherpa-onnx = { version = "1.13", optional = true }` in [`src-tauri/Cargo.toml:268`](../../../src-tauri/Cargo.toml)) shows `OnlineRecognizerConfig` has top-level fields `hotwords_file: Option<String>`, `hotwords_score: f32`, `hotwords_buf: Option<Vec<u8>>`, alongside `decoding_method: Option<String>` ("greedy_search | modified_beam_search") and an `hr: HomophoneReplacerConfig` field (see below). **AudioGraph's own [`src-tauri/src/asr/sherpa_streaming.rs`](../../../src-tauri/src/asr/sherpa_streaming.rs) does not set any of these fields**, and hard-codes `rec_config.decoding_method = Some("greedy_search".to_string())` — so wiring hotwords into the existing streaming worker requires (a) populating `hotwords_file`/`hotwords_score`/`modeling_unit`/`bpe_vocab` and (b) **switching decoding_method to `modified_beam_search`**, which is a real latency/behavior tradeoff (beam search over `max_active_paths`, currently `4`, vs. greedy — more compute per frame, and a different error profile), not a free config toggle. This is a concrete, scoped follow-up ticket, not a research gap.
- **Mid-session update model**: hotwords are bound at **stream** creation, not recognizer creation — `OnlineRecognizer::CreateStream()` uses the recognizer's default hotwords, while `OnlineRecognizer::CreateStream(const std::string &hotwords)` (and the corresponding C API `SherpaOnnxCreateOnlineStreamWithHotwords`) lets a caller supply hotwords *per stream*, combined with any recognizer-level defaults. There is no `set_hotwords()` on a live, mid-utterance `OnlineStream` — changing the list requires destroying and recreating the stream (confirmed: no such API exists; the Swift binding's `reset()` demonstrates the destroy-and-recreate pattern). **This matters directly for AudioGraph's design**: the existing `sherpa_streaming.rs` worker already calls `recognizer.reset(&self.stream)` at every detected endpoint (see `process_chunk`, `is_endpoint` branch) — recreating the *stream* (not the *recognizer*, which is the expensive part holding the loaded ONNX model) at that same endpoint boundary, with an updated hotwords string built from newly-discovered graph entities, is a natural, cheap, no-reconnect insertion point. This is structurally better than Deepgram's situation in this same repo, where `audio-graph-c9b3` is blocked precisely because keyterms are a `v1/listen` URL query param requiring a full WebSocket reconnect to change mid-session.
- **`HomophoneReplacerConfig` — a native post-decode substitution stage, but CJK-scoped**: the `hr` field (`lexicon: Option<String>`, `rule_fsts: Option<String>`) is a real, shipped post-processing stage inside sherpa-onnx itself — but reading the actual [`homophone-replacer.cc`](https://github.com/k2-fsa/sherpa-onnx/blob/master/sherpa-onnx/csrc/homophone-replacer.cc) source shows it operates on UTF-8 words, converts them to a pronunciation string via a lexicon, and explicitly skips anything where "the first byte is < 128" (i.e., plain ASCII) — this is a Chinese-homophone disambiguation pass (pinyin-style pronunciation matching + FST rule normalization), not a general Latin-script fuzzy-correction layer. **Do not treat "sherpa-onnx has a built-in correction stage" as solving AudioGraph's English/mixed-terminology correction problem** — it's real, it's shipped, and it's the wrong shape for this use case unless AudioGraph adds CJK support.

## 6. NVIDIA NeMo / Parakeet: the most mature and most portable-in-concept mechanism, gated behind NVIDIA's own stack

NeMo's word-boosting documentation (verified against the [live NVIDIA NeMo Framework docs](https://docs.nvidia.com/nemo-framework/user-guide/latest/nemotoolkit/asr/asr_customization/word_boosting.html) and the [ASR language modeling & customization page](https://docs.nvidia.com/nemo-framework/user-guide/latest/nemotoolkit/asr/asr_language_modeling_and_customization.html)) now offers three generations of the same idea:

1. **GPU-PB (GPU-accelerated Phrase-Boosting, current default/preferred)**: works across CTC, RNN-T/TDT, *and* AED (Canary) in both greedy and beam search, including CUDA-graph mode; built from a user-supplied `key_phrases_file`; tunable `context_score` (recommended `1.0`) and `depth_scaling` (`2.0` for CTC/RNN-T/TDT, `1.0` for Canary); shipped in NeMo via [PR #14277](https://github.com/NVIDIA-NeMo/NeMo/pull/14277) and detailed in the [TurboBias paper](https://arxiv.org/html/2508.07014v2) (§1 above) — F-score improvement of 8-10% (greedy) to 17-23% (beam) on key-phrase recognition, 2-5% RTFx overhead even at 20K phrases.
2. **CTC-WS (CTC-based Word Spotter)**: combines greedy CTC/RNN-T decoding with a separately-run word-spotter over CTC logits; requires a Hybrid Transducer-CTC model to work with RNN-T; multiple pronunciation spellings per phrase supported directly in the context file format (`nvlink` → `nv link`, `gpu` → `g p u`).
3. **Parakeet-TDT boosting in practice**: confirmed via a live [GitHub issue thread](https://github.com/NVIDIA-NeMo/NeMo/issues/14772) on `parakeet-tdt-0.6b-v3` — the working config is `rnnt_decoding.greedy.boosting_tree.key_phrases_file=...` with `boosting_tree_alpha` in the `0.5`–`10` range depending on how hard you want to force a match, and a subtlety: case-sensitive Parakeet models need hotwords capitalized to match, including full-word capitalization for abbreviations. NVIDIA's [Speech NIM release notes](https://docs.nvidia.com/nim/speech/26.02.0/about/release-notes.html) independently confirm boost-score ranges: **0.5–2.0 for RNN-T/TDT models, 20–100 for CTC models** — these are not interchangeable scales, a real gotcha if AudioGraph ever swaps model families and reuses a tuned boost value.

This is the deepest, most model-agnostic biasing implementation surveyed — but it lives inside NeMo/PyTorch (a Python/CUDA training-and-inference framework, not something embeddable in a Tauri Rust binary without a sidecar process or a from-scratch reimplementation of the boosting-tree algorithm against an exported ONNX/TensorRT Parakeet model). Whether Parakeet reaches AudioGraph at all, and through which runtime, is the GPU-backend-landscape/rust-inference-stacks angles' call; the point for *this* angle is that if Parakeet-via-NeMo is chosen, its biasing story is the strongest of anything surveyed and directly reuses AudioGraph's existing graph-entity extraction as the `key_phrases_file` source with almost no translation.

## 7. Moonshine: two delivery paths with completely different biasing capability — do not conflate them

This is the sharpest finding of this angle, because AudioGraph already has a `moonshine.rs` seam (`MOONSHINE_PROVIDER_ID`, `MoonshineStreamingAdapter` — currently, per its own doc comment, *"backend-only and native-library-free for the first slice"*), and "Moonshine" resolves to two structurally different things depending on which runtime backs it:

- **Path A — Moonshine-via-sherpa-onnx**: sherpa-onnx ships an `OfflineMoonshineModelConfig` (preprocessor/encoder/uncached-decoder/cached-decoder ONNX files) for the original Useful Sensors Moonshine ASR models, run through sherpa-onnx's *offline* recognizer with `decoding_method="greedy_search"` and `hotwords_file=""` in every documented example ([sherpa docs](https://k2-fsa.github.io/sherpa/onnx/moonshine/models.html)). Moonshine is not a transducer in sherpa-onnx's type system, so it gets none of the `ContextGraph`/hotwords machinery from §5 — **this path has no biasing hook at all**, and no streaming (`Online...`) config was found for it, only offline.
- **Path B — native Moonshine Voice (`moonshine-ai/moonshine`, MIT, 10.9k★, rebranded from Useful Sensors)**: this is the project's *own* from-scratch C++ core library (not ONNX-Runtime/sherpa-onnx mediated), with native builds for Python, JS/WASM, iOS, Android, macOS, Linux, and **Windows**, and it ships genuine domain customization directly in its C API — verified against the upstream [`docs/models/domain-customization.md`](https://github.com/moonshine-ai/moonshine/blob/main/docs/models/domain-customization.md):
  - `keyterms`: a comma-separated phrase list (multi-word phrases supported, e.g. `"Anushka Sharma"`), settable at load or mid-stream via `set_keyterms()` (Python) / `setKeyterms()` (Swift/Java/JS) / `moonshine_transcriber_set_keyterms()` (C) — **"can change while audio is streaming,"** verbatim.
  - `context`: a free-form text passage (meeting notes, a ticket, a document the user is looking at) — the model's own tokenizer picks out multi-subword tokens as candidate terms (jargon/proper nouns need multiple subwords; common words don't), ranked by frequency-in-passage with rarest-word tiebreak, capped at `context_max_terms` (default 200), settable mid-stream via `set_context()`. Only single words are extracted this way (multi-word names need the explicit `keyterms` list alongside it), and words containing digits are skipped.
  - **Mechanism** (documented, not just claimed): a prefix tree over the model's subword vocabulary, with a per-token decoding bonus of `boost * (1 + ln(depth))` — a ramp specifically designed so greedy decoding (which can't backtrack a token) doesn't fire a wrong-but-plausible first subword just because a boosted term starts that way.
  - **Cost, quantified**: default `keyterm_boost = 2.0` "removes about a quarter of the errors on the words you listed for at most a quarter of a point on everything else" (upstream's own framing); their published LibriSpeech-derived benchmark table (boost 0 vs 1 vs higher, terms-WER vs. other-WER, across Tiny/Small/Medium) is the only *quantified* accuracy-vs-collateral-damage tradeoff table found across all engines surveyed. Upstream also states "up to a 40% reduction in errors with no latency cost" for the general mechanism.
  - Only the streaming architectures (`tiny-streaming`, `small-streaming`, `medium-streaming`) support this; non-streaming Tiny/Base raise an error if you try.

**This is the best mid-session-update story of any engine surveyed for AudioGraph's exact design problem** (a session vocabulary that grows as the knowledge graph discovers entities): no reconnect, no stream recreation, applied "on the next transcription" (i.e., the next utterance boundary within an already-open stream) — strictly better than sherpa-onnx's destroy-and-recreate-the-stream requirement (§5) and categorically better than Deepgram's destroy-and-recreate-the-*connection* requirement that stalled `audio-graph-c9b3`. The catch: AudioGraph's `moonshine.rs` seam is currently backend-agnostic on paper but would need to specifically bind Path B's native C library (via `moonshine_transcriber_set_keyterms`/`_set_context` FFI) to get this — if a future implementer instead wires `moonshine.rs` to sherpa-onnx's `OfflineMoonshineModelConfig` because that's the ONNX Runtime path the GPU-backend angle recommends for other reasons, terminology biasing silently disappears (Path A has none). This fork needs to be an explicit, written-down decision, not an implementation detail someone discovers by testing.

## 8. Post-ASR correction as the necessary second tier

Decode-time biasing (§§2–7) is a rescoring intervention bounded by the model's existing vocabulary and by token/phrase-list budgets; it cannot resurrect a name the acoustic model genuinely can't spell, and every quantified biasing mechanism surveyed (Moonshine's table, TurboBias's F-score deltas) shows a real, nonzero collateral-accuracy cost on everything *not* on the list. The 2024–2026 literature has converged on retrieval-augmented, LLM-based correction as the complementary second tier, run over ASR *text* output rather than at decode time — directly relevant given AudioGraph already has an LLM route in its pipeline that could host this:

- **[Retrieval Augmented Correction of Named Entity Speech Recognition Errors](https://arxiv.org/html/2409.06062)** (Pusateri et al.): indexes a 2.6M-entity database with **acoustic neighbor embeddings** (not semantic embeddings — semantic search underperformed here, an important negative result), retrieves candidates from ASR hypothesis n-grams, feeds hints + hypothesis to an LLM adapted via a rank-4 LoRA. 33-39% relative WER reduction on rare-entity test sets, no regression on general queries.
- **[DeRAGEC](https://aclanthology.org/2025.findings-acl.786.pdf)**: extends the RAG-correction pattern with an explicit *denoising* gate — phonetic similarity score + a one-line entity definition attached to each retrieved candidate, filtered via in-context-learned synthetic rationales before the LLM ever sees them (addresses the failure mode where a noisy retrieved-entity list actively hurts the LLM corrector). 28% relative WER reduction, training-free.
- **[RECOVER](https://arxiv.org/html/2603.16411v1)** (March 2026, most recent in the sweep): the most complete architecture — multi-hypothesis ASR decoding (5 temperatures), a three-signal scoring function combining exact-token hits, best Levenshtein similarity (weighted *highest* of the three, since it's "the primary mechanism for recovering corrupted entities," e.g. `sitiva → cytiva`), and phonetic-prefix hits, top-K=200 candidates handed to a strictly constrained LLM editor that can only propose entity-only find/replace edits from the supplied list, verified by deterministic guardrails (edit must be a listed entity, case-only changes rejected, similarity floor to block unrelated substitutions like `star → cytiva`). 8-46% relative entity-WER reduction depending on domain and strategy; even single-hypothesis + constrained-LLM-edit beats no correction by 12-41% relative.
- **[Improving Named Entity Transcription with Contextual LLM-based Revision](https://arxiv.org/html/2506.10779v1)**: closest to AudioGraph's exact scenario — local context is literally "lecture notes" or session-adjacent documents, phonetic+semantic matching filters the context's named entities against the ASR's, and an LLM (tested across GPT-4o, GPT-4o-mini, Llama3-70B, all showing the same pattern) revises with an explicit, interpretable rationale. Notably, dumping the *entire* context document into the prompt instead of the filtered candidate set made WER *worse* (32.3% → 43.4%) — the filtering step, not the LLM's context window, is what does the work.

The consistent design across all four: **retrieval/fuzzy-filter first, then a tightly constrained LLM edit, then deterministic verification** — never an unconstrained "clean this transcript up" LLM pass, which every one of these papers found to regress non-entity accuracy or hallucinate. Any AudioGraph implementation of this tier should copy that shape exactly.

## 10. Implications for AudioGraph

**Existing in-repo precedent is Deepgram-shaped and has a real, unresolved gap.** `keyterms: Vec<String>` in `DeepgramConfig` ([`settings/mod.rs:226-236`](../../../src-tauri/src/settings/mod.rs)) is explicitly documented as *"a static, user- or config-supplied glossary only"* with *"deliberately no mechanism... to grow this list from session/graph content mid-session."* `audio-graph-c9b3` (open, priority 3, blocked on `audio-graph-3d3e`) is exactly the ticket asking "what would it take to feed live graph entities into keyterms," and its own description calls out the real cost: reconnect-to-update-keyterms, audio lost during the swap, dedup/clamp interaction with the 100-keyterm cap. **Every local engine surveyed except Moonshine-via-sherpa-onnx solves this more cheaply than Deepgram does**, because none of them require tearing down a network connection — sherpa-onnx needs a stream recreation (cheap: the loaded ONNX weights in the `OnlineRecognizer` survive), and native Moonshine Voice needs nothing at all. If the offline-STT-v2 effort ships local ASR before `audio-graph-c9b3` is resolved, it is worth explicitly noting in that ticket (or a linked one) that the local-model version of this problem is strictly easier than the Deepgram version, so the design doesn't get anchored to Deepgram's constraints.

**The `d163` seed (pin+feed vocabulary for the graph strip's remove/merge/split operations) is not actually about ASR terminology biasing** — it's UI copy for `graphChangeFeed`'s missing operation-type lines, unrelated to feeding vocabulary into a decoder. Worth flagging so it isn't conflated with the ASR-vocabulary-flow design question in any downstream planning; the relevant precedent for *this* angle is `3d3e`/`c9b3` only.

**Concrete, scoped next steps, ranked by leverage-to-effort:**

1. **sherpa-onnx hotwords wiring is now well-defined, not exploratory.** `sherpa_streaming.rs` needs: (a) `rec_config.decoding_method = Some("modified_beam_search")` instead of `greedy_search` — evaluate the latency/behavior delta this causes before shipping, since it changes the streaming worker's fundamental decode strategy; (b) `rec_config.hotwords_file` (or `hotwords_buf`) populated from the same per-session vocabulary source that would feed Deepgram's `keyterms`; (c) `modeling_unit`/`bpe_vocab` set to match whatever Zipformer model bundle ships, which means model-bundle metadata needs to travel with the biasing feature, not be assumed; (d) hotwords updated by recreating the `OnlineStream` (not the `OnlineRecognizer`) at the existing `is_endpoint`-triggered reset point in `process_chunk` — this is the natural hook, already present in the code.
2. **If Moonshine is pursued for local ASR, the Path A vs. Path B fork (§7) needs an explicit decision recorded**, not an implicit one made by whichever runtime the GPU-acceleration angle picks first. Path B (native `moonshine-ai/moonshine`) is the only local engine surveyed with a true live, no-recreation vocabulary update API, which is architecturally the cleanest match to "graph entities discovered mid-session flow into the decoder" — but it means a from-scratch FFI binding to a C library sherpa-onnx doesn't mediate, which is real integration cost, and its GPU-acceleration story (CUDA/DirectML/Vulkan support in the native library, as opposed to ONNX Runtime's provider abstraction) needs verification against the gpu-backend-landscape angle's findings before this tradeoff can be resourced.
3. **A correction-pass tier belongs in the design regardless of which decode-time mechanism ships first**, because every decode-time mechanism surveyed has a hard ceiling (token budget, phrase-list collateral cost, or — for Whisper-family and kyutai — a decay/one-shot limitation) that a correction pass targets directly. The shape to copy is RECOVER/DeRAGEC's: (a) build the candidate list from the session's existing graph entities + attendee list, exactly the data AudioGraph already has; (b) score ASR output tokens against that list with a fuzzy+phonetic function (RECOVER's weights — exact 1.0, fuzzy 1.2, phonetic 0.6 — are a reasonable starting point, not gospel, and should be tuned against AudioGraph's own transcript error patterns); (c) route only the top-K candidates plus the ASR text to the existing LLM route with an explicit "entity-only find/replace, must be exactly one of these listed entities" constraint; (d) verify every proposed edit deterministically (listed-entity check, similarity floor, no case-only edits) before it touches the transcript or the graph. This tier is decode-engine-agnostic — it's the same design whether the decode-time engine ends up being sherpa-onnx, Moonshine, or a cloud provider, which makes it the highest-leverage, lowest-lock-in piece of this whole research question to build first.
4. **Do not budget for kyutai-stt's prompt mechanism** as a biasing feature for the near term — it requires an audio exemplar per term (not just text), has no phrase-list API, and upstream itself calls it experimental and prompt-sensitive. Track it, don't design against it.
