# AudioGraph: LLM-to-System-1 migration audit

Research date: 2026-11-21. Scope: the current working-tree Rust implementation, relevant frontend display folds, existing research, ADR-0049, and Seeds. This is a source audit and migration recommendation, not a model-quality benchmark or an implementation change.

## Question and direct answer

Where does AudioGraph call an LLM, or use handwritten rules, for a typed decision, and which decisions should move to System-1?

**Move semantic judgments over bounded, already-known candidates—not text production, arithmetic, authorization, or replay—to named decision routes.** The strongest immediate targets are the existing live-assist kind/answerability shadows, claim-to-evidence support, and session-local same-referent checks. Entity/relation typing, note novelty/topic selection, semantic duplicate-question detection, and bounded retrieval reranking are additional candidates. Speaker self-introduction and name-reference decisions fit the same contract once a candidate/evidence host exists; acoustic speaker identity does not become reliable merely by expressing it as yes/no.

**There is no standalone production “classify this with an LLM” call to delete in the audited seams.** Instead, extraction and projection prompts mix generation with several hidden decisions; live-assist classification is still heuristic, with System-1 observing it in shadow. Consequently, most initial migrations improve quality or reduce downstream spend; they do **not** remove an entire LLM call. A pre-generation projection gate is the main potential whole-call saving, but it is also a coverage-loss risk. Evidence: the three executor operations are extraction, chat, and projection generation ([executor.rs:287–410](../../src-tauri/src/llm/executor.rs#L287)); extraction asks for new names/descriptions/relations ([ontology.rs:168–180](../../src-tauri/src/ontology.rs#L168)); projection asks for document/graph operations ([projection_llm.rs:1619–1647](../../src-tauri/src/projection_llm.rs#L1619)); live-assist still chooses the effective kind heuristically after shadow evaluation ([speech/mod.rs:1255–1332](../../src-tauri/src/speech/mod.rs#L1255)).

Recommended ordering:

1. Close the independent-holdout and authority/pin/provenance prerequisites; keep shadows non-authoritative.
2. Activate measured live-assist decisions first; then ADR-0049's claim-support → same-referent → relation-type sequence.
3. Evaluate speaker name/cue decisions on revisioned evidence; do not replace the acoustic diarizer.
4. Trial note-change/topic selection, duplicate-answer detection, and bounded retrieval ranking only after coverage and replay contracts are explicit.
5. Leave World Promotion decisions blocked on a real User World host; existing organization-promotion schemas are not that host.

The order builds on [ADR-0049 §4](../adr/0049-decision-route-layer.md#4-ordered-migration-list), rather than re-proposing its route architecture.

## Evidence conventions and boundaries

- **Observed** means read in source or an existing first-party measurement report. Source citations use repository-relative URLs with `#L` line anchors and spell out file:line. Line numbers describe this audit snapshot, not a permanent API.
- **Proposed** means a new schema, budget, acceptance rule, or integration design in this report. It is not shipped behavior. Expected savings below are **inferences**, not measured gains.
- The source audit did not load private sessions, send content to providers, install models, or run builds/tests/linters/benchmarks. Existing benchmark results are attributed, not rerun.
- React remains configuration/control/display; Rust owns provider connections, content policy, graph changes, and timing ([AGENTS.md:41–50](../../AGENTS.md#L41)). All candidate decisions stay in Rust.
- For a hosted decision, even shadow evaluation sends content. The [Provider Addition Content-Egress Checklist](../designs/provider-architecture.md#provider-addition-content-egress-checklist) and [ADR-0049 §2](../adr/0049-decision-route-layer.md#2-egress) apply before dispatch, not only before authority.

## 1. What already exists—and what does not

### Live-assist has question schemas, not two authoritative semantic routes

The route table names **engines** (`route.decision.laya`, `d3_edge`, hosted Jev, etc.); `agent_proposal_kind` is a question/schema id carried on that route. ADR-0049 calls the second migration `agent_signal_grade`, but the production shadow question is **`answerable_question: noul`**, not the replay harness's older three-level score. The current shadow sends kind for every evaluated utterance and answerability only when the **heuristic** already says question. State is `{text, asr_confidence}`. Sources: [route.rs:88–175](../../src-tauri/src/decision/route.rs#L88), [shadow.rs:117–177](../../src-tauri/src/decision/shadow.rs#L117), [ADR-0049:350–378](../adr/0049-decision-route-layer.md#L350).

Every route starts with `calibrations: &[]`; `DecisionAuthority` currently has only `Shadow`. Native component digests are unfilled, and records start with `source: Heuristic`. A returned `outcome: Decided` is therefore **not permission to act**. Sources: [route.rs:49–65](../../src-tauri/src/decision/route.rs#L49), [route.rs:258–273](../../src-tauri/src/decision/route.rs#L258), [route.rs:343–362](../../src-tauri/src/decision/route.rs#L343), [route.rs:529–559](../../src-tauri/src/decision/route.rs#L529), [route.rs:807–859](../../src-tauri/src/decision/route.rs#L807).

Two practical consequences for evaluation:

- The existing shadow cannot measure answerability on questions the heuristic misses. Replay must ask the production answerability schema on the human-labeled question population, not only the heuristic-question intersection. Otherwise the proposed kind-recall improvement is invisible. This is an inference from [shadow.rs:120,164](../../src-tauri/src/decision/shadow.rs#L120) and the existing conditional evaluation denominator ([system-one-eval:52–56](system-one-eval-2026-10-18.md#L52)). Changing when questions are bundled must be schema/engine-evaluation versioned, especially for a joint-schema engine.
- Shadow is not latency-free: speech waits for `work.evaluate` before card minting. Capture is not shown to block here, but proposal delivery can wait for the decision. Budget queueing/cold-load/end-to-end time, not just the model forward ([speech/mod.rs:1255–1332](../../src-tauri/src/speech/mod.rs#L1255)).

### New families need more than a question inserted into the current dispatcher

The present record builder stamps every request with `LIVE_ASSIST_SCHEMA_VERSION`; movement records declare `TranscriptText` and `UsageMetadata`; calibration has dataset/count/metric fields but no independent-holdout manifest fields. Do not send graph/notes/speaker-candidate state under these unchanged assumptions. New families need their actual schema version, data classes, candidate/evidence snapshot identity, and artifact host carried through the route boundary. Sources: [route.rs:307–325](../../src-tauri/src/decision/route.rs#L307), [route.rs:546](../../src-tauri/src/decision/route.rs#L546), [route.rs:628–630](../../src-tauri/src/decision/route.rs#L628).

## 3. Typed-decision candidate inventory

**All budgets in this section are proposed ceilings, not existing measured SLAs.** Unless stated otherwise, use a warm native route with a **≤500 ms p95 end-to-end decision budget** on an eligible CPU-only configuration; target **≤100 ms p95 on an actually supported/measured GPU**. Queueing, serialization, model cold load and each question's compute must be reported separately. Failure/abstention retains the named baseline; no alternate-provider walker.

The per-row evaluation metric is applied using the common independent-holdout protocol in §6. Each row identifies its baseline and error risk so “agreement” is not confused with quality.

## 5. Expected performance and economic result: bounded claims only

The existing native benchmark measured d3-edge at **7.36 ms p95 short / 20.8 ms p95 long on CUDA FP32**, versus **400 ms short / 1,540 ms long on CPU FP32**, with short = 128 tokens and long = 751 tokens, one question per request. These are warm measurements on one Ryzen 7700X / RTX 5090 Windows machine. CUDA edge construction + first forward was **1.2–1.8 s**. Do not generalize “d3-edge meets 500 ms on CPU” to graph/notes state or multi-question requests. Source: [d3-native-latency:8–40](d3-native-latency-2026-10-18.md#L8).

The existing live Jev evaluation actually completed: **12 synthetic spans**, requested `jev-latest`, served `jev-1.13.0`, p50/p95 **87.8/428.0 ms**, estimated **$0.00029064** from reported input tokens at the report's dated price. This supersedes ADR-0049's earlier “pending credential” statement. It is heuristic agreement on a diagnostic set, not human-labeled production accuracy or current pricing. Source: [system-one-eval:79–120](system-one-eval-2026-10-18.md#L79), versus [ADR-0049:65–79](../adr/0049-decision-route-layer.md#L65).

D3's native runtime does **one forward per question**; bundling questions on its API does not imply shared-compute savings. Clef-flash's design has a joint schema head, but current post-review parity is explicitly unmeasured pending `audio-graph-a1c7`, and the route table still reserves native Clef. Do not select a large joint model merely to save HTTP calls. Sources: [d3 design:105–112](../designs/d3-native-runtime-2026-10-18.md#L105), [Clef design:16–24,90](../designs/clef-flash-native-2026-10-18.md#L16), [route reservation](../../src-tauri/src/decision/route.rs#L213).

For each route, measure:

- `net API saving = avoided generation input/output cost − decision API cost − extra repair/catch-up generation cost`.
- `net critical-path latency = decision queue + load + inference + transport/validation − avoided generation critical-path time`.
- Native inference has no per-call API bill, **not zero compute/energy/memory cost**. For A1/A2/B2 and regex normalization, the current heuristic baseline is already local and cheap; replacing it cannot honestly be advertised as an inference-speed improvement.
- For post-generation checks (B1/B3/B4/C3), the original generation has already been paid. Count fewer future repairs/wrong actions only if a measured replay demonstrates them. For C1, measure complete-session cost including final catch-up, not isolated skipped ticks.

These formulas and ceilings are proposed accounting, not empirical speedup ratios. Current source telemetry is insufficient to claim a specific dollar/latency reduction for any new route.

## 6. Shadow evaluation and the independent-holdout authority gate

### Required split and anti-leakage rule

[Seed `audio-graph-6345`](../../.seeds/issues.jsonl) explicitly corrects ADR-0049 G3: the holdout must be **disjoint and fixed before fitting temperature or selecting thresholds**, and promotion must enforce that split. ADR-0049 currently describes fitting T and evaluating G3 on “the record's labeled set”; this report does not treat that in-sample result as authority evidence ([ADR-0049:237–249,335–337](../adr/0049-decision-route-layer.md#L237)). Existing `audio-graph-f284` already calls for session/source splits and a separate calibration partition; extend it, do not invent a competing labeling project ([Seeds](../../.seeds/issues.jsonl)).

Proposed dataset protocol:

1. Define each question schema, eligible population, state construction, option order/candidate cap, baseline and target/safety metrics before labels are inspected for promotion.
2. Split at **session/source** level, with linked revisions, utterance paraphrases and speaker-identity examples kept together. Training/development may choose prompts/models; calibration fits T and thresholds; **independent holdout** is used only to decide G3. No same-meeting revisions in both calibration and holdout. For candidate-selection routes, retain the same candidate-generator version and record misses before classification.
3. Keep ADR-0049's minimum calibration fit counts (≥200 items/schema, ≥20/option); choose and justify separate holdout size by safety-error bounds and rare-option prevalence. There is no evidence that 200 total items establishes safe speaker-identity or high-impact authority.
4. Freeze the holdout manifest/hash and labels before T/threshold tuning. Store split ids/digests, counts, schema version, generator version, pin, served model, precision, thresholds, target/safety metrics and uncertainty intervals in a promotion evidence record. The present `CalibrationRecord` does not contain this full proof, so “fit exists” must not be the future promotion constructor's only predicate ([route.rs:307–325,807–832](../../src-tauri/src/decision/route.rs#L307)).
5. If holdout fails, stay shadow. After changing prompt/threshold/model using failure information, do not repeatedly call the same inspected holdout “independent”; version the experiment and obtain a fresh sealed holdout or explicitly disclose validation reuse with no promotion claim.

### Per-attempt observations

Use ADR-0049's record alongside the host artifact: route/model identity and precision; schema version; canonical-state digest; span **and relevant speaker/candidate** revision basis; raw probability/confidence; calibrated view and threshold snapshot; route answer and heuristic/baseline answer; effective source; latency/usage/error class. Names/text stay in authorized state/evidence artifacts, not option keys or content-free logs. Existing `DecisionRecord` is a starting point, not permission to log candidate names ([route.rs:369–397](../../src-tauri/src/decision/route.rs#L369), [ADR-0049:296–325](../adr/0049-decision-route-layer.md#L296)).

For S2-embedded decisions, baseline means the actual generated candidate/type/operation plus its deterministic ingest result—not a newly invented heuristic reference. For C1 prefilters, always run the baseline in shadow so misses can be measured. For speaker naming, label explicit/implicit cues separately and compare against the unknown/no-rename policy; “agrees with the other LLM” is not ground truth.

### Authority acceptance common to every wave

- G1 authorization/registry/producer/data-class coverage, including blocked-policy **no-write** fixtures for hosted shadows.
- G2 model/component pin and precision matched to a schema-specific calibration record. Native probabilities remain raw plus calibrated view; HTTP confidence stays vendor-relative with T=1 under the existing ADR. No universal 0.8 threshold ([ADR-0049:231–268](../adr/0049-decision-route-layer.md#L231)).
- **Corrected G3:** held-out target improvement and no safety regression on the frozen independent split. Publish abstention/coverage, confusion, precision/recall, ECE/Brier and safety confidence intervals; include language, ASR quality and overlap strata relevant to the route. Do not infer semantic accuracy from native/Python parity or heuristic agreement.
- G4 observed p95 meets the actual proposed per-request and per-job ceilings on CPU and each advertised execution provider. Include long state, cold load, queue contention and candidate-count scaling. A CPU path exceeding ADR's 500 ms gate is not offered as CPU-authoritative; no Windows/CUDA-only universal default.
- G5 same state/pin/options produces repeatable answers within documented tolerance; flag BF16 near ties (<0.05 margin). G6 unchanged deterministic fallback behavior, crash/session rotation safety and persisted replay without fresh model calls ([ADR-0049:329–346](../adr/0049-decision-route-layer.md#L329)).
- Authority activation must be a deliberate implementation change. The current enum supports shadow only; a calibration metric alone cannot enable behavior. Unavailable/abstained remains the recorded local baseline, never an implicit cloud fallback.

## 9. Uncertainties and tracker reconciliation

1. **No production quality data for new schemas:** existing parity and synthetic replay do not establish AudioGraph accuracy. Human-labeled consented datasets and independent holdouts are mandatory. New-route gains remain hypotheses.
